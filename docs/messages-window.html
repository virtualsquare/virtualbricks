Messages Window Rewrite

The messages window of Virtualbricks was one text view that grew a line of eventAsText() for every log event. It is now a light console built from structured messages: one line each, the brick it comes from, a symbol for its level, and the rest folded until you ask for it.

  • branch mg/abandon-glade on 2efeaf1
  • 1 new module, 4 changed
  • mock-ups: light console, T2 · S2 · N3 · M3 + M4

At a glance

Before
A single Gtk.TextBuffer, created at start and shared by every messages window. Each event became a line of 2026-09-24T17:47:09+0200 [virtualbricks.bricks.Process#error] …, coloured as a whole by its level. The message started some 60 characters in, the module path hid which brick spoke, a brick's stderr was an error, and there was no filtering.
Now
A list of structured messages, MessageLog, kept by the application. Each window renders it in its own text view, so each window has its own filter and its own open folds.
Looks
The light console mock-up, with the chosen options: time as a clock with a line for each day T2, a symbol per level S2, the brick or part of Virtualbricks N3, first line only with the rest on demand M3, program output as printed M4. Program output folds too.
Unchanged
Save and Report a bug write the same text as before. The log file, the terminal output and the error dialogs are untouched, apart from the namespace of four brick messages (below).

Reading a line

Every message is one line of four columns, aligned with tab stops that come from the width of the monospace font. When the first line wraps, the rest of it lines up under the message column.

Folds and program output

Folds

  • Extra lines of a message: ▸ 2 more lines after the first line. Old messages that started their extra lines with a tab lose that tab, because the fold already indents them.
  • A traceback: ▸ traceback, 3 calls, counting the File "…" lines. Opened, it's shown dim under the message column.
  • Extra lines of program output: the same ▸ N more lines toggle.

A click on a toggle opens or closes that fold only; the pointer turns into a hand over toggles. Expand all and Collapse all in the menu act on every message. A toggle label never breaks over two lines: its spaces are non-breaking.

Program output

What a brick's program prints on stdout or stderr is shown as printed, on a light grey band, with 2> before stderr. Carriage returns and the empty lines at the end of a chunk are dropped; everything else stays, spaces included. Program output is its own category: it has the terminal symbol, and the status bar counts its lines instead of counting it as errors. Each chunk that Twisted delivers is one message, so a program that writes many lines at once gets a single fold.

The filter

The field in the header bar filters as you type. Its terms combine: a message must match all of them.

TermKeeps
level:warningWarnings and worse. Also level:info, level:error, level:critical, and warn, err, crit for short. Program output counts as a warning on stderr and as info on stdout, so level:warning keeps sudo's complaint next to the error it explains.
source:tap0,router1Messages of those bricks, events or parts, or of every brick of a type: source:qemu. Case doesn't matter.
any other wordMessages whose source or lines contain it, case aside. A level: with an unknown level counts as a plain word.

Ctrl+F puts the cursor in the field, Esc empties it. Filtering renders the matching messages again and keeps the open folds.

Following, status bar and menu

  • Following is a toggle button in the header bar, on by default: new messages scroll into view. Scrolling up turns it off, scrolling back to the end turns it on, and so does clicking it. Opening a fold of an older message, when the view can scroll, also turns it off, since that means reading; opening a fold of the last message keeps the end in view.
  • The status bar shows 18 messages, or 6 of 18 messages with a filter, then the errors in red, the warnings in orange and the lines of program output. The counts are of all messages, not of the filtered ones. On the right: Following the newest or Paused.
  • The menu has Expand all, Collapse all, Save…, Report a bug… and Clear. Clear empties the messages of every open window, as before. The window closes from the header bar: the old Close button is gone.

How it works

The path of a log event, from any Logger to every open window:

MessageLogObserverEvents may come from any thread; it adds them in the GTK main loop.

An entry

entry_from_event() reads everything a window needs from the event once, as a frozen attrs class, so a later rename or deletion of a brick doesn't change past messages.

Derived from these: category (output, error, warn or info, with critical counted as error) for the status bar, rank for level:, and calls for the traceback toggle.

Where a message comes from

  1. If log_source is a base.Base, a brick or an event, that's the source, with its type in lower case.
  2. Else, if it has a brick attribute, as the process of a brick, a plug or a socket do, that brick is the source.
  3. Else the namespace names a part, by the longest match: …gui.windows.virtualbricks Main window, …migrate Migration, …config Settings, …project Project, …console Console, …events Events, …virtualmachines Virtual machines, …bricks Bricks, …link Connections, other …gui Windows, the rest of virtualbricks Virtualbricks. A namespace outside Virtualbricks shows its first word, such as Twisted.

Rendering

  • Columns. update_geometry() measures the width of a character of the view's font and sets four tab stops: after the time, after the image of the type, after the 14 characters of the source, after the symbol. The tag first gives the first line a negative indent equal to the message column, a hanging indent; the tag more gives the folded lines a left margin at that column. It runs again on style-updated, when the font changes.
  • Tags. One buffer per window, with named tags for every style (day, time, time-repeat, brick, part, warn, error, critical, output, stream, extra, toggle) and for finding things back: source, symbol, toggle-lines, toggle-traceback. Images are pixbufs in the buffer: the symbolic icons, coloured with Gtk.IconInfo.load_symbolic(), and the brick images at 16 pixels, both cached.
  • Marks. Each rendered entry keeps a mark, with left gravity, where its text starts; the next entry's mark is where it ends. The day line belongs to the entry that starts the day.
  • Folding in place. A toggle deletes the text of that entry only, inserts it again with the fold open or closed, and moves the next entry's mark after it. Nothing else moves.
  • The oldest message. When the log is full, the entry that falls out is deleted from the start of each view that shows it, and the new first entry is rendered again, since it now starts the first day.
  • Finding the entry under the pointer. Clicks, the hand cursor and the tooltips (query-tooltip) turn the pointer into a buffer iterator, then find its entry by a binary search over the marks, and its column by the tags there.
  • Filtering and Expand all render every matching entry again, from scratch.

Behaviour changes

  • Only the latest 2,000 messages are kept. The old buffer grew for as long as Virtualbricks ran. messages.LIMIT sets the number.
  • The console stays light on a dark desktop theme.
  • Each window filters and folds on its own. Clear still empties them all.
  • Save and Report a bug write every message, whatever the filter, in the same format as before.
  • In the log file, the four brick messages above change namespace, for example from virtualbricks.bricks to virtualbricks.switches.Switch.
  • The window is titled “Messages” instead of “Virtualbricks logging” and opens at 900 × 560; the old one only had a minimum size of 700 × 450.

Limits and next steps

  • Consecutive chunks of output from the same program fold one chunk at a time. Grouping them, or buffering the output of each process by lines, would give one fold per burst.
  • A dark palette taken from the dark console mock-up could follow the desktop theme instead of forcing the light one.
  • The information symbol is the theme's own; with Adwaita that's a lightbulb, not the circled “i” of the mock-ups.
  • Keyboard: folds open with the mouse or with Expand all; there's no key for a single fold yet.
  • High-DPI screens: the images in the buffer are drawn at 16 pixels without scaling, so they are sharp only at scale 1.
