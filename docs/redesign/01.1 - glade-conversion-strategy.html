The rules for turning the Glade files of Virtualbricks into Python code that builds the same widgets: no XML loaded at run time, and every window a class that can be read, searched and tested as code.

§1At a glance

Input
The 36 Glade files of virtualbricks/gui/data/*.ui, loaded by Gtk.Builder, with the custom widgets of glade-catalog.xml. No .glade files.
Output
A Python module per file, with the same name, that creates every widget in GTK 3 code. The .ui files go; git keeps them.
Classes
Each module holds the class that used the file, with its name and its code, plus build_ui() and get_root_widget().
Checked
Against Gtk.Builder, widget by widget, property by property, and by running every window (step 1.2, §6).

§3Conversion rules

Files

  • my_dialog.ui becomes my_dialog.py, in one package for all of them, then gui/windows/.
  • The modules never import gui.py or dialogs.py, which import them: what they share goes in windows/base.py, and a window that opens another imports it from the package.

In this order

  1. The widget hierarchy and its structure.
  2. Properties: titles, labels, sizes and the rest.
  3. Layout and packing: boxes, grids, notebooks, stacks.
  4. Signal handlers, connected to the methods of the class.
  5. Custom properties and settings.

Special handling

  • GTK widgets become their GTK 3 equivalents in Python. GTK 4 was never a target: the application, its reactor and its panels are GTK 3.
  • Signal handlers keep the names Glade gave them. The class that loaded the file already has them; a stub, with a comment, only where no class does.
  • Custom objects, the widgets of glade-catalog.xml, are made from virtualbricks.gui.widgets and marked with a comment.
  • Styles: the one style class of the files, title in confirmdialog.ui, is added to the widget’s style context. No file had CSS, which would have become a provider.
  • Names of widgets follow one schema, <purpose>_<kind>: ok_button, kvm_check, bricks_view. A widget is an attribute only when something reads it after build_ui(); the others are local variables. The schema is in step 1.2, §3.

§4Quality standards

  • Every widget is created and packed in code.
  • No XML files in the output: the .ui files and glade-catalog.xml are gone.
  • The code is readable and maintainable: the properties are the keyword arguments of the constructors, in Glade’s order.
  • A docstring on build_ui() names the file it replaces, in every generated module; about.py was written by hand.
  • The same windows as before: step 1.2 compares each built tree with Gtk.Builder’s.
