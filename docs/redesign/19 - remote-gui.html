Virtualbricks Remote GUI

virtualbricks --connect ssl:lab.example:8765 opens the windows of the Virtualbricks that runs on another machine. The project you see is the one open there, and whatever you do in the windows, from starting a brick to the OK of its settings, happens there, through protocol 2 of AMP. The windows keep a copy of that project, which the other end keeps up to date, so they read it as fast as today and only the actions cross the network.

§1At a glance

Below, the lab machine is the one whose Virtualbricks runs the bricks, and the desktop the one that shows the windows. They can be the same machine.

Start
virtualbricks --connect DESCRIPTION, with the descriptions that --command takes: unix:PATH, tcp:HOST:PORT, ssl:HOST:PORT:caCertsDir=FOLDER. Without --command or --run, --connect opens the windows, which speak AMP and assume protocol=amp when the description leaves it out (R1).
Lab machine
Any Virtualbricks with an AMP socket, with or without its own windows: --socket ssl:8765:privateKey=FILE:protocol=amp:interface=0.0.0.0. Nothing else to set.
The copy
The windows hold a copy of the open project, made of the real bricks, events and images, in a factory that never starts a program. The lab machine sends the project when the windows connect, then each change as it happens (R3).
Actions
Whatever the windows do goes through one object, the engine. On this machine it calls the bricks as today. Over a connection it calls the typed command of protocol 2, BrickStart(name=["vm1"]), or a command of the windows where the console has none, as the OK of a panel (R4).
Protocol
AMP, protocol 2, which the windows agree on with Hello; AMP lets the lab machine call the windows as well as answer them (R2). The commands of the windows join protocol 2 as new names; nothing of protocol 1, nor of the typed commands, changes.
Order
An answer comes after the changes its command made: once BrickNew is answered, the brick is in the copy.
Long work
Save as a New Image, Merge and the copy of Add Image take minutes, and are greyed over a connection for now (R13).
Projects
The Projects window lists, opens and changes the projects of the lab machine, and every window connected follows (R5).
Together
Any number of windows at once, the lab machine’s own too. An OK sets the keys its panel changed, and the last OK wins; the keys a panel didn’t touch keep what others set (R7).
Files
A path is a path of the lab machine, typed with completion from its folders (R9). Import and Export wait (R12).
Consoles
The console of a brick opens in a terminal of the desktop, through the connection (R8).
Quit
Closes the windows; the lab machine goes on (R6).
Plan
Seven steps, a commit each, on a new branch mg/remote-gui from develop. The first sends today’s windows through the engine and changes nothing you can see (§11).

§2Today

--command sends a line of the console to the Virtualbricks that runs, through its control socket, and prints the answer (page 15). Page 16 added AMP, page 17 added tcp and ssl with a token or client certificates, and --command speaks both protocols; --connect names the Virtualbricks it talks to. Page 20 added protocol 2 to AMP: a typed command for each command of the console, which a connection speaks once Hello agrees on 2. Whatever reaches a socket can do what the console does.

The windows use none of it. They hold the factory of their own process and call it and its objects directly:

  • The Bricks, Events, Images and Topology tabs read factory.bricks, factory.events and factory.images, and follow the signals factory.brick_added, brick_changed, brick_removed and those of the events and images.
  • A menu calls brick.poweron(), send_signal(), open_console(); a dialog calls factory.new_brick(), remove_brick(), rename_item(); the OK of a panel calls apply(draft), which moves the plugs and calls update_config(). The Projects window calls the workspace, the Readme tab set_description(), the Settings window set_setting(). grep finds about 50 such places, in some 20 modules.
  • Some read the machine they run on: qemu-img info of the image files, the answers of QEMU for the machine’s panel, lsusb for its USB devices, the programs of VDE and QEMU for New Brick and the warning at start, and the file choosers.

The console can’t do everything the windows do. It can’t set a key whose value is a list or a table, as usb_devices or the states of a Netemu: those kinds say “can’t be set from the console”. It can’t make an image file, work on the private copies of a machine’s disks, read or write the README, or import and export archives. brick monitor opens its terminal on the machine where Virtualbricks runs. The typed commands of protocol 2 are the console’s, so they can’t either, and they answer lines of text, not data (20 T3).

And a socket only answers: nothing tells a client that a brick stopped. The IDEAS have “Follow what changes through the control socket, watch… over AMP, as commands that Virtualbricks sends to the program (16 §10)”. This page does that, for the windows.

§3How it looks

On the lab machine, a Virtualbricks with an AMP socket; on the desktop, the windows. Across the network, ssl with the token or a client certificate, as page 17 set up. Or a unix socket that ssh forwards, which needs neither, since ssh already knows who you are:

  • The windows are the ones you know, with the project of the lab machine. The title names it: Virtualbricks (project: ospf-lab on lab.example), and its workspace too when it isn’t the setting there, as the lab machine’s own title does. A lab machine that runs a Virtualbricks in each workspace (page 21) gives each its own sockets, and the description picks one.
  • An action shows once the lab machine has done it: Start, and the row turns to Running with its process when the program runs there. A refusal opens a dialog, as today, with the lab machine’s message: “Cannot start ‘vm1’: not configured”.
  • The Messages window, File › Logs, shows the messages of the lab machine beside those of the windows, each with the machine it comes from, starting with the last 500 that the lab machine kept.
  • When the connection breaks, the windows turn insensitive under a bar: “The connection to lab.example port 8765 is lost: connection refused”, with Reconnect and Quit. If the lab machine quit, the bar says so. Reconnect builds the copy again from nothing.
  • What doesn’t work over a connection yet is greyed, with the tooltip “Not over a connection, for now” where the item can show one: Import and Export (R12); Save as a New Image and Merge in the menu of a disk, and Copy it to the image folder in Add Image, which leaves Use it where it is (R13); Show in Files, in the menus of an image and of a disk.
  • The messages of the lab machine, refusals and log, come in its language; the words of the windows in yours. The IDEAS already have this for --command.
  • The terminal that started the windows reads no console: the windows imply --noterm. --connect with a description and neither --command nor --run opens them; with either, it is today’s client, which sends commands and exits. --no-gui, --workspace, --lock and --socket are refused with the windows, as the options of a run are with --command: “--connect opens the windows of another Virtualbricks: --lock is for the one that runs the bricks”. The windows read a description without protocol= as AMP, and refuse protocol=text: “the windows speak AMP: protocol=text is for --command”. --command and --run keep text as the default, so to send a command to the socket of the windows, write protocol=amp: virtualbricks --connect tcp:lab.example:8765:protocol=amp --command status. --connect alone, which names the text socket .control of a workspace, is refused with the windows (R1). The windows take no lock and open no project of their own.

§4The two ends

The same windows serve both cases. What changes between them is two objects, which the windows get when they start:

  • What they read: the factory of this process, or MirrorFactory, the copy of the lab machine’s project (§5). Both are a BrickFactory, with the same objects and signals.
  • What they call: LocalEngine, which does what the windows do today, or RemoteEngine, which sends it (§6).

On the lab machine, each AMP connection that agreed on protocol 2 and asks to follow gets a Follower, which listens to the signals of the factory, the workspace and the settings, and turns them into commands that it calls on the windows (§7). Every AMP socket answers the windows; there is no option to open.

§5The copy of the project

The copy is built with the code that reads a project file. The lab machine sends the tables that project_document() writes, one object at a time, as brick_table() gives them, and the windows build them with restore_project() into a MirrorFactory. The classes are the real ones, so brickinfo and eventinfo, the drafts of the panels with their checks and their when, the summaries of the rows and the layout of the Topology tab all work as they are.

Beyond the project file

  • The state. A running brick has its process number: its proc is a stand-in that has the number and nothing to signal, so is_running() and brickinfo.process() answer as for a local one. An event that waits has the seconds left, which the windows count down on their own clock; no clock is shared between the machines.
  • The lab machine. The name of the project and of its workspace, its settings, the path of its runtime folder (New Brick and Rename check that the sockets of a name fit, 107 bytes; since page 21 it is in the folder of the workspace, 9 bytes longer), its version, which programs it lacks and what each kind of New Brick lacks there, and whether it has KSM.

Kept up to date

  • A change updates the object in place: load_config_table(), the plugs moved to their new sockets, the state, then changed.notify(). The rows and an open panel keep their objects.
  • A rename is a push of its own, since the copy finds objects by name; the objects whose references moved come as changes after it.
  • A new project opened on the lab machine empties the copy, and the whole project comes again; the tabs get their on_open(), as when a project opens today.

It never starts anything

The engine never calls a brick of the copy, but a window that still does, a bug, must not start a program on the desktop. So the bricks and events of a MirrorFactory refuse poweron(), poweroff(), send(), send_signal() and open_console() with an error that names the call. The copy is never saved either: the lab machine saves its project, and saves it every three minutes, as today.

The typed commands take values, not words, so a name or a description with spaces arrives whole, with nothing to quote; the lab machine reads each value with the kinds of the console, as it reads a line, and logs the line the command would be. §7The protocol

AMP, over any socket of --socket with protocol=amp, in protocol 2 (page 20). On tcp and ssl the windows prove the token first, with Challenge and Authenticate. Then they call Hello(protocols=[2]), and go on only if it answers 2 (R11). For what the console does they call its typed commands, those of console/ampcommands.py; for the rest, the commands below.

These join protocol 2 as new names, which the rule of page 20 allows without a protocol 3 (20 T7 A): a program of 2 that doesn’t know them never sends them. Before they run, they pass the checks of the typed commands: the proof of the token, the agreement on 2, and no key they don’t declare. They are in the record of protocol 2, tests/data/amp-protocol-2.txt, so a later change that isn’t additive fails a test, and the test that keeps the names of the typed commands unique covers them too. Protocol 1, Hello without a list and Run, doesn’t change, and --command goes on with it. Structured values, as the table of a brick, are JSON in an AMP string, since AMP has no tables.

Four rules

  • Pushes before the answer. Before it writes the answer of a command, the lab machine sends the pushes that wait. Once BrickNew is answered, New Brick finds the brick in the copy and opens its settings.
  • Once a turn. Changes gather until the end of the reactor’s turn, and each object goes once, in the order it first changed: starting 20 bricks sends 20 Changed, not 60. A new switch goes before the brick plugged into it.
  • 64 KiB. A value of AMP holds at most 64 KiB. A brick’s table is a few hundred bytes; a README or a project summary longer than that is refused with the message of page 16’s AnswerTooLong.
  • Nothing long holds the queue. The commands of a connection run one after the other (16 M4 A), so a merge of ten minutes would hold every Start behind it: the copy, the save and the merge are greyed for now (R13). The reads that take a moment and change nothing, DiskUsage and the facts of the machine, answer beside the queue.

Nothing here gives a connection more than it has: whatever reaches an AMP socket can already do what the console does, shell actions included (17 §12). Folder lists what the user of the lab machine can list, Attach reaches only the console sockets of a running brick, which the lab machine names itself.

§9Files, consoles, displays

A brick lives on the lab machine, and so does what it uses. Four things follow from that.

Paths

A path in a panel, in Add Image, the kernel and initrd of a machine, a CD-ROM: all are paths of the lab machine. A file chooser shows the desktop’s files, so over a connection a path row is an entry that completes from the lab machine’s folders with Folder, and its Browse button goes (R9). The image of a new disk is made there, with the qemu-img of the lab machine.

The trash

Removing an image or a project moves its files to the trash when the lab machine’s Virtualbricks has windows, which give it one. A Virtualbricks with --no-gui has no trash, so the windows offer to delete for good, as project delete --force does.

Consoles

Open Console, over a connection (R8):

  1. The windows listen on a unix socket, 0600, in a folder of their own, .connect-PID in the runtime folder, since the folders there without a dot are those of the workspaces (page 21); they open the terminal of the desktop’s settings on it, with vdeterm or unixterm, as the brick would.
  2. When the terminal connects, the windows open a new connection to the lab machine, prove the token if needed, agree on protocol 2, and call Attach(brick, console).
  3. The lab machine checks that the brick runs and connects to its socket: NAME.mgmt, the monitor of a machine, or its serial socket. It answers, and the connection carries bytes both ways from then on, AMP’s ProtocolSwitchCommand. The windows join the two sockets.

The desktop needs VDE’s vdeterm and unixterm for this; without them the item is greyed and its tooltip names the package.

The display of a machine

An SDL window shows on the screen of the lab machine, if it has one. VNC, -vnc :N, listens on port 5900 + N of every address of the lab machine, without a password, so a VNC viewer on the desktop reaches it today; the windows don’t open it for you yet (§13).

§10The code and the tests

New modules

  • virtualbricks/engine.py: the operations of §6 and LocalEngine. No GTK, no Twisted beyond Deferreds.
  • virtualbricks/remote/commands.py: the commands of the windows, §7, in protocol 2 beside console/ampcommands.py. Like it, the module loads only Twisted’s amp and the errors of ampwire and ampcommands, so a program that follows can import it, or copy it.

  • remote/tunnel.py: the consoles, in step 6.
