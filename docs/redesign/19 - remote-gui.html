Virtualbricks Remote GUI

virtualbricks --connect ssl:lab.example:8765 opens the windows of the Virtualbricks that runs on another machine. The project you see is the one open there, and whatever you do in the windows, from starting a brick to the OK of its settings, happens there. The windows keep a copy of that project, which the other end keeps up to date, so they read it as fast as today and only the actions cross the network.

§1At a glance

Below, the lab machine is the one whose Virtualbricks runs the bricks, and the desktop the one that shows the windows. They can be the same machine.

Start
virtualbricks --connect DESCRIPTION, with the descriptions that --command takes: unix:PATH, tcp:PORT, ssl:HOST:PORT:caCertsDir=FOLDER. The socket must speak AMP, and --connect assumes protocol=amp (R1).
Lab machine
Any Virtualbricks with an AMP socket, with or without its own windows: --socket ssl:8765:privateKey=FILE:protocol=amp:interface=0.0.0.0. Nothing else to set.
The copy
The windows hold a copy of the open project, made of the real bricks, events and images, in a factory that never starts a program. The lab machine sends the project when the windows connect, then each change as it happens (R3).
Actions
Whatever the windows do goes through one object, the engine. On this machine it calls the bricks as today. Over a connection it sends the console’s line, brick start vm1, or a command of its own where the console has none, as the OK of a panel (R4).
Protocol
AMP, which lets the lab machine call the windows as well as answer them (R2). New commands, with new names; those of page 16 don’t change.
Order
An answer comes after the changes its command made: once brick new is answered, the brick is in the copy.
Projects
The Projects window lists, opens and changes the projects of the lab machine, and every window connected follows (R5).
Together
Any number of windows at once, the lab machine’s own too. An OK is refused when a key it changes changed there since the panel opened (R7).
Files
A path is a path of the lab machine, typed with completion from its folders (R9). Import and Export wait (R12).
Consoles
The console of a brick opens in a terminal of the desktop, through the connection (R8).
Quit
Closes the windows; the lab machine goes on (R6).
Plan
Seven steps, a commit each, on a new branch mg/remote-gui. The first sends today’s windows through the engine and changes nothing you can see (§11).

§2Today

--command sends a line of the console to the Virtualbricks that runs, through its control socket, and prints the answer (page 15). Page 16 added AMP, page 17 added tcp and ssl with a token or client certificates, and --command speaks both protocols. Whatever reaches a socket can do what the console does.

The windows use none of it. They hold the factory of their own process and call it and its objects directly:

  • The Bricks, Events, Images and Topology tabs read factory.bricks, iter_events() and iter_disk_images(), and follow the signals brick-added, brick-changed, brick-removed and those of the events and images.
  • A menu calls brick.poweron(), send_signal(), open_console(); a dialog calls factory.new_brick(), del_brick(), rename(); the OK of a panel calls draft.apply(), which moves the plugs and calls brick.set(). The Projects window calls the workspace, the Readme tab set_description(), the Settings window set_setting(). grep finds about 50 such places, in some 20 modules.
  • Some read the machine they run on: qemu-img info of the image files, the answers of QEMU for the machine’s panel, lsusb for its USB devices, the programs of VDE and QEMU for New Brick and the warning at start, and the file choosers.

The console can’t do everything the windows do. It can’t set a key whose value is a list or a table, as usb_devices or the states of a Netemu: those kinds say “can’t be set from the console”. It can’t make an image file, work on the private copies of a machine’s disks, read or write the README, or import and export archives. brick monitor opens its terminal on the machine where Virtualbricks runs.

And a socket only answers: nothing tells a client that a brick stopped. The IDEAS have “Follow what changes through the control socket, watch… over AMP, as commands that Virtualbricks sends to the program (16 §10)”. This page does that, for the windows.

§3How it looks

On the lab machine, a Virtualbricks with an AMP socket; on the desktop, the windows. Across the network, ssl with the token or a client certificate, as page 17 set up. Or a unix socket that ssh forwards, which needs neither, since ssh already knows who you are:

  • The windows are the ones you know, with the project of the lab machine. The title names it: Virtualbricks (project: ospf-lab on lab.example).
  • An action shows once the lab machine has done it: Start, and the row turns to Running with its process when the program runs there. A refusal opens a dialog, as today, with the lab machine’s message: “Cannot start ‘vm1’: not configured”.
  • The Logs window shows the messages of the lab machine beside those of the windows, each with the machine it comes from, starting with the last 500 that the lab machine kept.
  • When the connection breaks, the windows turn insensitive under a bar: “The connection to lab.example port 8765 is lost: connection refused”, with Reconnect and Quit. If the lab machine quit, the bar says so. Reconnect builds the copy again from nothing.
  • What doesn’t work over a connection yet is greyed, with the tooltip “Not over a connection, for now”: Import and Export (R12).
  • The messages of the lab machine, refusals and log, come in its language; the words of the windows in yours. The IDEAS already have this for --command.
  • The terminal that started the windows reads no console: --connect implies --noterm. --no-gui, --run, --workspace, --lock and --socket are refused with it, as the options of a run are with --command: “--connect opens the windows of another Virtualbricks: --lock is for the one that runs the bricks”. The windows take no lock and open no project of their own.

§4The two ends

The same windows serve both cases. What changes between them is two objects, which the windows get when they start:

  • What they read: the factory of this process, or MirrorFactory, the copy of the lab machine’s project (§5). Both are a BrickFactory, with the same objects and signals.
  • What they call: LocalEngine, which does what the windows do today, or RemoteEngine, which sends it (§6).

On the lab machine, each AMP connection that asks to follow gets a Follower, which listens to the signals of the factory, the workspace and the settings, and turns them into commands that it calls on the windows (§7). Every AMP socket answers the windows; there is no option to open.

§5The copy of the project

The copy is built with the code that reads a project file. The lab machine sends the tables that project_document() writes, one object at a time, and the windows build them with restore_project() into a MirrorFactory. The classes are the real ones, so brickinfo and eventinfo, the drafts of the panels with their checks and their when, the summaries of the rows and the layout of the Topology tab all work as they are.

Beyond the project file

  • The state. A running brick has its process number: its proc is a stand-in that has the number and nothing to signal, so is_running() and brickinfo.process() answer as for a local one. An event that waits has the seconds left, which the windows count down on their own clock; no clock is shared between the machines.
  • The lab machine. The name of the project, its settings, the length of its runtime folder (New Brick and Rename check that the sockets of a name fit, 107 bytes), its version, which programs it lacks and what each kind of New Brick lacks there, and whether it has KSM.

Kept up to date

  • A change updates the object in place: load_config_table(), the plugs moved to their new sockets, the state, then notify_changed(). The rows and an open panel keep their objects.
  • A rename is a push of its own, since the copy finds objects by name; the objects whose references moved come as changes after it.
  • A new project opened on the lab machine empties the copy, and the whole project comes again; the tabs get their on_open(), as when a project opens today.

It never starts anything

The engine never calls a brick of the copy, but a window that still does, a bug, must not start a program on the desktop. So the bricks and events of a MirrorFactory refuse poweron(), poweroff(), send(), send_signal() and open_console() with an error that names the call. The copy is never saved either: the lab machine saves its project, and saves it every three minutes, as today.

§6The engine

Step 1 of the plan gives today’s windows the engine, with LocalEngine only. It is the IDEAS items “Extract the logic from the windows” and “Move startstop_brick out of VBGUI”, for what changes the project.

§7The protocol

AMP, over any socket of --socket with protocol=amp. The commands of page 16, Hello, Run, Challenge and Authenticate, don’t change, and Hello still answers protocol 1, the number --command checks: the new commands are new names, as page 16 asks. On tcp and ssl, they wait for the proof of the token, as Run does. Structured values, as the table of a brick, are JSON in an AMP string, since AMP has no tables.

Three rules

  • Pushes before the answer. Before it writes the answer of a command, the lab machine sends the pushes that wait. Once brick new is answered, New Brick finds the brick in the copy and opens its settings.
  • Once a turn. Changes gather until the end of the reactor’s turn, and each object goes once, in the order it first changed: starting 20 bricks sends 20 Changed, not 60. A new switch goes before the brick plugged into it.
  • 64 KiB. A value of AMP holds at most 64 KiB. A brick’s table is a few hundred bytes; a README or a project summary longer than that is refused with the message of page 16’s AnswerTooLong.

Nothing here gives a connection more than it has: whatever reaches an AMP socket can already do what the console does, shell actions included (17 §12). Folder lists what the user of the lab machine can list, and Attach reaches only the console sockets of a running brick, which the lab machine names itself.

§9Files, consoles, displays

A brick lives on the lab machine, and so does what it uses. Four things follow from that.

Paths

A path in a panel, in Add Image, the kernel and initrd of a machine, a CD-ROM: all are paths of the lab machine. A file chooser shows the desktop’s files, so over a connection a path row is an entry that completes from the lab machine’s folders with Folder, and its Browse button goes (R9). The image of a new disk is made there, with the qemu-img of the lab machine.

The trash

Removing an image or a project moves its files to the trash when the lab machine’s Virtualbricks has windows, which give it one. A Virtualbricks with --no-gui has no trash, so the windows offer to delete for good, as project delete --force does.

Consoles

Open Console, over a connection (R8):

  1. The windows listen on a unix socket of their own runtime folder, 0600, and open the terminal of the desktop’s settings on it, with vdeterm or unixterm, as the brick would.
  2. When the terminal connects, the windows open a new connection to the lab machine, prove the token if needed, and call Attach(brick, console).
  3. The lab machine checks that the brick runs and connects to its socket: NAME.mgmt, the monitor of a machine, or its serial socket. It answers, and the connection carries bytes both ways from then on, AMP’s ProtocolSwitchCommand. The windows join the two sockets.

The desktop needs VDE’s vdeterm and unixterm for this; without them the item is greyed and its tooltip names the package.

The display of a machine

An SDL window shows on the screen of the lab machine, if it has one. VNC, -vnc :N, listens on port 5900 + N of every address of the lab machine, without a password, so a VNC viewer on the desktop reaches it today; the windows don’t open it for you yet (§13).

§10The code and the tests

New modules

  • virtualbricks/engine.py: the operations of §6 and LocalEngine. No GTK, no Twisted beyond Deferreds.
  • virtualbricks/remote/commands.py: the AMP commands of §7. console/ampwire.py keeps page 16’s, short enough for a program to copy.
  • remote/follower.py: the lab machine’s side: Follower, the gathering of changes, the log it keeps, and the answers to the new commands, which AMPControl takes on.
  • remote/mirror.py: MirrorFactory, the stand-in process, the deadlines of the events, the refusals.
  • remote/client.py: RemoteEngine, the connection over unix, tcp and ssl with Twisted, the proof with ampwire.authenticate(), the certificates with console/tls.py, Reconnect.
  • remote/tunnel.py: the consoles, in step 6.

What changes

  • app.py and scripts/virtualbricks.py: --connect, its refusals, and a start with neither lock, migration, workspace, autosave nor sockets.
  • gui/gui.py: RemoteApplication beside Application; VBGUI gets its factory and its engine.
  • The windows: the modules of §2 call the engine.
  • config/settings.py and config/workspace.py: a signal when a setting changes and when a project opens, for SettingsChanged and Opened; neither imports anything of the GUI.
  • console/control.py: AMPControl writes the waiting pushes before each answer.

Tests

  • The windows with a fake engine: each menu item, button and OK calls the operation it should, and nothing else changes the project.
  • The copy, both ends in one test with Twisted’s iosim: a real factory on the lab side, a MirrorFactory on the other. After each change, new, set, connect, rename, delete, a start with a fake process, a project opened, both give the same project_document() and the same states.
  • The rules: pushes before the answer, once a turn in order, the 64 KiB refusal, Apply all or nothing, its Conflict.
  • The connection: the proof over tcp, the certificates of tests/data/tls over ssl, a lab machine of another version refused, the bar when the connection is lost, Reconnect.
  • The copy refuses to start a brick or an event.
  • The consoles: bytes both ways between a fake terminal and a fake console socket.

My choices, which the questions don’t cover: --connect assumes protocol=amp and refuses protocol=text; it implies --noterm and refuses the options of a run; cwd is never sent; every AMP socket answers the windows, with no option of its own; the lab machine keeps its last 500 messages while it has an AMP socket; errors open dialogs only for the windows’ own actions; Reconnect is a button, not an automatic retry; JSON inside the values of AMP; the copy is never saved; the name of the lab machine in the title.

Checked on 29 September, in the code at 6430114: the kinds ListOf and Record have no parse(), so brick set refuses usb_devices and the states of a Netemu. --command refuses an AMP socket whose Hello answers a protocol other than 1. project_document() and restore_project() write and read a whole project as tables. The Projects window, the name dialog, the Readme tab, the image dialogs and the import already take a workspace as an argument, the global one by default; the tabs take their factory.
