The Brick Factory

BrickFactory holds the bricks, the events and the images of the open project, and all of Virtualbricks uses it: the windows read it, and the console, the sockets, the project files and the bricks call it. This page asks whether it belongs inside the engine of the windows, which it doesn’t; whether its name should change; and whether the end of the run, which the run waits for through the factory, belongs to the application.

§1At a glance

Engine
The factory stays out of the engine. Only the windows have an engine; the console, the sockets, the project files, the converter of 2.1 and the bricks use the factory alone, and the windows of --connect read a copy that is a BrickFactory too (§3).
Docstring
Fixed in 41186a48: the objects of the open project, their signals, and who calls it.
Name
BrickFactory stays (F1): a rename touches about 650 lines in 66 modules and 1 270 lines in 94 test files, and changes no behaviour. If it changes, to Testbed, the README’s word (§4, F2).
End of the run
The Deferred that ends the run becomes the application’s: main.run() waits for app.done, and the windows of --connect fire their own, not the copy’s. The factory keeps quit() and quitting (§5, F3).
Plan
One step for F3, with the log line Engine: Bye!; a second one, mechanical, only if F1 isn’t A (§6).

§2Today

brickfactory.py holds, by name, the bricks, the events, the images and the sockets of the open project, and ten signals: a brick, an event or an image came, changed or went, and quitting. It checks the names (check_name(), check_brick_name()), and a rename or a delete reaches whatever names the object (rename_item(), users()). Its calls answer at once. One factory lasts the whole run: opening a project empties it with reset() and fills it again.

§3Into the engine

It could be done: LocalEngine takes the bricks, the events, the images and the signals, and the factory goes. It doesn’t fit, for three reasons.

  • Most of the program has no engine. Everything in §2 but the windows holds the factory alone. Merged, the console, the sockets, the converter and the bricks would hold an object that brings the workspace, the reactor’s clock, qemu-img, the USB devices and the programs, which they don’t use; or every mode would make an engine, the converter’s too.
  • The windows read the same thing on both sides. MirrorFactory is a BrickFactory, so that the copy of another Virtualbricks is built by the code that reads a project file, and the tabs read engine.factory and follow its signals whichever engine they have. A factory inside LocalEngine needs MirrorFactory inside RemoteEngine too, or the two engines differ in what the windows read.
  • Two kinds of call. The factory’s calls answer at once; the engine’s return a Deferred, so that a window waits for this machine as it would for another (19 §6). On one object, a window could call the new_brick() that answers at once where it should call the engine’s, and over a connection that changes the copy, not the project there. Page 19 put the line where the windows stop: they read the factory, and change things through the engine.

So the two stay as they are: the factory, the objects of the open project for whoever holds it; the engine, what the windows ask, of this machine or of another.

§4The name

What it says wrong

  • It makes the bricks, new_brick(), but it also holds the events, the images and the sockets, renames, deletes, checks the names and quits.
  • It called itself the core engine in its docstring until 41186a48, and still does in the log, when Virtualbricks quits: Engine: Bye! (brickfactory.py:70).
  • Twisted has factories too. The protocols of the control sockets and the console’s terminal call it brickfactory, since a protocol of Twisted has a factory of its own (console/control.py, console/terminal.py).

What a rename touches

  • The class, its module (44 modules import it) and MirrorFactory.
  • The attributes and the parameters that hold it: engine.factory, brick.factory, Context.factory, brickfactory, and every factory argument. With the class, about 650 lines in 66 modules.
  • The tests: 1 270 lines in 94 files, make_factory() among them.
  • What users see: the name factory in the Python shell, written in virtualbricks(1), in command-line.html and in the README. It could stay as a second name for a release.
  • The design pages name the factory in 18 of them; they stay as written, as the history of each step.

None of it changes what Virtualbricks does. The confusion with the engine came from the docstring, now fixed, and the clash with Twisted is in two modules, where it is already handled. Hence F1 A: keep the name. The log line goes in any case (§6).

§5The end of the run

Today

  • Application.install_factory() makes the factory with a new Deferred (app.py:165), and main.run() ends when it fires, await factory.quit_d (main.py:134); then the reactor stops, the project is saved, the settings stored and the lock released.
  • factory.quit() (brickfactory.py:195) refuses while bricks run, logs Engine: Bye!, stops the events, tells quitting and fires the Deferred. The console’s quit calls it (console/general.py:150), and through run() so do Ctrl+D in the terminal, the control sockets, --run and an event that runs quit; the windows’ Quit calls it through LocalEngine.quit() (engine.py:570).
  • quitting is followed by the main window, whose tabs stop following the factory and the Readme tab saves its text (window.py:166), and by Follower, which tells the windows of another Virtualbricks Quitting (follower.py:418).
  • The windows of --connect don’t quit the Virtualbricks there. RemoteEngine.quit() calls RemoteApplication.quit() (gui/app.py:470), which closes the windows and the connection, and ends the run by firing the copy’s quit_d (gui/app.py:486). The copy itself never quits: its end is ended, when Quitting comes.
  • MirrorFactory (mirror.py:133) and the converter make a Deferred that nobody waits for.

The factory doesn’t make the Deferred, install_factory() passes it in; but the run waits for it through the factory, and the windows of --connect reach into the copy to fire it.

The proposal

The application keeps what ends its run (F3 B):

RemoteApplication.quit() fires self.done rather than self.copy.quit_d. factory.quit() doesn’t change: it fires the Deferred it was given, which is app.done. Nothing that users see changes.

Why not take quitting out of the factory altogether (F3 C): quit() needs the bricks, for the refusal, and the events, to stop them, so whatever holds it would hold the factory as well; and everything that runs a command would carry a second object for one command: run() has seven callers in five modules, app.py, bricks/eventaction.py, console/control.py, console/general.py and console/terminal.py. The two that follow quitting hold the factory already.
