Virtualbricks Single-Instance Mode

A new option, --lock, sets the single-instance mode, how many Virtualbricks can run at once: one on the machine, the default and today’s rule; one for each user; or any number. A Virtualbricks in the user mode respects one in the system mode, and the locks go away with the process, even after a crash.

§1At a glance

The option
virtualbricks --lock system|user|none sets the single-instance mode for one run. Without it, system. Any other word stops the start: --lock: 'workspace' is not one of system, user, none.
system
One Virtualbricks on the machine, whoever runs it and whatever its workspace, as today. It holds the system lock, /tmp/virtualbricks.lock, alone.
user
One for each user, so the users of a shared machine stop blocking each other. It holds $XDG_RUNTIME_DIR/virtualbricks/.lock alone and shares the system lock with the others in this mode. It doesn’t start while a Virtualbricks in the system mode runs, and while it runs, none in the system mode starts.
none
No lock: it starts beside any other, and the others don’t see it. It is for a test instance beside your own, or for two workspaces at once.
Who
A refused start says which processes hold the lock and who started them: Held by process 4242 of bob.
Crashes
The locks are flock(2) locks: the system releases them when the process ends. No lock is left behind, and the message that told you to delete one goes.
Migration
Migrating your files in place holds the locks of the user mode: it waits for your own Virtualbricks, whatever its mode, and for one in the system mode.

§2The lock before

Virtualbricks took a single lock, /tmp/vb.lock, through Twisted’s FilesystemLock: a symbolic link whose target is the process id. The configuration redesign kept it global (D3) and listed its faults:

  • One user blocked the machine. While Alice ran Virtualbricks, Bob couldn’t start his, on his own files.
  • Another user’s lock was an error. To check a lock, FilesystemLock sends signal 0 to its process. For another user’s process that raises EPERM, so Bob got a traceback instead of the message.
  • A crash could leave the lock behind. Your own stale lock was cleaned up, but not another user’s: /tmp is sticky, and only its owner can remove it.
  • No test instance beside your own. A throwaway HOME still met the same lock, as the README said.

§3The three modes

ModeAt mostHoldsDoesn’t start while
system, the default one Virtualbricks on the machine the system lock, exclusive any other Virtualbricks holds the system lock, shared or exclusive
user one for each user the system lock, shared, then the user lock, exclusive a Virtualbricks in the system mode runs, or one of yours holds your user lock
none no limit nothing never refused

This is a readers–writer lock on the machine. The system mode is the writer: it needs the machine to itself. The user mode is a reader of the machine, and a writer of its user.

Holding the shared system lock is how the user lock complies with a system lock already held, as you asked. It works in the other direction too: while any Virtualbricks in the user mode runs, the system mode can’t have the machine to itself, so it refuses to start (L1).

§5The locks

flock

Both locks are flock(2) locks, shared or exclusive, taken without waiting (LOCK_NB). The kernel releases them when the process ends, however it ends, so there is never a stale lock to clean up. The files themselves stay; an empty file costs nothing, and deleting a lock file that someone may be opening is a race.

A flock belongs to an open file, not to a process: two opens of the same file in one process exclude each other. The tests rely on this and hold several Virtualbricks’ locks in one process (§8).

Where

System
/tmp/virtualbricks.lock, a fixed path. Not the temporary directory of TMPDIR, which can be a user’s own and would hide the lock from the others. A new name, because a Virtualbricks from before this change reads /tmp/vb.lock as a symbolic link: on a plain file its readlink fails and it would stop with a traceback (L4).
User
.lock in the runtime directory, $XDG_RUNTIME_DIR/virtualbricks/ (/tmp/virtualbricks-uid/ without the variable), next to the sockets and private to you. A project’s name never starts with a dot, so no project’s runtime directory can be named like it.

Opening the system lock safely

  • Read-only, without following a symbolic link (O_RDONLY | O_NOFOLLOW). A link planted at the path fails the open, rather than making Virtualbricks create or lock a file elsewhere. flock works on a file opened read-only. Without O_NOFOLLOW, a dangling link would also make the open loop forever, and the tests check it.
  • Created only if it is missing, with O_CREAT | O_EXCL. systemd sets fs.protected_regular (2 on this Debian), which refuses O_CREAT on another user’s file in a sticky directory such as /tmp, even when the file exists already.
  • Readable by everyone: the file is set to mode 0644 after it is made, whatever the umask, so another user can open it to share it.
  • Not inherited: Python opens files close-on-exec, so QEMU and VDE, which Virtualbricks starts, don’t keep the lock after it exits.

§6Messages

When a lock is held, Virtualbricks exits with status 1 and says why. A failed exclusive lock on the system file doesn’t tell who holds it; a second try with a shared lock does: if that succeeds, the holders are in the user mode.

StartingHeld byMessage
system or userone in the system modeAnother Virtualbricks is running on this machine with --lock system, the default, which lets only one run at a time.
systemsome in the user modeVirtualbricks is running on this machine with --lock user, one for each user: start this one with --lock user as well.
userone of yours, in the user modeAnother Virtualbricks of yours is running, and --lock user lets each user run one.
system or usernobody, but the file can’t be openedCannot take the lock /tmp/virtualbricks.lock: Permission denied. With --lock none, Virtualbricks runs without locks.

A migration in progress holds the locks of the user mode, so it is reported as a Virtualbricks in that mode.

Who holds the lock

Each message then names the processes that hold the lock, and the user that started each:

  • The processes come from /proc/locks, which lists every flock with the process that took it and the device and inode of its file, as FLOCK ADVISORY READ 4242 00:28:19858. Virtualbricks keeps the lines of its lock file, leaves out the processes that only wait for it, and names each process once.
  • The user is the real user of the Uid: line of /proc/pid/status, the one who started the process, by name, or by number when it has none.
  • Any user can read both, so Bob sees Alice’s process. Where /proc is mounted with hidepid, another user’s process shows without its user. A process in another PID namespace, as in a container, shows as 0 and is left out. When /proc/locks can’t be read, the message ends after its first sentence.
  • Looked up after the refusal, once this Virtualbricks holds nothing of the file it asks about, so it never names itself. A holder that exits in between is simply not named.

§7The migration

The migration command and window hold the app’s lock while they change your files in place (02 §11). They now hold the locks of the user mode (L3). They wait for your own Virtualbricks, whatever its mode, since one in the system mode holds the system lock alone. They don’t wait for another user’s Virtualbricks in the user mode, which never touches your files. When a lock is held, the command still exits with status 3 and the window still asks you to close Virtualbricks.

The migration at startup runs inside the app, under the locks it already holds. With --lock none, it runs without any.

§8The code and the tests

  • virtualbricks/locks.py, new: SYSTEM, USER, NONE, POLICIES; acquire(policy); Lock (policy, locked, unlock(), which can be called twice); Held (policy, holder, path, holders; str() is the message of §6); holders(path), the pairs of process and user from /proc, whose root is PROC for the tests.
  • locations.py: SYSTEM_LOCK_FILE replaces LOCK_FILE; user_lock_file().
  • app.py: the --lock option and its check; _LockedApplication takes the locks of config["lock"] and releases them after the reactor’s shutdown; its lock argument goes.
  • migrate/engine.py: lock_in_place() returns acquire(USER), or None when a lock is held. migrate/gui.py only changes a type.
  • Tests: tests/test_locks.py, new, 22 tests: each mode against the others, another user played by another runtime directory, a refused start that holds nothing, the file modes under umask 077, a symbolic link not followed, descriptors not inherited, and child processes: one that holds the lock and is killed with SIGKILL, after which the lock is free, two that share the system lock, one that holds your user lock, each named in the refusal. The lines of /proc/locks and the users of a fake /proc have tests of their own. test_app.py has 5 on the option and the launcher, in place of one on the lock’s path; test_locations.py one on user_lock_file(); the migration’s lock tests follow the new rules.
  • Test helpers: isolate() points the system lock into the test’s folder and checks at the end that it is free; hold_lock(test, policy, user) holds the locks of any mode, as another user when user is given.
  • Docs: the README (the option, the modes, and --lock none for a test instance), virtualbricks-config(5) and config-files.html (both files under Files), the TODO.

Checks: nine deliberate breaks of locks.py and app.py, one at a time, each made the new tests fail. The real virtualbricks ran on GTK’s Broadway display with a second one started beside it in each mode. Every refusal of §4 and §6 came out as written, and --lock none ran beside a Virtualbricks in the system mode.
