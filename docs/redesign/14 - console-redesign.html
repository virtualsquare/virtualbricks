Virtualbricks Console Redesign

The console becomes a command language for what the windows do: make, change, start, stop, rename, duplicate and delete bricks and events, with their links, the images, the settings and the projects. One grammar, noun verb arguments, for the terminal, the scripts and the events, with quoting, help and completion, and an answer for every command.

The differences from the plan: brickinfo.py and eventinfo.py moved to bricks/ with their names, not into kinds.py and event.py. The table is console/command.py, with help, status, source and quit in general.py, and run() is in console/dispatch.py, which imports the modules of the commands: the package itself exports nothing. A socket card has no name=, since the draft of a card has none: the socket is named after the machine and the card. A console action is checked as it’s added, by event action add and in the event editor, whose field shows a warning icon with the reason as its tooltip, not a line under it; the parser checks the words and the names, and the keys are checked when the action runs. A project isn’t checked when it opens: the upgrade from format 1 reports the commands it can’t read. image list shows the name, the file and the machines, without the format and the size. When the input isn’t a terminal, as a pipe, the console reads it a line at a time, each command after the one before, and quits at its end. Ctrl+L clears the screen, Ctrl+A and Ctrl+E go to the ends of the line, and Tab lists the words when it has nothing to add. A run on a real terminal found that Twisted’s terminal protocol sets factory on the protocol it runs, which hid the factory of the bricks: the console keeps it as brickfactory, and a test goes through that protocol. The debugger of --debug is off with --noterm, as it was with --daemon. The manual page virtualbricks(1) and its web page, docs/command-line.html, have every option and command, and a test checks both lists against the code.

Since then: the line has the keys of readline, in the console and in the Python shell, in console/lineedit.py. Ctrl+R and Ctrl+S search the history as you type; Ctrl+B, Ctrl+F, Alt+B, Alt+F, Ctrl+Left and Ctrl+Right move by characters and words; Ctrl+D deletes the character under the cursor, and quits only on an empty line; Ctrl+W, Alt+Backspace, Alt+D, Ctrl+U and Ctrl+K delete words and the two halves of the line, and Ctrl+Y puts back what they deleted last, together when they came one after the other; Ctrl+T and Alt+T swap characters and words. The line is drawn with the cursor where it is, after Ctrl+L and Tab too. The manual page lists every key.

§1At a glance

Grammar
A noun, a verb, then names, KEY=VALUE pairs and flags, split as the shell splits words: brick set vm1 memory=1024 kernel_command_line="console=ttyS0 root=/dev/vda". A name is never a command word, so any name works (K1, K3).
Commands
Bricks: list, new, show, set, start, stop, rename, duplicate, delete, connect, a machine’s cards, and the process menu: pause, suspend, restart, kill. Events: list, new, show, set, their actions, start, stop, run now, rename, duplicate, delete. Then images, settings and projects, and help, status, source, python, quit (K2).
Answers
Every command answers: what it made, what it shows, or one error that says what and why. A start waits until the brick runs or fails, and says which (K4).
Events
Starting or stopping a brick or an event becomes an action of its own, {kind = "start", target = "sw1"}, which a rename follows. Other console commands use the new grammar, and one that fails is an error in the log, no longer a success. Projects written before are rewritten once, as format 2 (K5).
Terminal
History, line editing and Tab completion; the prompt names the open project; python opens the Python shell, as today (K8).
No GUI
virtualbricks --no-gui runs the same program without GTK, for a lab on a server; --run FILE and source FILE run the commands of a file (K6, K7).
Code
A package without GTK, virtualbricks/console/: the parser, one table of the commands that also gives the help and the completion, the commands, the terminal. What the console shares with the windows moves out of gui/ first.
Plan
Seven steps, a commit each, on this branch (§9).

§2The console today

Started from a terminal, Virtualbricks reads commands on its standard input, unless it has --noterm or --daemon. console.VBProtocol takes a line and splits it at the spaces. When the first word is one of its commands, it calls do_word; otherwise the first word is taken as the name of a brick or an event, and the second as what to do with it. Its help says:

The help doesn’t list config get KEY and config set KEY VALUE for the settings, images list, python, which opens a Python shell with the factory in it, warranty, and the short forms q, cfg, i.

Who else speaks it

  • Events. An action {kind = "vb", command = "sw1 on"} runs a console command through console.parse(), which answers to a transport that drops every line.
  • The event editor. eventinfo.read() takes NAME on and NAME off as Start or Stop a brick or an event, and anything else as a console command; eventinfo.write() writes them back.
  • The migration of 2.1. convert_command() gives BRICK config KEY=VALUE the key names of today.
  • Five tests in tests/test_console.py: show, new, config and the settings.

§3What gets in the way

From the code at af06a05. Items marked checked were run on this branch, through VBProtocol.

Commands that fail, or fail silently

  • checked brick sw1 on does nothing: do_brick passes the words unpacked, so “on” becomes the letters o and n. brick sw1 config ports=4 answers “invalid number of arguments”. The help lists both as TODO.
  • checked A value with a space can’t be set: vm1 config kernel_command_line=console=ttyS0 root=/dev/vda answers “No such parameter root”.
  • checked A brick named like a command can’t be reached: after new switch list, which works, list show answers “invalid number of arguments”.
  • checked sw1 help, in the help, does nothing. brick nope on says “No such event ‘nope’”.
  • checked An event’s console command that fails is logged as a success: the event with sw1 config nope=1 logs “Process ended with exit code None”, and the error went to the transport that drops it.
  • sw1 on doesn’t wait for the start, nor say whether it worked: the Deferred of poweron() is dropped, where the windows log its failure.
  • checked reset deletes every brick, event and image of the open project without asking, and the autosave writes the empty project within three minutes.
  • Protocol.lineReceived turns every TypeError, a bug in a command included, into “invalid number of arguments”.

What it can’t do

  • Rename, duplicate; an event’s delay and actions, and Run Now; the process menu (pause, continue, suspend, resume, reset, restart, kill).
  • A machine’s cards: connect fills the first free plug, with no model, MAC address, socket card or host-only card, and disconnect unplugs them all. A wire’s ends can’t be chosen.
  • Images: only a list. Settings: no list. Projects: nothing.

How it’s built

  • The answers have no shape of their own: ps, list, socks and connections each lay them out their own way, and an error looks like any other line.
  • One class parses, dispatches, formats and changes the project, so the tests call brick_action() directly. The terminal, Console and Manhole, lives in brickfactory.py.
  • The terminal is the tty’s own line mode: no history, and the arrows print escape codes. The greeting says “Copyright (C) 2022”, and warranty prints “NotImplementedError”.
  • The console exists only beside the windows: scripts/virtualbricks.py always starts GTK, though brickfactory.py and console.py load none of it.
  • What the console would share with the windows is under gui/, whose package loads GTK: the kinds, names and summaries of the bricks (brickinfo.py), the actions of the events (eventinfo.py), restart, suspend and resume (brickmenu.py).

§4The command language

Rules

  • A line is NOUN VERB ARGUMENTS: the nouns are brick, event, image, setting and project, and a few words stand alone: help, status, source, python, quit. A name is always an argument, never a command, so a brick can be called list.
  • Words are split as the shell splits them, with shlex: quotes keep spaces, a backslash escapes, # starts a comment. Settings are KEY=VALUE, as many as needed in one command, all checked before any is set.
  • Every command succeeds or fails. A success answers when there is something to say: the name given to a new brick, the process of a started one. A failure is one message that names the brick, the key and the reason. Nothing fails without a word.
  • What takes time waits: start, stop, restart and suspend come back when they are done or failed.
  • The words of the windows: start, stop, rename, duplicate, delete, the kinds of New Brick (switch, vm, tap…), the keys of project.toml, the names of the Settings window.
  • One table lists the commands, their arguments and their help: the parser, help, the completion and the manual page read it, so they can’t drift apart.

§6Events and their commands

An event’s actions are kept as console or shell commands, and the event editor guesses from the text which were Start or Stop. With K5 B, starting and stopping get actions of their own, and the console commands speak the new grammar:

  • start and stop take a target, a brick or an event: names are unique among bricks, events and images, so one word is enough. Renaming the target renames it in every action, as renaming an event already does for on_start.
  • console is any command of §4. It is checked when the project opens and when the event editor takes it; shell stays as it is.
  • An action that fails is an error of the event in the log, with its number and its command: “Event bigger, action 2: router memory: 99999999 is outside 1–99999”. The other actions still run.
  • Format 2. A step in projectfile.UPGRADES rewrites a format 1 file once, when it opens: NAME on and NAME off become start and stop; NAME config KEY=VALUE… becomes brick set or event set, quoted where needed; NAME remove, connect, disconnect, new and config set become their new commands. Anything else stays a console command, and the report of the opening says it may not run. An older Virtualbricks then refuses the file, as it refuses any newer format.
  • The migration of 2.1 writes format 2 directly, after its renames of keys.
  • The event editor keeps its six kinds: Start and Stop a brick or an event become start and stop with a target. Its console field is checked by the parser as you type, with the error under it, as the name fields are.

§7Terminal, scripts, no GUI

The terminal

  • Line editing, history and completion with twisted.conch.recvline on the raw terminal that the Python shell already uses (K8). The history is kept in $XDG_STATE_HOME/virtualbricks/history, the last 500 lines. Tab completes nouns, verbs, names of bricks, events and images, kinds, KEY= and the choices of a key.
  • Keys: Ctrl+C clears the line, or stops waiting for a command, not the brick; Ctrl+D quits, as today.
  • The prompt is the name of the open project. The greeting says the version and how to get help.
  • python switches to the Python shell, with factory, and Ctrl+D comes back: the same as today, without the switching of brickfactory.Console.
  • Messages go through _() as those of the windows; command words, kinds and keys stay English (K9).

Scripts

  • virtualbricks --run FILE runs a file of commands once the last project is open; source FILE runs one from the console (K7).
  • Empty lines and # comments are skipped. The first error stops the file, as lab.vb:7: router memory: 99999999 is outside 1–99999; the program goes on.

Without the GUI

  • virtualbricks --no-gui runs brickfactory.Application with Twisted’s default reactor and never loads GTK (K6). The startup migration logs what it converts instead of opening its window. The console is the way in.
  • With --noterm as well, it runs the lab of --run until it gets SIGTERM. --daemon, which has no help and does what --noterm does, and keeps the debugger of --debug away, goes.
  • Talking to a Virtualbricks that runs already, through a socket, is for later (§11).

§8The code

  • A command is a function of the factory and its parsed arguments that returns a Deferred of its answer, or fails with a CommandError that holds the message. The terminal prints; the events log; the scripts stop at the first failure.
  • The table declares each argument’s kind (a brick, an event, a kind, KEY=VALUE, a flag), from which the parser checks, the completion proposes and help writes.
  • The windows keep calling the model, not the console; they import the moved modules from their new places. The event editor uses the parser to check its console field.
  • No GTK: a test imports virtualbricks.console in a fresh process and checks that no gi module is loaded, as for the workspace.

§11Later

  • A control socket in the runtime folder, so that virtualbricks --command … or a script talks to a Virtualbricks that runs (K6 C).
  • Answers in JSON for scripts, as brick list --json.
