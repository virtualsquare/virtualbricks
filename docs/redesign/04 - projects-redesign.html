§2What gets in the way today

From the code on this branch; the canvas redraws these windows in its first row.

Import

  1. It extracts everything before you choose anything. Pressing Next on the first page runs bsdtar on the whole archive, disk images included, into a randomly named folder of the workspace (_HumbleImport.step_1, ProjectManager.import_prj). The folder stays behind if the import fails or Virtualbricks stops, and once it holds a project file the Open list shows it.
  2. You can't finish without a file for every image. The third page stays incomplete until every image has a path (all_paths_set), even one you don't have.
  3. The choices hide in table cells. A path changes only by clicking its cell, marked “(Click here to select an image)”, and one question, where each image comes from, is split across two pages.
  4. The last page shows True and False for “Open” and “existing project overwritten”.
  5. Overwriting deletes the existing project, even the open one. Project.rename(name, overwrite=True) removes the folder while the factory still holds its bricks; the next autosave writes them over the import.
  6. The paths of this computer come last: the qemupath and vdepath choice (S3) is on the confirmation page.
  7. Private disks are rebased as if every image were qcow2 (qemu-img rebase -F qcow2).

Managing projects

  1. Five dialogs that show only names. Open and Delete list names (projectlistdialog.py), New and Rename ask for one (simpleentry.py), Save As lists them again (saveprojectasdialog.py). Nothing tells two labs apart.
  2. New and Rename don't check the name. A name that exists or isn't valid raises ProjectExistsError or InvalidNameError inside the GTK callback, after the dialog has closed.
  3. Save As copies the project and leaves you in the old one (Project.save_as, also called copy).
  4. Delete is permanent and removes the private disks with the folder, without saying how much is lost.
  5. At start-up, a project that can't be opened is replaced by a new new_project_N (ProjectManager.restore_last). An error dialog says why, and each failure adds another folder to the workspace.

Implementation

  1. Archives need bsdtar (BsdTgz), from libarchive-tools, which isn't a dependency and often isn't installed: without it, import and export fail. To include images, export links them into a temporary .images folder inside the project and has bsdtar follow the links. It gives no progress, so the windows can only pulse.
  2. project.py mixes four things: the workspace (listing, creating, renaming), the open project (the factory, the settings, the runtime directory), archives and the README. Ten modules reach into project.manager.current, virtual machines included, for the paths of their private disks.
  3. The name of the temporary folder comes from a private Twisted helper, filepath._secureEnoughString, behind a version check.

The Projects window (board A)

  • The list shows each project's name, the first line of its README and a line of facts, for example “6 bricks · 612 MB · yesterday”. It sorts by last use. The open project carries an Open badge; a missing image or an unreadable file shows in the facts line, in the warning colour.

  • The actions: Open (Enter), Duplicate…, Export…, and a menu with Rename… (F2), Show in Files and Remove… (Delete). New and Import… sit in the header bar. A project that can't be read keeps only Show in Files and Remove…, with the reason from its ProjectFormatError.

§4Importing a project

The canvas's third row. Both layouts rest on the same model, an import plan (§7): I1 shows it on one page, I2 in three steps. Decided: I1 (P2). Every choice has a valid default, so a single page with the Import button enabled from the start is shorter and hides nothing.

Reading the archive

Exports are large, and a compressed tar can't be listed without decompressing all of it. On the test lab, listing a 250 MB .tar.gz took 2.7 s with tarfile, 3.3 s with bsdtar and 5.9 s with GNU tar, on tmpfs. An export of several gigabytes on a real disk takes minutes. Stopping at the project file took no time when it came first, and 2.1 s when it came after the image. So new archives put the small files first and say what the rest holds:

  1. contents.toml: the archive's format, then each member with its size and kind (project file, README, other file, private disk, image). For an image it also gives the name the project uses and whether it's packed (P10).
  2. project.toml, the README, and the project's other small files.
  3. The private disks, then the images, from the smallest to the largest.

Choosing a file reads the archive only up to the end of this head, a few kilobytes, with tarfile reading the stream whatever the compression. Then it stops. A project file of an older Virtualbricks is converted in memory, with the migration's own code (D9), and its report joins the import's.

Archives without the list, which is every archive written today, are read in two parts. Today's export writes the project's own files first and .images/ last, so the project file comes before the images, though a private disk can come before it. The page opens as soon as the project file is read, with the name, the README and the images the project uses. Then the rest of the archive is scanned, with a progress bar in the images section, and each image row says “Looking in the archive…” until the scan finds the image or ends. The Import button doesn't wait. Pressed during the scan, it stops the scan and starts the import, which reads the whole archive anyway. An image the scan hasn't reached is copied if the archive has it, and otherwise gets the default for images not in the archive. An old archive is read once, not twice.

An image left unset stays out of the library. The disks that use it keep its name, so opening the project reports them, and they get an image in their settings later. Each one is pointed at its image with qemu-img rebase -u, in the image's own format as qemu-img info reports it; disks whose image is unset are left as they are and reported.

Running it

  1. The import runs in the archive process (§7) and extracts into a hidden folder of the workspace, .importing-ospf-lab-2-*, which the project list ignores.
  2. Images go straight to their destinations. A packed image is unpacked into a normal one with qemu-img convert; any other file keeps its holes.
  3. The project file is rewritten with the image paths and this computer's paths, and the private disks are rebased.
  4. The folder is renamed into place. If the name was taken meanwhile, it takes the next free one and the result says so.

Cancelling stops the process, and the hidden folder and the images copied so far are removed; so is a failure. The window shows each step with its progress in bytes, and can be closed; the Messages window says when the import is done. The result lists the warnings of the report, with where they are, as in board “I1 · Importing, and done with warnings”.

§5Names, trash, export, start-up

Names

One check, used by New, Rename, Duplicate and Import. It runs as you type, and its message appears under the field, which the main action waits for. A name is valid if it:

  • isn't empty and has no /;
  • doesn't start with a dot: hidden folders are for imports in progress;
  • is at most 40 bytes in UTF-8, and leaves room for the project's longest brick name in its socket paths (below, P9);
  • isn't the name of another project.

Where the limit comes from. A file name can have 255 bytes, so the folder doesn't limit anything. The limit comes from the sockets: a Unix socket path can have at most 107 bytes. Today every socket of the open project is under <runtime dir>/<project>/, where the runtime folder is /run/user/1000/virtualbricks, 28 bytes. The longest socket is a plug's inside a switch: a switch's socket is a folder, <brick>.ctl, and each plug adds its own socket there. libvdeplug names these .<pid>-<n>, up to 14 bytes; that's from its source, since VDE isn't installed here. That leaves about 58 bytes for the project's name and the brick's name together. With a 40-byte project name, a switch's name has 18 bytes. Brick names have no limit today, so a long one already fails.

The project's name stays in the socket paths, and the two names share those 58 bytes (P9):

  • a project name has at most 40 bytes;
  • a brick name is checked against what the project's name leaves, when it's created or renamed, with a message that says how many bytes are left;
  • renaming a project also checks its longest brick name, so a rename never makes a socket path too long;
  • a project whose bricks are already too long for its name opens, and its report names those bricks.

New, Rename, Duplicate

  • New asks for a name and an optional description, which becomes the README. As today, a new project starts from your settings, and the dialog says which ones.
  • Rename works on any project, the open one included; the title and state.toml follow. Running bricks keep their sockets until the project is opened again.
  • Duplicate replaces Save As. It copies the folder with its private disks, not the images, and sets the copy's time to now. Open the copy is on by default, which is what Save As did in other applications.

Remove

Remove… asks what to do, and says how much goes with the project: its private disks and other files, never the images of the library (P3).

  • Move to Trash, the default button: the folder goes to the desktop's trash through Gio.File.trash(), and the file manager can restore it. That code is in gui/trash.py: workspace.py imports no graphics library, so that the workspace works in a console or a script, and without a desktop trash it deletes what it is asked to trash.
  • Delete Permanently, in the destructive colour: the folder is removed at once.

Where the workspace has no trash, as on some network or removable drives, only Delete Permanently is offered, and the dialog says why. The open project can't be removed: open another one first.

Export (board “Export”)

  • Three choices with their sizes: the project, always; the private disks, on; the images they use, off.
  • The other files of the folder sit behind an expander, all included, as today.
  • If P11 goes to packing: each qcow2 disk, image or private disk, is compressed on its own by qemu-img, in parallel, and the tar around them isn't gzipped again (§7).
  • The archive is written by the archive process to a temporary file next to the destination and renamed at the end, so a cancelled export leaves nothing half written.
  • Images go in under .images/<name> straight from their paths, with no links inside the project.

Start-up

If the last project can't be opened, the Projects window opens with an info bar that says why, instead of a new new_project_N (board “Start-up”, P5). A workspace with no projects at all, a first run, still gets a new_project, so the main window has something open. Without the GUI the console keeps today's behaviour.

§7The code in virtualbricks.config

The package already reads and writes the project file; it takes over the rest of project.py, in two parts. workspace.py runs in the application: listing, names, creating, renaming, opening, saving. archive.py and importing.py do the work that moves gigabytes, and that runs in a process of its own. Neither part knows GTK.

The archive process

Inspecting an archive, exporting and importing run in a Python process of their own, started with reactor.spawnProcess as python -c "…archive import main…": with -m, runpy would warn that the package already imported the module. A crash, a full disk or a slow decompression there never blocks the windows or the running bricks, and cancelling is a signal.

  • The application side is an ArchiveJob, a ProcessProtocol that turns the lines into progress calls and the end into a Deferred with the report. If the process dies without cleaning up, the job removes the hidden import folder or the temporary archive itself.
  • The process lowers its own CPU priority and runs the tools it needs as children: qemu-img to pack, unpack and rebase disks, and the archive tool: bsdtar, GNU tar or neither (§7).
  • What stays in the application is small and fast: planning an import from the contents an inspection returned, checking names, and opening the project at the end.

Archives and disks with holes

A qcow2 image can have holes, and an archive must neither store them as zeros nor lose them on extraction. I measured the ways to do it on a test lab: a 4 GiB qcow2 image with 600 MiB of data taken from system libraries and 3.5 GiB of holes, plus a 96 MiB private disk. The machine was tmpfs with 16 cores, running Python 3.10, bsdtar 3.7.4, GNU tar 1.35 and QEMU 10.0. Every extracted file was checked against the original.

Archive written byExportArchiveHoles after extraction
bsdtar, today's flags21.5 s244 MiBKept by bsdtar, GNU tar and Python: bsdtar records them
GNU tar -S24.2 s244 MiBKept by all three
tarfile as it is34.4 s247 MiBLost, 4 GiB on disk, except with bsdtar -S; it reads and compresses the 3.5 GiB of zeros
tarfile with sparse members, gzip 621.9 s244 MiBKept by all three
the same, gzip 18.3 s266 MiBKept by all three
the same, no gzip0.9 s695 MiBKept by all three; listing is instant
qemu-img convert -c, zstd, parallel, the image alone0.9 s259 MiBNothing to keep: a compact qcow2 that qemu-img unpacks in 0.3 s, or that QEMU uses as it is
  • What keeps the holes is recording them when the archive is written. Then every extractor restores them, Python's plain extractall included. bsdtar -S matters only for archives that don't record them: it's the only tool that restores those. With GNU tar or tarfile, the archive process restores them itself, skipping runs of zeros as it writes.
  • Python can record them, with the standard library only. A prototype of about 100 lines on top of tarfile finds the data with os.SEEK_DATA and os.SEEK_HOLE, and writes each file with holes as a GNU sparse 1.0 member. That's the PAX form GNU tar uses, which bsdtar, GNU tar and tarfile all read. It was as fast as bsdtar, with an archive of the same size.
  • tarfile has a bug with large sparse members. When a sparse member stores more than 8 GiB, and its size is in a PAX record as bsdtar and GNU tar write it, Python 3.10 and 3.13 read the wrong size and lose the member after it. Writing the size in the member's own header, in base-256 as GNU tar does for other large numbers, avoids it: all three readers got a 12 GiB member and the file after it right. When tarfile is the only tool, the process recognizes such a member, a sparse one with a PAX size, and asks for bsdtar or GNU tar rather than reading it wrong.
  • Compression is what costs time. Level 1 of gzip is 2.6 times faster than level 6 for 9% more. qemu-img compresses disks in parallel, and with zstd it packed the image about 20 times faster than gzip level 6 compressed the lab, for about the same size. A packed qcow2 is still a qcow2: it works as a backing file without unpacking. zstd needs QEMU 5.1 or newer; zlib works with any, and took 6.4 s in parallel.

The archive tool

One order, to write and to read: bsdtar when it’s installed, otherwise GNU tar, otherwise Python’s tarfile (P4, P12). None of them is required. tar counts as GNU tar only when tar --version says so: BusyBox’s doesn’t handle holes. The tools run as children of the archive process, which feeds them the archive through a pipe or takes theirs, so every tool gives the same progress: the share of the archive read or written.

ToolWritingReading
bsdtarbsdtar -c -f - -C <staging> … records the holes by itselfbsdtar -x -S -f - -C <folder> restores the holes, recorded or not
GNU tartar -c --sparse -f - -C <staging> …tar -x -f - -C <folder> restores the recorded holes; for a large file that doesn’t record them, the process reads it with tar -x -O and skips the zeros itself
tarfileThe sparse writer: holes as GNU sparse 1.0 members, sizes over 8 GiB in base-256extractall with the data filter restores the recorded holes; the others by skipping zeros; sparse members with a PAX size are refused

The members come in a fixed order, the small files first and the largest last (§4), and packed disks are written into a staging folder under the names they have in the archive, so no tool needs to rename or follow links.

Where the compression goes (P11). An archive holds a few small text files and a few very large disks, and only the disks are worth compressing. There are two places to do it:

  • Around the whole archive, as today: the tar is written as it is and the whole stream goes through gzip, which runs on one core. Reading any member means decompressing everything before it.
  • Inside each disk, which is what “packed” means here. qcow2 can store each 64 KiB cluster compressed, and QEMU reads such a file directly, decompressing the clusters as it reads them. qemu-img convert -c writes a copy of a disk with every cluster compressed, using several cores. The packed copies go into the tar, and the tar isn't gzipped: that would compress them a second time and gain nothing. The small text files stay as they are.

Nothing is stored both compressed and uncompressed. The archive is about the same size either way: 244 MiB with gzip, 259 MiB packed, on the test lab. Packing was about 20 times faster. A raw image, or anything that isn't qcow2, can't be packed: it goes into the tar uncompressed, with its holes skipped.

Proposed format for new archives, with packing: a PAX tar written in the archive process, not gzipped.

  • It starts with contents.toml, project.toml and the README, and ends with the images, the largest last (§4).
  • The disks, images and qcow2 private disks, are packed with qemu-img convert -c -o compression_type=zstd -m 8 -W. A private disk keeps its backing file (-B).
  • Other files with holes go in as sparse members, and sizes above 8 GiB are written in base-256.

Packed disks at import (P13). A packed disk is a working qcow2, so the import can either keep it as it is or unpack it.

  • Unpacking runs qemu-img convert without -c. That takes seconds: 0.3 s for the 600 MiB test image. The result is the disk as it was before export, holes included, and it takes its full size on disk.
  • Keeping it packed saves that space, 259 MiB instead of 600 MiB for the test image. But every read decompresses the clusters, which costs CPU while the machine runs; I haven't measured how much. A private disk grows again as the machine writes to it, since QEMU writes new clusters uncompressed. An image is only read, because the machines write to their private disks, so it would stay packed.

Recommended: unpack both, so a disk behaves after import as it did before export. Every tar tool can read these archives, and today's import can take them as they are, since a packed disk is a valid qcow2.

  • Extracting goes through tarfile's data filter, in Python since 3.10.12, which refuses absolute paths, .., links that leave the folder and device files. bsdtar and GNU tar extract absolute names under the folder and refuse .. by default.
  • Old project files inside archives are converted with virtualbricks.migrate, imported lazily in the archive process, as project.py does today, to keep config free of import cycles (P8).
  • Rebasing runs qemu-img rebase -u in the archive process, one private disk at a time, in the image's own format.
  • Last used is the time of project.toml. Autosave keeps it current while the project is open, so no new state is needed (P7).
  • The listing skips hidden folders and reads each project.toml, a few kilobytes. It reuses the summary while a project's file keeps its time.

Exports follow the package's rule, names by name: Workspace, OpenProject, ProjectSummary, DiskUsage, ArchiveContents, ArchiveJob, ImageUse, ImportPlan, inspect_archive, export_project, import_project and plan_import. One workspace instance replaces project.manager. It's exported as projects, so callers read projects.current, projects.open(name, factory) and projects.summaries() (P8). None of these names clashes with an existing export.

§9Implementation plan

Each step leaves the application working and can be committed on its own.

  1. The workspace in config. workspace.py takes over from project.py: listing, names, create, rename, duplicate, trash, delete, open, close, save, start-up. The ten callers move to projects, and project.py is removed. The windows look the same, but New and Rename report a bad name instead of failing inside a callback.
  2. The archive process and import. archive.py and importing.py, the process and its ArchiveJob, and the import window on them (I1). The old assistant and _HumbleImport go; the archive tool is chosen as in §7.
  3. The Projects window, the name dialog, Remove and the reorganized File menu. The five old dialogs go.
  4. Export and start-up: the export window on write_archive, and the Projects window when the last project can't be opened.
  5. Later, if wanted: B's switcher once the main window has a header bar, and dropping archives on the window.

What building steps 1 and 2 changed:

  • Step 1 left project.py with the archive code the old windows used. Step 2 removed the import part; the export part goes with step 4.
  • Brick names are checked against the socket paths in the New Brick and Rename dialogs, not in the factory, so a project with long names still opens and its report names them.
  • Duplicate copies in the application, keeping holes, as Save As did: a large project blocks the window while it copies.
  • GNU tar can't recognize the compression of a pipe, so the process reads the first bytes of the archive and passes --gzip, --bzip2, --xz or --zstd.
  • Without bsdtar, the private disks and the copied images are rewritten with holes for their runs of zeros, when that saves at least 1 MiB.
  • The import doesn't unpack packed disks yet: no archive has them until P11 and P13 are settled.

What building step 3 changed:

  • The File menu has no Remove item: the open project can't be removed, so Remove is only in the Projects window, with the Delete key. The menu is Projects… (Ctrl+O), which opens the Projects window, New Project… (Ctrl+N), Open Recent with the eight projects used last, Save (Ctrl+S), Duplicate…, Rename…, Import…, Export… and Quit.
  • Rename has no F2 shortcut in the main window, where F2 isn't free; it has one in the Projects window.
  • The Projects window exports any readable project, not only the open one, with the images the project uses that are on this computer.
  • Dropping an archive on the window is left for later, as planned.
  • The workspace has no trash of its own. The GUI gives it projects.trasher, the trash of the desktop, when it starts; without one, Workspace.trash() deletes the project for good and says so with its return value.
  • After trying it: the menu item is Projects…, not Open Project…, which didn't say that the window manages the projects; and a click in the list only selects a project, while a double click or Enter opens it.

What building step 4 changed:

  • A new archive starts with contents.toml, the project file and the README, and ends with the private disks and the images, the largest last. Each qcow2 disk is packed by qemu-img convert -c, zstd with zlib as the fallback, in a staging folder next to the archive; a private disk keeps its image as its backing file, so it holds its own data only. contents.toml marks the packed members, with their size before packing, which the import uses to recognize an image your library already has.
  • What isn't qcow2 goes in as it is, with its holes recorded, and so does a disk qemu-img can't read, as when its image is gone; the result says which. Without qemu-img, the archive is gzipped as a whole, by the process, so the progress counts the data written.
  • The import unpacks the images where they land and each private disk after pointing it at its image, with qemu-img convert -B, so the disk holds its own data only. A disk whose image is unset stays packed, and works as it is; so does everything, without qemu-img. contents.toml isn't left in the project.
  • The tools read the members through a staging folder of links, outside the project, under the names they have in the archive; tarfile writes GNU sparse 1.0 members, with sizes above 8 GiB in base-256.
  • At start-up, closing the Projects window without opening a project opens a new new_project_N, as the console does, so the main window is never without a project.
  • project.py is gone.

The tests went with each step: each archive tool, and archives written by one and read by the others; names and free names, listing with hidden and unreadable folders, rename and duplicate of the open project, trash and delete, trash without a trash folder, reading old and new archives, archives read only up to their head, the Import button pressed during a scan, refused archive members, sparse images, import choices and their defaults, cancelling an import, and start-up recovery.
