Virtualbricks Typed AMP Commands

Every command of the console becomes a command of AMP. BrickStart(name=["sw1", "vm1"]) starts two bricks, and BrickSet(name="vm1", key_value=[{"key": "memory", "value": "1024"}]) changes one. The arguments are typed, nothing is quoted, and a brick that isn’t there raises NotFound. This is protocol 2. Protocol 1, Hello and Run, stays on the same socket, unchanged. Each connection agrees on its protocol with Hello. When the two ends don’t speak the same one, the program gets protocol 1 or an error it can catch, never a command read wrong.

§1At a glance

Commands
One AMP command for each of the 59 commands of the console. The name is the command’s words, one capital each: brick card add is BrickCardAdd, status is Status. The arguments have the names the parser gives them (T5).
Types
A number is an Integer. A word that repeats, NAME…, is a ListOf. KEY=VALUE… is a list of key and value records (T6). An option such as --force is a Boolean. The rest is text.
Same checks
A typed value goes through the kinds of the command table, just like a word typed in the console: a name finds its brick, a choice is checked. The command then runs through the same function, with the same messages.
Answer
The lines the console would show, as Run answers them; data of its own is a future improvement (T3).
Errors
NotFound and BadArgument, both kinds of CommandFailed, mean that nothing was done. CommandFailed itself means that the command ran and failed. ProtocolNeeded comes before Hello has agreed on 2. AnswerTooLong and TokenNeeded are as they were (T4).
Versions
One AMP socket speaks both. Hello takes an optional protocols, the list the program speaks, and answers the highest one both ends have; the connection then speaks it. Without the list, as --command and every program of page 16 call it, the answer is 1, as today. The typed commands wait for that agreement and refuse an argument they don’t declare, so a mismatch ends in 1 or in an error, never in a command read wrong (T1).
Definitions
console/ampcommands.py, written from the table by ampgen.py and committed. A test fails when the file and the table differ. As with ampwire.py, a program imports it without loading Virtualbricks, or copies it (T2).
Later changes
A new command or a new optional argument keeps protocol 2. Any other change to a command makes protocol 3. A record of protocol 2 in the tests catches the change that forgets to do so (T7).
Plan
Four steps after this page, a commit each, on a new branch mg/typed-amp from develop (§9).

§2Today

An AMP socket, --socket …:protocol=amp, answers four commands (page 16, page 17). Hello says who answers and gives protocol 1. Run takes a line of the console and answers its lines. Challenge and Authenticate prove the token on tcp and ssl. Every failure is CommandFailed, with the console’s message.

A program therefore writes lines. To start the bricks a user picked, it has to quote each name as the shell would, since the parser splits lines with shlex. A name with a space or a # in it breaks a line that isn’t quoted, or turns into a comment. To tell “no brick named vm9” from “vm9 didn’t start”, the program has to read the message, in the language of the Virtualbricks that runs. That is what M2 B of page 16 left for later: “about fifty commands to keep stable, and each change to the console changes the protocol”. §7 answers that cost.

What holds it together today:

  • The table. Each command is a Command in command.COMMANDS: words, Args with a kind, many and optional, and Flags. The parser reads a line with it, help writes it out, the terminal completes from it, and test_docs checks it against the manual page.
  • The kinds read words. Named finds the brick, event or image, Number reads an integer, Choice checks, and Pair splits KEY=VALUE. Sixteen kinds in all, most of them in the modules of the nouns.
  • --command checks the protocol. client.AMPConnection refuses a Hello that answers anything but 1, with “restart it”. A Virtualbricks that answered 2 to everyone would lock out every --command of 2.1.
  • Page 19, a proposal, has the remote windows send console lines through Run where a command exists, and keeps Hello at 1 (19 R4, §7). With this page they can call the typed commands instead.

§3Versions 1 and 2 together

Protocol 1 is Hello, Run, Challenge and Authenticate, as page 16 and page 17 wrote them. Protocol 2 is all of that plus the 59 typed commands. Every AMP socket speaks both. A Virtualbricks always speaks 1, plus its newest typed protocol. Under T7 A a typed protocol replaces the one before it rather than adding to it, so a program of 3 doesn’t necessarily speak 2, nor a Virtualbricks of 3.

The agreement

  • The answer. protocols lists the protocols the program speaks. Hello answers, in protocol, the highest number that is both in that list and in PROTOCOLS. 1 counts as common even when the program leaves it out. So without the list, or with no number in common, the answer is 1.
  • Binding. The connection speaks what Hello answered, until the next Hello. The typed commands of 2 answer only on a connection that agreed on 2. Before that they fail with ProtocolNeeded, “The typed commands need protocol 2: call Hello with protocols [2] first”, and nothing is done. Run answers on any connection. On tcp and ssl the proof of the token still comes first: Challenge, Authenticate, Hello, then the commands.
  • Strict arguments. Before it runs, a typed command refuses with BadArgument any key it doesn’t declare, such as “ProjectDelete has no argument force”. It also refuses a key it needs that is missing. Left to itself, AMP ignores the first and closes the connection on the second. The types are the agreement’s job, since AMP can’t check them: a text read as a ListOf comes out as an empty list.
  • Nothing of 1 changes. Run, its errors, the order, the token and the 64 KiB limit stay as they are. A program that copied ampwire.py from the manual page never sends protocols and still gets 1. --command goes on sending lines through Run, and its check for 1 stays.
  • The text socket keeps its own protocol 1, in its greeting. This page doesn’t touch it.

Without the strict check, an argument that the Virtualbricks doesn’t declare is dropped and the command runs, and BrickStart(name="sw1") sent to a command that takes a ListOf runs with name=[]. A locateResponder() that refuses such keys with RemoteAmpError(b"BAD_ARGUMENT", …) reaches the program as its own BadArgument, and the connection stays open.

§4The typed commands

Names

The name is the command’s words, each starting with a capital: brick start is BrickStart, event action add is EventActionAdd, help is Help. The 59 names are all different, and none is Hello, Run, Challenge or Authenticate. A test keeps it that way.

Arguments

Each argument has the name the parser passes to the command’s function, command.keyword(): NAME is name, KEY=VALUE is key_value, KIND|NAME is kind_name (T5). Its type follows from the kind, from many and from optional:

In the tableIn AMP
Arg of Numberamp.Integer()
Arg of Pair or KeyValues, manyamp.AmpList([(b"key", amp.Unicode()), (b"value", amp.Unicode())]). The value is text, read as the console reads it, since which keys a brick has, and their kinds, depend on the brick (T6).
Arg of any other kindamp.Unicode(): a name, a choice, a key, a path, a word of OPTIONS

optionaloptional=True; left out, it is None, or an empty list when many
Flag, no valueamp.Boolean(optional=True); left out, false
Flag with a valuethe type of its value, optional
every commandcwd, amp.Unicode(optional=True), as on Run

cwd goes on every command, not only on source and image add, the two that read paths today. A command that learns to read a path later then needs no change to the protocol. It is checked with wire.check_cwd(), as on Run.

Reading

The typed values go through the same reading as the words of a line. The parser splits into two parts. parse() splits the line and finds the command. A new bind() reads the values of each argument with its kind and checks what is missing, what is too much and what is empty. Run goes through both, a typed command only through bind(). So BrickStart(name=["vm9"]) fails with “No brick named vm9”, and BrickStart(name=[]) with “brick start NAME…: NAME is missing”, the console’s own messages.

A kind reads a word. A typed value that isn’t a word, a number or a key/value record, goes through a new take() on the kind. Its default is read(). Number takes the integer as it comes, and Pair takes the record and refuses an empty key, as it does for =VALUE.

Answer

{"lines": […]}, the lines the console shows, as Run answers them. The same AnswerTooLong applies past 65 535 bytes (T3).

Errors

ErrorWhen
NotFound NOT_FOUNDAn argument names a brick, event, image or project that isn’t there: the “No … named …” of Named, Target and ProjectName. Nothing was done.
BadArgument BAD_ARGUMENTAny other refusal before the command runs: an argument the command doesn’t declare, or one it needs that is missing (§3); not a virtual machine, not a card, no such kind or setting, not one of the choices, a missing name, an empty key, a cwd that isn’t absolute. Nothing was done.
ProtocolNeeded PROTOCOL_NEEDEDA typed command on a connection that hasn’t agreed on 2 with Hello (§3). Nothing was done.
CommandFailed COMMAND_FAILEDThe command ran and failed, as on Run. What it did first is dropped (16 M3 A).
AnswerTooLong, TokenNeededAs on Run.

NotFound and BadArgument are subclasses of CommandFailed, so except CommandFailed catches all three. ProtocolNeeded isn’t one, just as TokenNeeded isn’t: it says what the connection has to do first. In each command’s errors they come before CommandFailed, since Twisted sends the code of the first class that matches. The console and the text socket don’t change: there, NotFound is a CommandError like any other.

Checked on Twisted 26.4 and 22.1: a program whose command doesn’t declare NOT_FOUND gets UnknownRemoteError, not CommandFailed. So a new error can’t be added to a command of protocol 2 later without breaking its programs. The three new errors come now or with protocol 3 (T4, T7).

Order and the log

Typed commands and Run share the queue of the connection: one after the other, in the order sent (16 M4 A). On tcp and ssl they wait for the proof of the token, as Run does, and on every socket for the agreement of Hello. The log shows the line the command would be in the console, brick set vm1 memory=1024, with the words quoted where needed, so that a typed command and Run read the same in the Messages window.

Each class has the usage and the help of the table as its docstring, and each choice lists its words in a comment. The commands don’t share a base class, since Twisted would put the errors of the base first and CommandFailed would then match before NotFound.

§6A program

For a Virtualbricks started with --socket unix:~/labs/lab1.amp:protocol=amp:

  • Where Virtualbricks isn’t installed, the program copies ampwire.py and ampcommands.py, or only the classes it uses together with ERRORS.
  • Hello comes first on every connection, since the typed commands wait for it. On tcp and ssl, await authenticate(vb, token) comes before it, as today.
  • With cwd=os.getcwd(), Source(file="lab.vb") reads the program’s own lab.vb.

§7Made from the table

The file and its check

  • console/ampgen.py has source(), the text of ampcommands.py made from COMMANDS, and a main(). python -m virtualbricks.console.ampgen writes the file again.
  • console/ampcommands.py is committed and shipped. Like ampwire.py, it imports only Twisted’s amp and ampwire, so a program loads nothing else of Virtualbricks (T2).
  • test_ampgen fails when the file differs from source(), and its message gives the command that writes it. A change to the table therefore shows up in the diff as a change to the protocol, in the same commit. It is the same idea as test_docs for the manual page.
  • ampgen refuses a kind it can’t map, such as a Pair that isn’t many, which no command has today, so that a new shape is a decision and not an accident.

When the console changes

This is the cost M2 B named. The rule (T7):

  • Additive, protocol 2 stays: a new command; a new optional argument or option; a new word in a choice; a new optional key in the answer. A program of 2 never sends the new things, and ignores keys it doesn’t know. The other way round, a program built on a later 2 that sends something an earlier Virtualbricks doesn’t know gets BadArgument or UnhandledCommand (§3).
  • Anything else makes 3: a command removed or renamed; an argument removed, renamed, of another type, or no longer optional; a new error. PROTOCOLS becomes (1, 3). A program that lists only 2 gets 1, and its typed commands get ProtocolNeeded. It falls back to Run, which never changes.
  • The record. tests/data/amp-protocol-2.txt has one line for each command of protocol 2, its arguments with their types, and its errors. test_ampgen compares the table with it and fails on any change that isn’t additive while PROTOCOLS still has 2. The message says: raise the protocol, and write amp-protocol-3.txt.

§8The code and the tests

What changes

  • console/command.py: ArgKind.take(), with read() as its default, plus Number.take() and Pair.take(); NotFound(CommandError), raised by Named.read().
  • console/bricks.py, projects.py: Target and ProjectName raise NotFound for “No … named …”.
  • console/parser.py: bind(context, command, given), which parse() now calls, and line_of(command, values), the line for the log.
  • console/dispatch.py: run_command(factory, command, given, reactor, cwd) beside run(), which shares the rest of it: the call, the answer as a list, _reason().
  • console/ampwire.py: PROTOCOLS in place of PROTOCOL, Hello’s protocols, the docstring.
  • console/ampgen.py, console/ampcommands.py: new.
  • console/control.py: AMPControl gets one responder for each typed command, registered in a loop with Command.responder (checked on Twisted 26.4 and 22.1). Each one checks the proof, the agreement and cwd, logs the line, queues the call in self.requests, and maps the errors: NotFound to NOT_FOUND, any other error of bind() to BAD_ARGUMENT, the rest as Run does. hello() answers the highest protocol in both lists and keeps it as the connection’s. For a typed command, locateResponder() refuses a key of the box that the command doesn’t declare, and one it needs that is missing, before AMP reads the box.
  • Not changed: client.py and ampbox.py. --command sends lines through Run and asks for no protocol.

  • The file: equal to source(); a class for each command; names unique and apart from ampwire’s; the types of §4; the record of protocol 2, including one additive change and one change that isn’t, made on a copy of the table.

  • The new tests also run in the Twisted 22.1 environment of page 17. The tests that patch amp._log already fail there, an item of the IDEAS.

§10Decisions

QuestionOptionsDecided
T1 How 1 and 2 live together

A On the same socket, agreed per connection. Hello takes the list of protocols the program speaks and answers the highest in both, 1 without the list. The typed commands wait for that agreement, with ProtocolNeeded, and refuse an argument they don’t declare. Nothing of 1 changes, a Virtualbricks of today answers 1, and every mismatch ends in 1 or in an error (§3).

B As A, without the agreement: the typed commands answer on any connection, as in revision 1. One call fewer, but a program that skips Hello, or an end of another build, can get a command read wrong or an argument dropped (§3).

C On separate sockets: protocol=amp speaks 1, a new protocol=amp2 speaks 2, and --socket picks one for each socket. A program has to know which socket to use, and a Virtualbricks that wants both opens two sockets.

D On the same socket, with Hello answering 2 to everyone. --command of 2.1, and any program that checks for 1, then refuse the socket.

 A
T2 Where the definitions come from

A A file written from the table and committed, ampcommands.py, which a test keeps equal to the table. A program imports it without loading Virtualbricks, or copies it, and each change to the protocol shows up in a diff.

B Classes built from the table when the module is imported. Nothing to write again, but a program loads the whole console (the factory, the config, the bricks), can’t copy the definitions, and a change to the table changes the protocol without a trace.

 A
T3 What a command answers

A Its lines, as Run answers them: typed in, text out. The functions of the console don’t change.

B Data of its own: BrickList a list of name, kind, state and summary records, BrickStart the processes, and so on. Each of the 59 functions splits into its data and the lines made from it.

 A; B a future improvement, as new optional keys of the answer, which keep protocol 2
T4 The errors

A Those of Run: CommandFailed, AnswerTooLong, TokenNeeded.

B Those, plus NotFound and BadArgument, subclasses of CommandFailed, which mean that nothing was done (§4). Adding them later needs protocol 3, since a program that doesn’t declare a code gets UnknownRemoteError.

T5 The names of the arguments

A The parser’s keywords: BrickStart(name=[…]), EventActionRemove(name=, n=[…]). One name for each argument, the one the functions already take.

B Plural for a list: names=, key_values=, numbers=. Reads better, but where adding an s doesn’t work (n, options, key_value), Arg needs a second name of its own.

 A
T6 KEY=VALUE…

A A list of records with key and value, both text, the value read as the console reads it.

B A list of "KEY=VALUE" texts, as typed in the console.

C One JSON object in a text, {"memory": 1024}, whose values are turned into the kinds of the brick’s schema.

A Additive changes keep 2. Any other change makes 3, which replaces 2: a program of 2 then gets 1 and uses Run. A record of protocol 2 in the tests catches a change that forgets (§7).

B A command of 2 never changes. A console command that changes gets a new AMP name, BrickSet2, and the old one stays, translated into the new call, for as long as Virtualbricks lives.
