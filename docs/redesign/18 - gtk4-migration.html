Virtualbricks on GTK 4

The windows move from GTK 3 to GTK 4 on every Debian and Ubuntu that Virtualbricks supports, from GTK 4.6 in Ubuntu 22.04 to GTK 4.22 in Ubuntu 26.04 and Debian testing. First, the parts that GTK 3 can already write the GTK 4 way, merged one at a time with the program working. Then the switch itself, on one branch.

  • branch develop at d7d452d
  • revision 2 · 4 October 2026
  • proposal

What this covers: your request of today: migrate the project to GTK 4, prepare a plan, and highlight the compatibility with the Debian and Ubuntu releases. The versions and the behaviour in §3 to §5 were checked today in podman containers of the six targets, with GTK 4, PyGObject and Twisted installed from each distribution. At your request, the page is committed on develop as a plan for later: nothing of it is implemented, and the eight questions, G1 to G8 in §11, stay open until the work starts. The versions will need checking again then.

Since then: on 4 October the reactor of step A1 came ahead of the rest: scripts/virtualbricks.py and migrate/gui.py install gireactor in place of gtk3reactor, so Virtualbricks no longer starts with Twisted’s warning. There is no Gtk.Application yet: on Twisted 22.1 and 22.4, those of Ubuntu 22.04 and Debian 12, gireactor runs a GLib main loop where gtk3reactor ran Gtk.main(), as every Twisted from 23.8 does. Tried on both in containers, on Broadway: the program starts, answers on its socket and quits. A1 keeps the rest: the Gtk.Application of G7, registered with the reactor, the application window, the icon and has_display.

§1At a glance

Why now
GTK 3 only gets fixes now. Twisted deprecated gtk3reactor in 23.8, so Virtualbricks already starts with a deprecation warning on Ubuntu 24.04 and Debian 13 and newer. GTK 3 is still packaged on all six targets (3.24.33 to 3.24.52), so nothing forces a date.
Targets
Every target has GTK 4: 4.6.9 in Ubuntu 22.04, 4.8.3 in Debian 12, 4.14.5 in Ubuntu 24.04, 4.18.6 in Debian 13, 4.22.4 in Ubuntu 26.04 and Debian testing. All 28 widgets and features that Virtualbricks needs build and show on all six (§5).
Lowest
GTK 4.6 with PyGObject 3.42, so Ubuntu 22.04 keeps working (G1). Only three things need an API newer than 4.6: the file chooser, opening a link and loading CSS. gui/compat.py asks GTK what it has and picks (§7).
The 4.10 line
GTK 4.10 deprecated the combo boxes, the tree views, Gtk.Dialog, the file choosers, the info bar and the style contexts. Their replacements in GTK 4.0 are used, except for the file chooser, whose replacement came in 4.10. Nothing deprecated in GTK 4.22 is used.
PyGObject
PyGObject 3.42, on 22.04 and Debian 12, can’t hold GTK’s expressions or render nodes. So there are no drop-downs with search, and no pictures of widgets in the tests. 3.48 and newer have both, and they warn when a deprecated function is called.
Reactor
gireactor, with a Gtk.Application registered with the reactor (G7). This works with GTK 4 on Twisted 22.1 to 26.4.
Dialogs
A Dialog of our own on Gtk.Window, whose answer is a Deferred (G3). GTK 4 has no run(), so no window waits in a loop of its own.
Gone
The tray icon: GTK 4 has none (G4). Window positions, window types and the undecorated “action in progress” window go too.
Tests
GTK 4 has no OffscreenWindow, and Python can’t make GTK 4 events. So the tests call the handlers with values and size widgets by hand. They run under Xvfb on 22.04, where the Broadway of GTK 4.6 crashes, and under Xvfb or Broadway elsewhere.
Plan
Phase A: four steps on GTK 3, each merged into develop with the program working. Phase B: the switch, seven steps on a branch mg/gtk4, merged once the GUI tests pass in a container of each target. Phase C comes later (§10, §12).

GTK 3 and GTK 4 can’t be loaded in the same process. So there’s no period in which some windows are GTK 3 and others GTK 4: the program switches all at once. That’s why the plan first moves, still on GTK 3, what GTK 3 can already write the GTK 4 way (§10).

The package is gir1.2-gtk-4.0 on all six, beside python3-gi and python3-gi-cairo. The tests’ Broadway is gtk4-broadwayd, in libgtk-4-bin.

The line that matters falls between Debian 12 and Ubuntu 24.04. GTK jumps from 4.8 to 4.14, and PyGObject from 3.42 to 3.48. The two older targets have everything that Virtualbricks needs from GTK 4.0 to 4.6. They lack the replacements that came with 4.10 and 4.12, and their PyGObject can’t pass GTK’s expressions and render nodes. The support dates are the ones Canonical and Debian publish; they weren’t checked today.

§6How the code changes

Four rules for all of it:

  • gi.require_version("Gtk", "4.0") once, in virtualbricks/gui/__init__.py, in place of the 44 modules asking each for itself. migrate/gui.py loads it from there.
  • Nothing deprecated in GTK 4.22; nothing newer than 4.6 outside compat.py (§4).
  • No Gtk.Expression, no render nodes, no get_current_event(), for PyGObject 3.42.
  • Handlers take values, not events: a click handler gets the number of presses, x and y; a key handler gets keyval and the modifiers. The tests call them the same way.

The start

scripts/virtualbricks.py and migrate/gui.py install gireactor in place of gtk3reactor. They make a Gtk.Application with NON_UNIQUE and register it with reactor.registerGApplication() before task.react() runs the reactor (G7). The lock of page 13 stays the only rule about a second Virtualbricks. reactor.stop() ends the application, as it ends the program today.

Containers and styles

  • pack_start(child, expand, fill, padding) becomes append(child), with hexpand or vexpand, halign or valign, and margins on the child. add() becomes set_child(). visible=True, show_all() and border_width go.
  • get_children() becomes a children(widget) helper in gui/dialogs/base.py, or a list the class keeps. GTK 4 counts inner widgets as children too (a button’s label is its child), so code and tests reach widgets by their attributes, not by their position in the tree.
  • get_style_context().add_class() becomes add_css_class(). The five CSS providers, now each added to its own widgets, become one provider for the display, loaded at start by compat.load_css() and aimed at the widgets through classes.

Menus and shortcuts

  • The menu bar becomes a Gio.Menu shown by a Gtk.PopoverMenuBar (G5), and each item an action: app.quit, app.settings, win.save, … The six shortcuts, Ctrl+N, Ctrl+O, Ctrl+S, Ctrl+Q, Ctrl+P and F1, go through set_accels_for_action(), which also shows them in the menus. Open Recent is a section of the model, rebuilt when the list of recent projects changes.
  • The menus of the rows are already Gio.Menu models with actions (brickmenu.py, eventmenu.py, imagemenu.py, rowtab.py, the popup() of tab.py). Gtk.Menu.new_from_model() becomes Gtk.PopoverMenu.new_from_model(), parented to the list and pointing at the row or at the click. The Add menu of the Images tab, built by hand today, becomes a model too.
  • A menu opened by the keyboard (Menu, Shift+F10), today the popup-menu signal and keys=True, gets a ShortcutController on each list.

Events

button-press-event becomes GestureClick (button 3 for the menus, two presses to open a row), key-press-event EventControllerKey, motion-notify-event EventControllerMotion, scroll-event EventControllerScroll, and delete-event close-request. size-allocate has no signal in GTK 4. markdownview.py, the buttons of readme.py, and the bar and the area of the topology get a small subclass that overrides do_size_allocate(), or the resize signal of the drawing area.

Dialogs and files

  • The seven Gtk.Dialogs (confirm, settings, rename, project name, add image, the image dialogs, new event) become a Dialog of our own in gui/dialogs/base.py (G3). It is a Gtk.Window, modal and transient for its parent, with its buttons at the bottom, a default button, and Escape to cancel. Its show() returns a Deferred that fires with the answer.
  • The five nested loops go: the chooser and the question “replace the archive?” of exportproject.py, the chooser of importdialog.py, and the two of migrate/gui.py. Each waits on a Deferred, in an inlineCallbacks where the code reads better that way.
  • The four file chooser buttons (addimage.py, imagedialogs.py, importdialog.py, settings.py) become a button that shows the file’s name and opens compat.choose_file(). The eight choosers become compat.choose_file(), choose_folder() and save_file().
  • The three Gtk.MessageDialogs (the errors of gui.py, the question “replace the archive?” of exportproject.py, and the question of projects.py) become Dialogs too. Gtk.AboutDialog stays: it isn’t deprecated. Its logo becomes a texture.

Widgets that change

  • The 13 combo boxes become Gtk.DropDowns on a Gtk.StringList. The ids they carry today, as active_id, become a list of values beside the labels, and the selected index maps between them. There is no search in them: it needs an expression, which PyGObject 3.42 can’t pass.
  • The 13 radio buttons become Gtk.CheckButtons in a group; GTK 4 draws them as radio buttons.
  • The three info bars (the Projects window, the machine’s panel, the running bar of rowtab.py) become a small bar of our own: a revealer with a box, a label and its buttons, and a CSS class.
  • The one tree view, the list of migrate/gui.py, becomes a Gtk.ColumnView on a Gio.ListStore.
  • The lists of the tabs stay Gtk.ListBoxes with the rows of rowtab.py (G8).
  • Icons: GdkPixbuf in widgets becomes Gdk.Texture.new_from_filename(); Gtk.Image.new_from_icon_name(name, size) becomes new_from_icon_name(name) with set_pixel_size(); a button with an image and a label gets a box with both as its child.
  • The popovers of picker.py, imagepicker.py, newbrick.py, readme.py and rowtab.py take their widget with set_parent() in place of GTK 3’s relative_to, and let it go with unparent() when the widget goes.

Drag and drop

In bricklist.py, each row gets a Gtk.DragSource whose content is the row’s brick (Gdk.ContentProvider.new_for_value()). Its icon is a WidgetPaintable of the label that says what the drop would do. Each row also gets a Gtk.DropTarget for the brick’s type with the link action. Its motion handler answers whether this brick can plug into that one, and drop plugs it. GTK sets the :drop(active) state on the row, which the CSS highlights, in place of drag_highlight().

The topology

topologyview.py draws with set_draw_func(); its cairo code stays as it is. Its five event signals become controllers, query-tooltip stays, and the cursor goes through set_cursor_from_name(). picture.py paints the icons from cairo images (cairo.ImageSurface.create_from_png(), scaled in cairo) in place of Gdk.cairo_set_source_pixbuf(), deprecated in 4.20. The picture then loads neither Gdk nor GdkPixbuf: only cairo and Pango.

Text views

markdownview.py and the log window (logging.py) keep their text views, tags and window_to_buffer_coords(), which takes Gtk.TextWindowType.WIDGET. The pointer over a link comes from EventControllerMotion, and the hand cursor from set_cursor_from_name().

Windows and the tray

  • Window positions, type hints, skip_taskbar_hint and urgency_hint go: GTK 4 has none of them. The window manager places the windows, a dialog over its parent. get_toplevel() becomes get_root().
  • The “action in progress” window, undecorated and of the notification type, becomes a modal Dialog with a spinner and no buttons.
  • The tray icon and its menu go, since GTK 4 has no Gtk.StatusIcon (G4). The tray_icon setting stays readable in the files, has no effect, and leaves the Settings window. virtualbricks-config(5) and config-files.html say so.
  • The window icon becomes the name virtualbricks, looked up in the icon theme (§9).

§7compat.py

The only module that asks GTK what it has. It asks with hasattr, not by version number, as programs.py asks QEMU for its options.

A cancelled chooser fires with None. The tests patch each flag, so both branches run on every machine. Each branch also runs for real in the containers of the targets that have it (step B7). Raising the lowest GTK to 4.12 later removes every old branch (§12).

The Dialog of gui/dialogs/base.py isn’t in compat.py: it is the same on every GTK 4.

§8The tests

  • The display. Today tests/gui/__init__.py asks Gtk.init_check(). On GTK 4 it returns True even without a display, on all six targets, and the first widget then crashes the whole run. has_display becomes Gdk.Display.get_default() is not None.
  • No OffscreenWindow. The nine test modules that use it size the widget by hand with allocate(width, height, -1, None), which works without a window on all six. Where a test needs a real window, it presents a Gtk.Window and turns the main loop.
  • No events. GTK 4 events can’t be made from Python, so the 41 events that ten test modules build go away. The tests call the handlers with the values a controller passes. Phase A moves the handlers to controllers while still on GTK 3, so most of these tests change there, with GTK 3 still running them.
  • The tree. The 101 get_children() of 30 test modules become children(), or better the attribute of the widget, since GTK 4 lists inner widgets as children.
  • The main loop. Gtk.main_iteration(), in six test modules, becomes GLib.MainContext.default().iteration(False).
  • Where they run. xvfb-run -a python -m twisted.trial virtualbricks on every target. Broadway works too from Debian 12 on, and on this machine, but not on Ubuntu 22.04. Step B7 adds a check that runs the GUI tests in a container of each target, as tests/data/programs/start.py starts the sample project in each. It is the check before a release.
  • Deprecations. The run on the newest target is clean of GTK’s DeprecationWarnings. PyGObject 3.48 and newer report each deprecated call, so the rule of §4 is checked, not only written down.
  • Pictures. Rendering a widget to a PNG needs PyGObject 3.48, so it stays out of the suite and is used only to look at a window, as on Broadway today.

New code gets new tests: compat.py, the Dialog, the info bar of our own, children(). Moved code keeps its tests, changed only where GTK 4 makes them change.

§9Packages, icon, desktop

  • Packages. gir1.2-gtk-4.0 in place of gir1.2-gtk-3.0, with the same name on all six targets. python3-gi, python3-gi-cairo and python3-twisted stay as today. For the tests, xvfb, or libgtk-4-bin for Broadway. pyproject.toml keeps PyGObject>=3.42. PyGObject-stubs, the types for the editor, is installed with its GTK 4 configuration.
  • The icon. A GTK 4 window takes only an icon name. virtualbricks.png is 130×140 today, so a square 128×128 copy goes in share/icons/hicolor/128x128/apps/virtualbricks.png, installed beside the .xpm of share/pixmaps. Run from the sources, the program adds its data folder to the icon theme, with the icon in the same hicolor layout: GTK 4.6 and 4.8 find only that layout (§5).
  • The desktop file. On Wayland, a window is matched to its desktop file by the application id. With G7 A, share/virtualbricks.desktop becomes share/org.virtualsquare.Virtualbricks.desktop and keeps Icon=virtualbricks. With G7 B, nothing changes: GTK uses the program’s name, virtualbricks.
  • The README. “GTK 3” becomes “GTK 4, 4.6 or newer”; the apt lines and the tests section follow. The manual pages name no version of GTK. virtualbricks-config(5) describes tray_icon as “Show an icon in the system tray”, and says instead that it has no effect (step A3).

§10Implementation plan

§11Decisions

QuestionOptionsI’d choose
G1 The lowest GTK 4

A 4.6, all six targets. compat.py covers the file chooser, links and CSS, and the code follows the limits of PyGObject 3.42 (§4). Ubuntu 22.04 runs its tests under Xvfb.

B 4.14, Ubuntu 24.04 and newer. No compat.py, and PyGObject 3.48 lifts the limits. Ubuntu 22.04 and Debian 12 stay on a GTK 3 release, a branch that gets fixes until April 2027 and June 2028.

C Stay on GTK 3 until the two older targets end, and migrate then as B.

 A
G2 How to get there

A Phase A on GTK 3 first, four steps merged into develop one at a time, then the switch on mg/gtk4 (§10). The switch is smaller, and most test changes run on GTK 3 first.

B Everything on one branch from the start. Fewer steps, but nothing of it runs until the end.

 A
G3 Dialogs

A A Dialog of our own on Gtk.Window, whose answer is a Deferred. It is the same on every GTK 4, and uses nothing deprecated.

B Keep Gtk.Dialog and Gtk.MessageDialog: they are deprecated in 4.10, their methods warn on PyGObject 3.48 and newer, and Gtk.ResponseType is deprecated in 4.20.

C The dialogs of libadwaita: 1.5 or newer, so not on Ubuntu 22.04 or Debian 12.

 A
G4 The tray icon

A Drop it. The tray_icon setting stays readable and has no effect. On GNOME the icon hasn’t shown for years even with GTK 3, since GNOME no longer has a tray.

B A StatusNotifierItem of our own, over D-Bus with Gio, with no new dependency. It shows on KDE, XFCE and the GNOME of Ubuntu, which has the extension, but not on plain GNOME.

C libayatana-appindicator: it is built on GTK 3 and can’t load beside GTK 4.

 A, with B under IDEAS
G5 The menu bar

A Keep a menu bar, as today, from a Gio.Menu.

B A header bar with a main menu, as GNOME programs have. It fits the IDEAS item of switching projects from the title (page 04 §3, direction B), but it changes how the program looks in the same step.

 A, with B under IDEAS
G6 libadwaita

A No. Plain GTK 4 looks the same everywhere and needs no new dependency. The 1.1 of Ubuntu 22.04 lacks most of what would help.

B Yes, as a dependency, 1.1 or newer.

 A
G7 The application

A A Gtk.Application, org.virtualsquare.Virtualbricks, with NON_UNIQUE so that the lock of page 13 stays the only rule, registered with the reactor. It gives the actions, the shortcuts shown in the menus and the menu bar. The desktop file takes the id as its name, so that Wayland matches the windows to it. The id is yours to choose; io.github.virtualsquare.Virtualbricks would do as well.

B Plain windows, without an application. Shortcuts through a ShortcutController on the main window, the shortcut labels in the menus written by hand, and actions added to each window. The desktop file keeps its name.

 A
G8 The lists of the tabs

A Keep Gtk.ListBox: it isn’t deprecated, and the rows of rowtab.py move over nearly as they are.

B Gtk.ListView or ColumnView, with factories that reuse rows: better for hundreds of bricks, but the rows and their tests are rewritten, and PyGObject 3.42 limits them to CustomSorter and CustomFilter.
