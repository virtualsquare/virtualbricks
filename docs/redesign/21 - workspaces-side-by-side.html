Virtualbricks Workspaces Side by Side

A fourth single-instance mode, --lock workspace, which --workspace implies, lets one Virtualbricks run in each workspace at the same time, whether yours or another user’s. Each workspace gets a lock of its own, a runtime folder of its own for the sockets of its bricks, and a control socket of its own. Two projects named lab1 in two workspaces no longer meet, and --command reaches either one.

§1At a glance

Mode
virtualbricks --lock workspace runs one Virtualbricks for each workspace. A second one in the same workspace is refused (W1).
Implied
--workspace without --lock runs in the workspace mode, so virtualbricks --workspace ~/labs/a and virtualbricks --workspace ~/labs/b start side by side. An explicit --lock wins. Without either, the default stays system, as page 13 decided (W7).
Levels
The modes nest: the machine, then the user, then the workspace. Each mode holds the lock of its own level alone and shares the locks of the levels above it. The workspace mode shares the system lock and your user lock, and holds the lock of its workspace alone.
The lock
The lock is .virtualbricks.lock in the workspace folder (W3). Every mode except none holds it, so two Virtualbricks never share a workspace, even when two users share its folder (W2).
Runtime
Each workspace has a folder in the runtime folder, named by a key of eight characters made from the workspace’s path, for example $XDG_RUNTIME_DIR/virtualbricks/fnknanf4/lab1/. The link .workspace in that folder points to the workspace (W4).
Socket
--socket alone listens on .control in the workspace’s runtime folder. --command talks to the only Virtualbricks of yours that listens there, or to the one in the workspace of --workspace FOLDER. When several listen, it names them and sends nothing (W5).
Settings
All your Virtualbricks share settings.toml and state.toml, as today, and the last one to write them wins (W6).
Windows
When the workspace isn’t the one of the settings, the title names it: Virtualbricks (project: lab1, workspace: ~/labs/b).
Plan
Four steps, a commit each, on a new branch mg/side-by-side from mg/typed-amp (§12).

§2Today

--workspace picks the folder of the projects for one run. The single-instance mode of page 13 doesn’t know about workspaces. system lets one Virtualbricks run on the machine, and user one for each user. Only --lock none lets a second one of yours start, and then nothing keeps the two apart:

  • The runtime folder of a project is named after the project alone: $XDG_RUNTIME_DIR/virtualbricks/lab1/. Two projects named lab1 in two workspaces share it. I tried both programs today. A second vde_switch on the same folder stops with Could not bind to socket …: Address already in use. A second QEMU takes over the first one’s monitor socket without a word, and removes it when it ends, so the first machine no longer has a monitor.
  • One control socket for each user. The first Virtualbricks started with --socket alone gets .control. The others run without a socket (15 Q4 A), so --command reaches only the first.
  • The settings. Each Virtualbricks keeps the settings in memory and writes all of them when it ends. The one that ends last undoes a setting that was changed in the other.
  • The state. Each writes the whole of state.toml when it opens a project. The entry of the other’s workspace goes back to what it was when this one started.
  • The workspace. Nothing stops two of them from opening the same workspace, or the same project.

§3The workspace mode

ModeAt mostHoldsDoesn’t start while

noneno limitnothingnever refused

This adds one level to the readers–writer lock of 13 §3. The machine holds users, and a user holds workspaces. Each mode is the writer of its own level and a reader of the levels above it. The workspace mode shares the machine with other users, shares your user with your other workspaces, and has its workspace to itself.

So the workspace mode complies with the other two modes, as the user mode complies with the system mode. A Virtualbricks of yours in the user mode means that you run only one, so the workspace mode doesn’t start beside it, and the user mode doesn’t start beside one in the workspace mode. Other users are free: their modes never meet yours unless you share a workspace folder.

The default stays system, as page 13 decided at your request, except with --workspace. A Virtualbricks started with --workspace and without --lock runs in the workspace mode (W7). An explicit --lock wins, --lock none included. The client options, --command and --connect --run, take no lock, and there --workspace only picks the Virtualbricks to talk to (§7).

A Virtualbricks started with neither option runs in the workspace of the settings, in the system mode, and so has the machine to itself. To run it beside others, start it with --lock workspace. The refusal says so (§9).

“The same workspace” means the same folder, whatever path you give for it. The lock is a file in the folder, so a link or another path to the folder reaches the same file.

The none mode still takes nothing and checks nothing (13 L2), so it starts even in a workspace that another Virtualbricks has, as it does today. The runtime folders and the sockets of §6 and §7 apply to every mode, none included. Two Virtualbricks with --lock none in two workspaces are now kept apart; in one workspace they still aren’t.

§5The workspace lock

Where

.virtualbricks.lock in the workspace folder (W3). A project’s name never starts with a dot, so no project can be named like it. The name is longer than the runtime folder’s .lock because --workspace can name any folder, even one that other programs use. The lock is in the folder itself, so every Virtualbricks that opens the folder sees it: yours through another path, and another user’s in a folder you share.

Opening it

  • It is opened the same way as the system lock (13 §5): without following a link, made only when it is missing, and readable by everyone.
  • It is opened for reading and writing when possible, and read-only otherwise. On NFS, Linux turns a flock into a lock of the whole file that the server keeps, and an exclusive lock then needs a file opened for writing (flock(2), NOTES). On a local disk, read-only is enough. I haven’t tried NFS here.
  • When the file isn’t there yet and you can’t write to the folder, the start is refused with the message of 13 §6: Cannot take the lock ~/labs/a/.virtualbricks.lock: Permission denied. With --lock none, Virtualbricks runs without locks. Such a workspace couldn’t save its projects anyway.

When

The locks of the mode come first, as today. The workspace lock comes right after them, before the migration at startup, which may change the projects of the workspace. The workspace is the one of --workspace, and otherwise the one of the settings, read the way the migration reads it: from settings.toml, or on the first start from the settings of 2.1. A missing workspace folder is made first, as today.

On the first start, when settings.toml isn’t there yet, the migration at startup also converts your settings from 2.1, once. These are files of your user, not of the workspace. In the user mode this already happens under the user lock. The workspace mode only shares that lock. So when a Virtualbricks in the workspace mode finds settings from 2.1 to convert, it takes the user lock alone, converts them, and then shares the lock. Another one of yours that starts during those seconds is refused, just as one in the user mode would refuse it.

The migration command and window (13 §7) hold the user lock alone, as today. They now also hold the lock of the workspace they migrate.

The kernel releases the lock when Virtualbricks ends, as it does the others (13 §5). The file stays in the workspace.

§6The runtime folders

  • The key is the first eight characters of the SHA-256 of the workspace’s real path, in lowercase base32: letters and the digits 2 to 7 (W4). The real path resolves links, so the same folder has the same key whatever path you give. The key doesn’t depend on the settings, so every Virtualbricks, and --command, computes the same one. It has 40 bits, so in practice two of your workspaces never get the same key.
  • .workspace is a link to the workspace, made again at each start, so that ls -l and --command (§7) can tell which folder is which. Its name starts with a dot, like .lock and .control, so no project can be named like it.
  • The bricks keep their sockets in key/project/: the folders of the switches and the monitors and serial ports of the machines, all one level down from today. Their paths come from the factory’s runtime_dir, set when the project opens. No project file names them, so no project changes.
  • The room for names. A Unix socket path has at most 107 bytes. The key and its slash take 9 bytes away from the names of the bricks. In /run/user/1000, the bricks of lab1 had 54 bytes and now have 45, and those of new_project go from 47 to 38. The existing checks still apply: New Brick and Rename refuse a name that doesn’t fit, and a project with a brick whose name no longer fits opens with the warning to rename it before starting it. Names that long are rare. W4 B, not taken, would have kept the old room for the default workspace.
  • The old folders. The runtime folders that projects got before this change, at the top, stay where they are. Nothing reads them, and the system empties $XDG_RUNTIME_DIR when you log out.
  • Without XDG_RUNTIME_DIR, the layout is the same under /tmp/virtualbricks-uid/.

§7The control socket

--socket alone listens on .control in the runtime folder of its workspace, with .control.lock beside it (W5). Each workspace has its own, so two Virtualbricks of yours in the workspace mode can both listen. The descriptions, unix:PATH, tcp:PORT and ssl:…, don’t change: a path or a port still belongs to whichever Virtualbricks takes it first.

Which one --command talks to

Given--command and --connect --run talk to
--connect DESCRIPTIONthe socket of the description, as today
--workspace FOLDER newthe Virtualbricks of that workspace, at its .control. Until now, --command refused --workspace.
neitherthe only Virtualbricks of yours that listens on the .control of its workspace. When several do, it names them and sends nothing (exit 2).

--connect with a description and --workspace are refused together, since each names a Virtualbricks.

To find who listens, --command looks at .control.lock in each folder of the runtime folder, without connecting. A lock that is held means a Virtualbricks listens there. The .workspace link names the workspace, and /proc/locks names the process, as in the messages of page 13.

With a single Virtualbricks, which is the common case, the commands you type don’t change: --socket, then --command status, as today. What changes is the path. The $XDG_RUNTIME_DIR/virtualbricks/.control of pages 15 and 16 moves one folder down, under the key of the workspace. A program that connects by itself, such as socat or a program that speaks Twisted’s AMP, can read the path from the log line Listening on …, or get a fixed path with --socket unix:PATH. W5 C, not taken, would have kept the old path for the workspace of the settings.

When nobody listens in the workspace of --workspace, --command says so, and exits with 2. If a Virtualbricks runs there without a socket, the holders of the workspace lock tell --command which process it is, and the message names it: Your Virtualbricks in ~/labs/a, process 4300, doesn’t listen: it was started without --socket, or its log says why.

§8Settings and state

settings.toml and state.toml belong to your user, and every Virtualbricks of yours reads them at start. They stay as they are today (W6), so when two Virtualbricks run, the last one to write a file wins:

  • settings.toml: the Settings dialog, settings set in the console and the end of each Virtualbricks write every setting that Virtualbricks holds. A setting changed in one Virtualbricks is undone when the other one ends. Restart the other one before you change a setting, or change it again afterwards.
  • state.toml: opening a project writes the whole file, with this Virtualbricks’ view of the other workspaces. The other workspace’s entry can go back to what it was when this Virtualbricks started, so the next start there may open the project that was open before the last one.
  • Both files are still replaced whole and atomically, as page 02 made them, so neither is ever left half written.
  • The settings of a project live in the project, so two workspaces never share them.

§10What stays shared

  • The none mode still takes and checks nothing (13 L2), so two Virtualbricks can still start in one workspace, as today.
  • What belongs to the machine: tap interfaces, the ports of tunnels and of VNC displays, and the USB devices of the host. The Virtualbricks that starts its brick second gets the program’s error, as it would beside any other program.
  • A disk image outside the workspaces that projects in both use: QEMU locks an image it writes, so the second machine stops with Failed to get "write" lock. I tried it today. The images of a workspace, in its vimages/, belong to that workspace alone.
  • The token of the tcp and ssl sockets, which is one for all your Virtualbricks (page 17).
  • The settings and the state, where the last to write wins (§8).
