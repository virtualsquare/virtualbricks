What each way of running Virtualbricks does from virtualbricks to its main loop: with the windows, with --no-gui, as the windows of another Virtualbricks, and with --command. In order, side by side, with the reactor each one installs and what has to come before what.

§1At a glance

Four modes
CLI, --no-gui: app.Application. GUI, the default: gui.app.GuiApplication, a subclass. Remote, --connect alone: gui.app.RemoteApplication, a class of its own. Command, --command or --connect --run: the function console.client.main.
One fork
cli.main() (cli.py:569) parses the options, then picks the mode with three ifs. Each mode imports its own module only after that, and the order of those imports is what decides the reactor (§2).
Reactor
GUI and remote install GIReactor explicitly, in install_gtk_reactor(). The CLI gets EPollReactor as a side effect of from virtualbricks import app, which reaches bricks/__init__.py:41. Command mode has none, and a test checks it. The migration window installs its own, elsewhere (§5).
Two timings
task.react calls run(reactor) before reactor.run(). So the whole start, windows included, runs before the loop, except in the GUI when a migration is pending: then the loop starts under the migration window, and the rest runs when it closes (§4).
Settings
Read three times before the app holds them: by startup_workspace() for the lock, by startup_migration(), then by load_settings() (§6).
Confusing
Ten things, in §7. The main ones: the reactor depends on import order, the remote app repeats the start of the others by hand, and logging and the locale start at different points in each mode.

§2Where the modes split

cli.main() after parsing. Red boxes install a reactor. Every import of the application classes is inside a factory function (make_application, make_remote_application, make_plain_application, cli.py:537–556), so cli.py itself loads seven modules of the package and no reactor.

Parsing has side effects too

Every mode parses the same Options, and some options act while they are read, before the mode is known:

  • --logfile opens the log file at once (_file_logger, cli.py:52), even when check_client() refuses it next because --command takes no --logfile.
  • --listen ssl:… imports console.tls (pyOpenSSL) and reads the key and the certificates; a socket with a token reads the token file (cli.py:286–342).
  • --logger imports the named module (reflect.namedAny, cli.py:502); --version prints and exits.
  • --workspace sets --lock workspace unless --lock is given; --connect alone forces noterm (cli.py:483–499).

So the GUI has two orders in time. Without a migration, MainWindow is built and shown, the project opened and the console started, all before the loop; the window appears when the loop starts. With a migration, the loop runs the migration window, and _start runs later in a GLib callback, when window.closed fires. The remote windows are always built inside the loop, on the connection.

§5The reactor

Twisted has one global reactor. The first from twisted.internet import reactor installs the default one, EPollReactor on Linux, unless another was installed before. gireactor.install() after that raises ReactorAlreadyInstalledError; tried today: import virtualbricks.bricks, then gireactor.install(), fails with it.

The hidden one

ksm.py:119 is reached from load_settings(): with kernel_samepage_merging on and KSM off, set_ksm() spawns sudo tee through the reactor (config/settings.py:332). Settings read before install_gtk_reactor(), for instance to choose the mode from a setting, would install EPoll on such a computer and only there.

GTK’s version

gi.require_version("Gtk", "3.0") is in cli.py:562 and again at the top of 44 modules of gui/ and migrate/gui.py:39. gui/app.py:27 imports Gtk without it and relies on cli.py having asked first.

Before the loop

task.react(main) calls main(reactor), then reactor.run(). Whatever run() does up to the first Deferred that hasn’t fired happens before the loop: the locks, the settings, the KSM process, the windows, the project, the sockets, the console. It works because Twisted queues what is scheduled before run(), but a step that waits on the loop (a Deferred from a process or a socket) silently moves everything after it into the loop, as the migration window does.

§7What makes it confusing

  1. The reactor is chosen by import order. Three places install one (cli.py:566, migrate/gui.py:523, and the import of bricks for the CLI), in two ways. GUI and remote work because cli.py imports nothing of the application at the top and each factory imports its module after install_gtk_reactor(). No comment states that order. The test of command mode catches a top-level import in cli.py; nothing checks that the factories import after the reactor is installed.
  2. Remote is not an Application. RemoteApplication repeats install_locale, install_settings, the logger and its triggers by hand (gui/app.py:256–278). It lives in gui/app.py beside GuiApplication, so importing it imports app, BrickFactory, bricks and LocalEngine, none of which it uses. remote/client.py:54 imports brickfactory for normalize_name alone.
  3. The settings are read three times. startup_workspace() and startup_migration() each call _startup_settings(), then load_settings() reads the file again; settings_to_convert() runs twice. The workspace that is locked and projects.path come from two different readers of the same setting.
  4. The locale comes at three different points. After the locks in CLI and GUI, first in remote, before client.main in command mode. Everything imported before it, all of gui/ in the GUI, is translated by the builtins that i18n.py:93 installs on import, without setlocale.
  5. Logging starts late. In _start, after the locks, the migration and the settings. Their messages are buffered and replayed before the “starts” line, so the log reads out of order. Command mode never starts the log, and neither does the migration window.
  6. Two timings in the GUI (§4): _start runs before the loop, or inside it when a migration is pending. A step that becomes asynchronous changes which.
  7. _start is one long method with hooks. migrate, _run, open_last_project, get_namespace are overridden by GuiApplication, which then adds steps after super()._start(). The pdb set-up sits in the middle. The quit order lives in addSystemEventTrigger calls spread over run, _start and the console.
  8. Two bugs, in BUGS.md. The remote windows’ load_settings() turns KSM on in this computer when the local setting says so (config/settings.py:332), though the bricks run on the other one: checked by calling install_settings() with set_ksm replaced. And each process writes all of settings.toml from its own copy, at each change and at quit, so the remote windows and the Virtualbricks they show on the same computer, or two side by side with --lock workspace, undo each other’s changes: checked with two processes on one file.
  9. Parsing acts. --logfile opens its file while it is parsed, even when check_client() refuses it next; --listen ssl: reads keys; --logger imports a module (§2).
  10. The names don’t say the shape. make_application makes the GUI and make_plain_application the CLI; run_app is used by three modes and command mode doesn’t go through it; the migration window has a main() of its own with its own reactor and loop.

§8Where to cut

Not decided; my recommendation, for revision 2.

  • One function picks the mode and installs its reactor, before any import of the application. gireactor for GUI and remote, twisted.internet.default.install() named for the CLI, none for command mode. A test per mode, in a subprocess, checks the reactor type after the start and that cli.py plus parsing loads no reactor. The migration window calls the same function.
  • Read the settings once, at the start of run(). A startup record (workspace, 2.1 file to convert, app settings) that the locks, the migration and load_settings take, so the locked workspace and projects.path are the same value.
  • Start the log and the locale first, right after parsing, in every mode that has a reactor. The order of the log is then the order of the start.
  • A base class for the steps that every app shares (locale, settings, logger, quit triggers), with Application, GuiApplication and RemoteApplication on it, and RemoteApplication in a module of its own that imports neither app nor bricks. Remote skips set_ksm.
  • _start as a list of named steps, each a method, the GUI adding its own at named places instead of around super(). One place registers the quit triggers, in their order.
