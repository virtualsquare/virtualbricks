QEMU for Other Architectures

Virtualbricks asks the QEMU program of a machine what it has, and builds the command line from the answers. The questions are the same for every qemu-system-*, but only qemu-system-x86_64 was recorded and tested. Asked of every emulator of the seven targets, the others answer in ways the parsers don’t read, and some settings stop their machines. This page says how to read every answer, what to leave out where a machine can’t take it, and which architectures to record.

§1At a glance

Asking
The network backends are asked with -machine none, so that a program without a default machine answers too. One reader for the CPU lists of every architecture and every QEMU from 6.2 (§4).
No default
On arm, aarch64 and five more a machine needs a machine type: without one the start is refused with a message, and the panel says so under the machine type (§5, Q2).
Left out
As for any setting a program lacks, with a warning: the PC speaker outside the PC machines, the clock drift fix outside the x86 ones, the standard VGA and virtio disks where the program has neither. A card the program lacks becomes an rtl8139, or else the program’s own virtio-net (§5).
Recordings
Six more architectures on the seven targets, those Debian releases on: aarch64, arm, ppc64, riscv64, s390x and mips64el; the other CPU lists as excerpts in the tests (§7, Q1).
Names
Each emulator once in the program menu, under QEMU’s name, not again under Debian’s links; the package of each one for the messages of a missing program (§8, Q3, Q4).
Plan
Four steps on develop, a commit each, the last a check of the recorded architectures in the containers (§10, Q5).

§2Today

The program menu of a machine lists every qemu-system-* in the QEMU folder and in PATH, and programs.py asks any of them the questions of QEMU_QUESTIONS. What goes wrong with the ones that aren’t x86:

  • The network backends. -netdev help fails on a program without a default machine: No machine specified, and there is no default. That is aarch64, arm, avr, rx and tricore everywhere, sh4 from QEMU 9.2, riscv32 and riscv64 on 11.1. The answer reads as no backend, so on Debian, whose QEMU has VDE, a machine of qemu-system-aarch64 starts with its cards unplugged and the warning can’t join a VDE switch.
  • The CPU models. Up to QEMU 8.2 each architecture writes its list its own way, and the reader expects a heading. With none, as PowerPC, MIPS, SPARC, RISC-V, m68k, sh4 and avr have, it finds no CPU model, and the one chosen is left out with has no CPU model. s390x has a heading only above its feature flags: the reader takes its 311 flags for the models. From 9.2 every list has the same shape, but SPARC follows its list with three lines of features, read as models named CPU, CPU and features.
  • No default machine type. The panel offers The default, and QEMU refuses the start with the message above.
  • The PC speaker goes into -machine pcspk-audiodev=snd0, which every machine that isn’t a PC refuses: Property ‘virt-10.0-machine.pcspk-audiodev’ not found.
  • The clock drift fix, -rtc driftfix=slew, stops the machines of alpha, hppa and MIPS, which have the clock chip of the PC: the ‘slew’ policy is only available for x86 machines from 9.2, Invalid lost tick policy before. On the others it does nothing, or warns.
  • The cards. rtl8139, the model of a new card and the stand-in for a model the program lacks, isn’t in s390x, sparc, avr, microblaze, rx, tricore, nios2 and hexagon: ‘rtl8139’ is not a valid device model name.
  • The standard VGA isn’t in s390x, sparc, m68k and the small boards: standard VGA not available. Virtio disks aren’t in sparc, or1k on 6.2 and the small boards: ‘virtio-blk’ is not a valid device model name.
  • The packages. PACKAGES knows the two programs of qemu-system-x86: a missing qemu-system-aarch64 is named without the package that has it.
  • Two names for one program. From Ubuntu 24.04 and Debian 13 the packages add links with Debian’s names of the architectures: arm64, armel, armhf, amd64, loong64, powerpc, ppc64el; ppc64le is a link to ppc64 on every target. The menu shows aarch64 and arm64, the same program.

Everything else works. On aarch64 and arm with virt, MIPS with malta, PowerPC with g3beige, s390x, riscv64 with virt, alpha, hppa and sparc64, the lines of the other settings start: disks and CD-ROM (on virt -hda and -cdrom become virtio drives, the machine’s own kind), USB, the serial socket, the keyboard, gdb, ACPI off where the machine has the property and left out with a warning where it hasn’t. KVM is listed by the x86 programs only, on this amd64 host, and the other ones leave it out with the warning they have today.

§4Asking

  • The network backends: -machine none -netdev help. The machine type none, the empty machine, is in every program from 6.2, and where both questions answer, the two answers are the same, on every emulator of every target. Only qemu-system-x86_64-microvm answers neither: it runs with KVM only.
  • The CPU models: one reader for the six shapes of §3. A line under a heading and indented is a model; a line that begins with x86, PowerPC or s390 is a model after that word; MIPS '…' is the name in quotes; Sparc is the name up to IU, its spaces as dashes; a line of a single word is a model; any other line, as the features of SPARC, is not. The list ends at the first blank line after a model, before the flags of x86 and s390x. Read this way, every list of the seven targets gives names that -cpu takes.
  • The properties of the machine type are asked of the type chosen, or of the default one; of none when the program has no default and the type chosen isn’t there, instead of -machine ,help, which fails.

The other questions answer on every architecture as they do on x86: --version, -help, -machine help, -device help, -display help, -audiodev help and -accel help, with or without a default machine.

§5Command lines

As step 10 decided for the settings a program can’t honour (10 §7, V2 B): the setting is left out, the machine starts, and the warning in Logs names the machine, the key and the version; the panel shows the same words under the row. Each check is an answer of the program or of its machine type, not the name of the architecture.

§6Left to QEMU

What a machine type needs of its own isn’t in any answer, and QEMU says it clearly in Logs when the start fails. These stay as they are:

  • a kernel (m68k mcf5208evb, cris), a BIOS (sh4 shix, rx) or a firmware that the distribution doesn’t ship (riscv32);
  • more memory than the default 64 MiB: 80 MiB for pseries, more than 1 GiB for loongarch64;
  • one CPU only: -smp 2 is refused by g3beige, the SPARC machines, sh4 and the small boards;
  • no PCI bus (riscv spike, sh4, xtensa, or1k’s simulator): no PCI card, sound card or virtio-pci disk; the machine type virt has one.

§8Names and packages

The program menu

Each program once (Q3): a name that is a link to another emulator of the same folder, as qemu-system-arm64 to qemu-system-aarch64, is left out of the menu, and the name QEMU gives the program stays. The one a machine uses stays in its menu, whichever it is, so a project made with qemu-system-amd64 shows it. The Settings window’s list of the programs of a folder does the same.

The packages

PACKAGES gets every emulator of the targets, by the package of Debian and Ubuntu: qemu-system-arm, -mips, -ppc, -sparc, -s390x, -riscv and -misc, and the links of §2 with the package of their program. Two moved (Q4): riscv32 and riscv64 are in qemu-system-misc up to Debian 12 and Ubuntu 24.04, in qemu-system-riscv after; s390x in qemu-system-misc on Debian 12. The proposal names both, the newer first: qemu-system-riscv64 (qemu-system-riscv or qemu-system-misc) isn’t installed.

The guide and the README

The table of packages in The programs it needs gets a line for the other architectures, and the README’s list of programs says which machines need a machine type chosen.

§9The code and the tests

  • programs.py: the question of the backends, parse_cpus(), PACKAGES with a tuple where a program has two packages, machine_properties() with no machine; qemu_programs() without the links.
  • bricks/virtualmachine.py: lacks() with the four checks, the stand-in card in _cards() and in VirtualMachineDraft.add_card(), prepare() refusing a machine without a type; the panel’s machine page shows the warning of the type.
  • tests/data/programs/record.py: the six programs and their machine types; the seven recordings made again.
  • Tests: the reader on each shape of §3; on each recording, each program’s CPU models are names -cpu takes and its backends are those of x86; command lines of every recorded program on every target, with the warnings of §5; the refusal; the menu without links. All of it new code, so with tests of its own.
  • The check (Q5): start.py starts, beside the sample project, a machine of each recorded program in the target’s container, paused, with a disk, a CD-ROM and a card, as this page’s survey did.
