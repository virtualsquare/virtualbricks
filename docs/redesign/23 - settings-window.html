Virtualbricks Settings Window

The Settings window, File › Settings, gets the rows of the brick panels: a label and a line of help from the schema, a switch, a menu or a folder, and under the row what is wrong with it. It keeps a page for each place the settings are kept, now with Cancel and OK on drafts, KSM included. The program folders say what they hold. The audio driver and the terminal offer what the computer has. The format of private copies stops being a setting: a new one is always qcow2.

§1At a glance

Layout
A page for each owner, as today: This computer, kept in settings.toml, and Project lab, kept in its project.toml. Over a connection, the lab machine gets a page between them. A line at the top of each page says where its settings are kept, and no page needs scrolling (S1).
Rows
The rows are those of the brick panels: form.py’s Form, with the label and the help from the schema, translated. Every setting gets a label= as the bricks’ have (§5).
OK
The window works on a draft for each owner. OK writes only the settings you changed, so a setting changed in the console while the window was open stays. Cancel changes nothing, KSM included: KSM changes on OK, and the window stays open with the reason if it couldn’t (S2).
Project
The settings of the project stay in this window, in a section named after the project (S3).
Folders
The QEMU and VDE folders are folders again, not “(None)”. Under each, a line says what is found there, or what is missing and the package that has it, as the alert at start does (S4).
Menus
The audio driver offers the drivers that QEMU lists (S5), and the terminal offers the terminals found that take -e (S6). Both can still be typed.
Fixes
The format of private copies is no longer a setting: a new private copy is always qcow2. The menu offered cow, which no QEMU of the targets makes (S7). The alert at start no longer says “KSM not found” when KSM is only off (S8). The workspace shows on this computer too (S9).

§2Today

The window is a Gtk.Dialog of 600 by 400 pixels with a notebook. On this computer it has two pages, Application and This project. Over a connection it has three: This computer, the lab machine, and This project. Each row is a label and a widget in a grid. These pictures are the window of 997ddc7 on Broadway, with a project open.

What I found, each one checked:

  1. The words are those of the Glade file: “X-window terminal command”, “Enable systray”, “VDE binaries path”, “Allow female plugs on devices”, “Private COW format”. Every setting has a line of help in the schema, written for the comments of the files on page 10, and the window shows none of them. The brick panels take their labels and help from the schema (11 P4).
  2. Both folders show “(None)”. The buttons are GtkFileChooserButtons in their default mode, OPEN, which shows a chosen file, and set_current_folder() chooses none. On Broadway, the same button in SELECT_FOLDER mode shows bin. The Glade file of 2.1 had the same buttons, so 2.1 showed “(None)” too. OK still keeps the folder, since get_current_folder() reads it.
  3. The format menu offers cow, which no QEMU of the targets makes. qemu-img create -f cow answers Unknown file format 'cow' with QEMU 6.2 of Ubuntu 22.04 (in podman) and with QEMU 10.0 here. Both still make qcow. A project set to cow can’t make a private copy, so none of its machines with a private disk start. The default of 2.1 was qcow2, so only a project whose user chose cow has it.
  4. The audio driver is typed. A typo shows only when a machine with a sound card starts, as a warning, and the machine starts without sound (10 V2 B). QEMU lists its drivers with -audiodev help, except QEMU 6.2, and the recordings have them: QEMU 7.2 has alsa dbus jack none oss pa sdl sndio spice wav, and 8.2 and later have pipewire but not sndio.
  5. The terminal is typed, and its default is /usr/bin/xterm, which a desktop doesn’t always have. A console runs terminal -e vdeterm socket, so the terminal must take -e followed by a program and its arguments. xterm and konsole do. gnome-terminal and xfce4-terminal don’t: their -e takes one string. Debian’s x-terminal-emulator is meant to take -e in the first way, through wrappers for the terminals that don’t; step 1 checks this on every target (§9).
  6. KSM changes at once, and again on OK. Turning the switch runs sudo tee at once, and the window’s close button does nothing until it answers. OK then sets KSM again. Cancel leaves KSM as the switch left it but saves nothing, so KSM can run while settings.toml says it’s off. The e2e notes record the trap: on a machine where KSM runs, OK with the tests’ settings tries sudo -n to turn it off.
  7. The alert at start says “KSM not found in Linux” when KSM is only off. check_prerequisites() asks check_ksm(), which reads 0 from /sys/kernel/mm/ksm/run as “not found”, then turns the setting off. Here, where KSM is off, every start shows the alert. The e2e tests turn the alert off for this reason. At start, load_settings() turns KSM on without waiting for the answer. If the setting is on, the check can therefore read 0 before sudo has written 1.
  8. OK writes every row. A setting changed in the console while the window is open is overwritten by the window’s old value. OK also sets KSM to the switch even if you didn’t touch it, which is the trap of item 6.
  9. With no project open, the project page is greyed out under a note about “the open project”.
  10. The workspace shows only over a connection.
  11. Cancel and OK fill the bottom of the window, as Glade had them. The newer dialogs (New Project, Add Image, New Event) put them in a header bar.

§3The window

The window keeps a page for each owner (S1): the notebook of today, under a header bar that holds Cancel and OK. On this computer it has two pages, This computer and Project lab, named after the open project. Over a connection it has three, with the lab machine’s page between them. A line at the top of each page says where its settings are kept. The window is 640 pixels wide and as tall as its tallest page, so nothing scrolls. The rows are form.py’s, drawn as GTK 3 with Adwaita draws a GtkListBox in a frame. The QEMU and VDE facts are from this machine.

The page This computer has two sections, Windows and Bricks. Over a connection, they are the two pages This computer and lab.example, so a setting is in the same place in both cases, and the sections tell you which settings move to the lab machine.

§4Other directions

The directions not taken, for the record. They use the same rows; what changes is how the rows are arranged, and when they apply.

A fourth direction moves the project’s settings out of this window: Projects › Project Settings… would open a window for the open project’s settings, and File › Settings would keep the application’s. Each menu would then say whose settings it opens. But the QEMU and VDE folders are what people look for in Settings, and with pages, the project’s already have a page of their own (S3 B).

The checks of the folders, the terminal and the audio driver need facts from the machine: what a folder holds, and what QEMU lists. The window asks the engine when it opens and again after you stop typing in a folder for half a second. Until the answer comes, a row shows no note. The drafts keep the facts and check against them, so check() stays synchronous, as on the brick panels.

The QEMU of the facts is qemu-system-x86_64, or else the first qemu-system-* of the folder. The audio drivers belong to the build, not to the emulator, so one emulator is enough. Its answers are the ones the machine panels already ask for, cached by path, size and time.

§6Cancel and OK

With S2 A, the window has a draft for each owner, as the brick panels do. A draft holds a copy of the settings when the window opened, and the values as the rows have them. Cancel, Escape and the window’s close button drop the drafts. OK does this, in order:

  1. It takes what was typed but not yet taken, as Panel.commit() does.
  2. If a draft has an error, OK stays greyed out. The tab of each page with an error carries a mark, and OK’s tooltip names the page, the row and the reason (board C).
  3. It writes the changes of this computer’s draft with set_setting() and store_settings(). It then sends the changes of the machine’s and the project’s drafts in one engine.set_settings(), which saves the project as it does today. Only the settings you changed are written; the others keep whatever value they have then.
  4. It starts or stops the tray icon if that setting changed.
  5. If the KSM switch changed, OK greys out and shows a spinner while it calls engine.set_ksm(). When KSM is as asked, the window closes. When it isn’t, the window stays open on the page with the KSM row (board D): the other changes are already saved, so their drafts now start from them, and the KSM row shows the error. OK tries again; Cancel closes.
  6. Otherwise the window closes.

The switch shows what KSM is when the window opens, as today: check_ksm() on this computer, or the lab machine’s setting over a connection.

The alert at start (S8): it names KSM only when the setting is on and /sys/kernel/mm/ksm/run doesn’t exist, and it no longer turns the setting off. A KSM that is merely off, which is the default, says nothing. When the setting is on, the check waits for the start’s own set_ksm(True) and warns if KSM is still off then.

§7Over a connection

The same window gets three pages (board C), as page 19 R10 decided, one for each draft. This computer’s draft reads get_setting(). The lab machine’s draft and the project’s read engine.machine.setting(), and their OK goes through SettingSet, as today. The folders are typed and completed from the lab machine with Folder (19 R9).

The facts of a folder need a command of protocol 2 that doesn’t exist yet. I propose ProgramsFound(vde_path, qemu_path), answered beside the requests that wait, as the facts are. It returns the programs missing, each with its package; the folder where each one found was; and whether each folder exists. On the lab machine it is missing_programs() plus the two lookups. The audio drivers come from QemuFacts, which the machine panels already call. The new command goes in tests/data/amp-protocol-2.txt, as rule T7 A of page 20 requires.

A setting that the lab machine changes while the window is open arrives with SettingsChanged. A row you haven’t touched shows the new value. A row you have changed keeps yours, and OK writes yours, as 19 R7 B decided for panels: the last OK wins for the keys it changed. On this computer, settings.changed does the same for a setting set in the console.

  • The terminals: a podman script installs each desktop’s terminal on each target, then checks two things: what x-terminal-emulator points to, and whether -e prog arg runs prog arg. That decides the table TERMINALS and the new default (S6). The script stays in the job’s temporary folder, as the recordings’ scripts do.
  • e2e: settings.feature has steps for pages (“on its page Application”) and old labels (“Enable systray”). The steps keep their pages under the new names: Application becomes This computer, and This project becomes Project name. The labels become the new ones, and there are new scenarios: Cancel leaves settings.toml as it was; the VDE folder names a missing program; the audio driver menu. The steps go in e2e/STEPS.md, and e2e/TODO.md is updated.
