Virtualbricks Control Socket

A Virtualbricks that runs listens on a socket in your runtime folder. virtualbricks --command brick start sw1 sends it a console command from any terminal or script, prints the answer and exits with its status. This works whether that Virtualbricks has windows or not.

§1At a glance

Command
virtualbricks --command brick start sw1: the words after --command are the command, quoted as in the console. With no words, the command reads its standard input a line at a time and stops at the first error (Q2).
Answer
The answer goes to the standard output and an error to the standard error. The exit status is 0 when the command was done, 1 when it failed, and 2 when no Virtualbricks answered (Q5).
Socket
$XDG_RUNTIME_DIR/virtualbricks/.control, mode 0600, in a folder that only you can enter. Every Virtualbricks listens there once its project is open, with or without the windows (Q1). --socket PATH puts it somewhere else, for both ends.
Owner
One Virtualbricks has the socket. It holds the lock .control.lock next to the socket. In the modes system and user there is only one of yours anyway. With --lock none, the first one to start has the socket and the others run without one, unless each gets its own with --socket (Q4).
Protocol
One line of JSON for each request and each answer, after a greeting that gives the protocol’s version. You can read it with socat, and any language can speak it (Q3).
Commands
Every command of the console works as in its terminal. Paths are read from the folder where you run --command (Q6). A command doesn’t wait for the terminal, the events or other connections (Q7).
Client
It loads no Twisted reactor and no GTK, takes no lock and opens no project. It connects, sends, prints and exits.
Plan
Four steps, a commit each, on a new branch mg/control-socket from mg/console-redesign (§9).

§2Today

The console of page 14 has two ways in: the terminal that started Virtualbricks, and the files of --run and source. A Virtualbricks started from the desktop’s menu, or with --noterm, has no console at all. A script can’t ask a running Virtualbricks to do anything. All it can do is start another one, and the single-instance mode refuses that.

The runtime folder already exists. locations.runtime_dir() is $XDG_RUNTIME_DIR/virtualbricks, or virtualbricks-uid in the temporary folder when the variable isn’t set. Virtualbricks makes it at start with mode 0700. Each open project gets a folder in it for the sockets of its bricks, and the user lock of page 13 is there as .lock. A project’s name never starts with a dot, so names that start with one are free for Virtualbricks’ own files.

§3The command line

  • Words. The words after --command are the words of the command, as the shell split them. The client quotes them again for the console with shlex.join, so kernel_command_line="console=ttyS0 root=/dev/vda" reaches the console as one word, as if typed there. The options of virtualbricks end at the first word, so an option of the command, such as --force, can come anywhere after it.
  • Output. The answer goes to the standard output a line at a time. When a command fails, what it did before goes to the standard output, and the error, Error: …, goes to the standard error, as in the console.
  • Exit status. 0: the command was done. 1: it failed. 2: no Virtualbricks answered, because none runs, it ended during the command, or it speaks another version of the protocol. A wrong option exits with 1, as today.
  • Standard input. With no words, --command reads commands from its standard input, one per line, over one connection, each after the one before. The first error stops it, as it stops source, and names its line: line 3: No brick named vm9. When the input is a terminal, it doesn’t sit waiting: it says how to use it.
  • Ctrl+C stops waiting, not the command. The connection closes and Virtualbricks goes on with the start, as when you press Ctrl+C in its console. The exit status is 130.
  • Another socket. --socket PATH gives the path of the socket, both to the Virtualbricks that listens and to --command. virtualbricks --no-gui --socket ~/labs/lab1.sock listens there, and virtualbricks --socket ~/labs/lab1.sock --command status talks to it. Like every option, it comes before the words (§4).
  • Other options. The options of a run mean nothing with --command, so they are refused: --no-gui, --noterm, --run, --workspace, --lock, --logfile and --logger. --socket is the one that goes with it. Words without --command are refused too, and the message shows the command with --command.

§4The socket

Who listens

Every Virtualbricks listens, with or without the windows. It starts once the last project is open, before the commands of --run, so --command works while a long script is starting machines (Q1).

The folder is 0700 and the socket 0600, so only you and root can connect. Anyone who can connect can already run programs as you, so the socket gives nobody new powers. Before it listens, Virtualbricks checks that the folder is a real folder, not a link, that it belongs to you, and that no one else can open it. This matters for the fallback in the temporary folder, where another user could have made virtualbricks-uid first. If the check fails, Virtualbricks runs without a socket and logs why. --command makes the same check before it connects.

Who has it

Only one Virtualbricks can listen on a path. The one that has the socket holds an exclusive flock on .control.lock, like the locks of page 13, for as long as it runs:

  1. It takes .control.lock without waiting. If another Virtualbricks holds it, this one runs without a socket and logs which process has it.
  2. It removes any .control left behind by a Virtualbricks that ended without removing it, as after a crash. While it holds the lock, nobody else listens there.
  3. It listens on .control, mode 0600.

When it ends, it stops listening and closes each connection after its last answer is written, so quit gets its answer too. Then it removes .control and releases the lock. After a crash the socket stays behind, and the next start removes it.

ModeVirtualbricks of yoursThe socket
systemone on the machineit has it
userone of yoursit has it
noneany numberthe first to start has it, whatever its mode; the others run without one and log it, unless each has its own --socket (Q4)

Another user’s Virtualbricks listens in that user’s runtime folder, so --command never reaches it. When --command finds no Virtualbricks of yours, it says whose one is running (§7).

The length of the path

A Unix socket path has at most 107 bytes. /run/user/1000/virtualbricks/.control has 37. When the folder is in a long TMPDIR, Virtualbricks runs without a socket and logs why, and --command says the same. A longer --socket is refused with the other options.

Another path

With --socket PATH, the socket is at PATH and its lock at PATH.lock. The default follows the same rule: .control and .control.lock. ~ is expanded, and a relative path is read from the folder where Virtualbricks starts. The folder must exist, since Virtualbricks doesn’t make it. It doesn’t have to be private, because the socket’s mode 0600 keeps others from connecting. In a folder that others can write to, such as /tmp, they can take the path first or hold its lock, so choose a folder of your own.

Virtualbricks removes what is at the path only when it is a socket of yours that nobody answers on. Anything else stays where it is, such as a file given by mistake, and Virtualbricks runs without a socket and logs why. --command connects only to a socket that belongs to you, at either path.

§5The protocol

UTF-8 JSON, one object per line (Q3). On connecting, the server sends a greeting. Then the client sends requests and gets one answer for each, in order, until it closes the connection.

MessageKeyWhat it is
greetingprotocol1. A client that doesn’t know the number says so and exits with 2.
versionThe version of the Virtualbricks that runs.
pidIts process.
projectThe name of the open project.
requestlineThe command, as typed in the console.
cwdThe folder that paths are read from. It is optional; without it, the server uses its own folder.
answerokWhether the command was done.
linesThe answer, or what the command did before it failed.
errorOnly when ok is false: the message, in the language of the Virtualbricks that runs.

A request that isn’t a JSON object with a string line gets ok: false with the reason, and the connection stays open. A line longer than 64 KiB closes the connection. The protocol number is there for the day the protocol changes: a Virtualbricks that has run since before an upgrade may speak an older one, and the client then says to restart it.

§6Commands from outside

  • Every command of the console works, with the same checks. quit works too, and is refused while bricks run. python isn’t a command but something the terminal does, so it isn’t available. brick monitor opens its terminal on the display of the Virtualbricks that runs, as its menu does.
  • Paths (Q6). Two commands take a path: source FILE and image add NAME PATH. They read it from the folder of the request’s cwd, so virtualbricks --command source lab.vb runs the lab.vb of the folder you’re in. Context gets a cwd and a path() that both commands use. The terminal and the events pass the folder of Virtualbricks, as they do today. KEY=VALUE values are kept as typed, as in the console.
  • Waiting (Q7). A connection runs its requests one after the other. The answer to brick start comes when the brick runs or fails. Connections don’t wait for each other, or for the terminal or the events, just as the terminal and the events don’t wait for each other today. The model refuses what can’t be done at that moment, such as opening a project while bricks run, or deleting a running brick.
  • The windows. A brick made from outside appears in the Bricks tab and in the Topology, as one made in the console does, because the windows follow the model.
  • The log. Each command from outside is logged, and so is its error if it fails, so the Logs window shows what a script did: Command from --command: brick start sw1. A failure that isn’t a CommandError is logged with its traceback, as in the console.
  • The language. The answers are in the language of the Virtualbricks that runs, not in that of the terminal where --command runs.

§8The code and the tests

  • Server. control.listen(factory, path, reactor) checks the folder, takes the lock, removes a stale socket and calls reactor.listenUNIX(path, ..., mode=0o600). It adds a before shutdown trigger that stops listening and returns a Deferred that fires once every connection has closed after its last answer. The protocol is a LineOnlyReceiver with a queue of requests, and each request goes through dispatch.run() with a Context that carries its cwd. The GUI’s Application inherits _start, so it listens too.
  • Client. client.main(words, stdin, stdout, stderr) returns the exit status. connect() finds and checks the socket, and talk(sock, lines, cwd, ...) speaks the protocol. It loads neither the Twisted reactor nor gi, so it starts at once.
  • Options. --command is a flag, and parseArgs keeps the words. Twisted’s option parser stops at the first word that isn’t an option, so brick start --force sw1 reaches the console whole.

Tests, each next to its module:

  • tests/console/test_control.py: the protocol on a fake transport: the greeting, a request and its answer, an error, a bad line, requests in order, a connection lost during a command, the log. listen() in a temporary runtime folder: the lock, a stale socket removed, a second listen() that goes without, a folder that isn’t private, a path too long, another path and its lock, a file at the path left alone. The shutdown after the last answer.
  • tests/console/test_client.py: talk() against a scripted peer on a socket pair. Each message of §7 and its exit status. The words quoted again. The standard input, with its first error. A fresh process that imports the client loads neither gi nor twisted.internet.reactor.
  • test_app.py: --command and its words, --socket and its checks, the refused options, words without --command. test_locks.py: hold(). test_locations.py: the two paths. test_general.py and test_images.py: a relative path read from cwd. test_docs.py already checks that the man page lists every option.

Q3 The protocol

A JSON Lines: a greeting, then a request and an answer per line. You can read it with socat, any language can speak it, and there is room for answers as data later.

B Twisted’s AMP: typed commands in length-prefixed boxes. It is robust, but only Twisted speaks it easily, and the client would need Twisted’s reactor.

C Text: the line in; the answer out, then an end line with the status. An answer line that looks like the end line needs escaping.

§11Later

These go under IDEAS in the TODO.

  • A second socket that speaks Twisted’s AMP, for programs written with Twisted, open at the same time as the JSON one (Q3).
  • An interactive console on the Virtualbricks that runs, virtualbricks --attach, with the line editing, the history and the completion of its terminal. Completion needs a request of its own.
  • Answers as data, for brick list --json, carried by the protocol as they are.
  • A socket for each workspace, with the runtime folders that tell apart projects of the same name (13 §10).
  • A way to turn the socket off, --no-control or a setting, if anyone wants a Virtualbricks that can’t be reached.
  • Answers in the language of the terminal where --command runs.
  • A connection that follows what changes, watch, for a status bar or another program.
