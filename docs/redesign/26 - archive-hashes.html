Virtualbricks Archive Hashes

Whether contents.toml should hold a hash of each member and of each image the project uses. They would catch three things that archives miss today: a member damaged on the way, a private disk put on the wrong image, and an image reused only because it has the same name and size. This page measures what they would catch, what gets in the way, and what they cost.

§1At a glance

The idea
contents.toml gives each member the SHA-256 of its bytes, and each image of the project the SHA-256 of its file, whether the archive has the image or not. Readers ignore the keys they don’t know, so the format stays 1 (§6).
Damage
A packed archive isn’t gzipped, so nothing checks its bytes. One bit flipped in a packed disk gave wrong data with no error 62 times out of 80. A gzipped archive is checked only when GNU tar reads it: bsdtar and tarfile extracted 30 damaged archives out of 30 without an error (§3). A hash per member names the damaged one.
Wrong image
The export leaves the images out by default, and the import then picks a file by its path or its name. Nothing checks that it is the image the private disk was made on. A wrong one corrupts the machine’s file system without an error (§4).
Reuse
An image in the archive is replaced by a file of the shared images with the same name and size. A raw image’s size is the size of its disk, so two raw images of 10 GiB always match (§2).
The catch
A hash of a file changes when qemu-img rewrites it, as packing and unpacking do, although the disk stays the same. Two copies of one Debian 13 disk on this computer have different hashes (§5).
Cost
SHA-256 runs at 2.1 GB/s here, so reading the disk costs more than hashing it. The export would read the images it leaves out, which it doesn’t touch today: once per file, with a cache (§7).
Not covered
Hashes catch accidents. Whoever changes a member on purpose can change contents.toml too (§10).

§2Today

contents.toml lists the members in the order of the archive: the name and size of each, and, for a disk packed by qemu-img, packed and real_size, its size before (vbp-format.html, virtualbricks-vbp(5)). There is no hash.

What checks the bytes

ArchiveWhenChecked by
GzippedWithout qemu-imgThe CRC-32 of the whole stream, at its end, but only GNU tar reads that far. bsdtar, which the import prefers, and Python’s tarfile stop at the end of the tar, before the CRC (§3).
PackedWith qemu-img, so nearly alwaysNothing. The checksums of tar cover the headers alone. A qcow2 file has no checksum of its data, and its compressed clusters have none that QEMU checks (§3).

How the import chooses an image

plan_image() and _local_default() in config/importing.py:

  • An image in the archive is copied to the shared images, unless they have a file of the same name and the same size, the real_size of a packed one. That file is used instead.
  • An image not in the archive is the file at its path on the computer it comes from, when this computer has one; otherwise a file of the shared images under that file’s name or the image’s name; otherwise it is left unset. The Export window leaves the images out by default (page 04), so this is the usual case.

Then rebase points each private disk at the chosen file. The Images tab does the same with qemu-img rebase -u when an image gets another file (relink(), page 09). Neither looks at what the file holds.

§3A damaged byte

Packed disks

Measured today: 8 MiB of random words, packed into qcow2 by qemu-img convert -c, with zstd (3.6 MB) and with zlib (4.3 MB). Forty copies of each, each with one bit flipped at a random offset past the first MiB, where the compressed clusters are. Each copy was read back with qemu-img convert -O raw and compared with the words.

Packed withRead errorWrong data, no errorUnchanged
zstd13270
zlib5350

qemu-img check found nothing wrong in the first five copies of each.

What the import does with them today. A read error makes the unpacking fail: the member stays packed, the import warns left compressed, and the machine gets an I/O error when it reads that cluster. Wrong data is unpacked as it is, and the machine reads it. A member that isn’t packed, as a raw image, is read as it is too.

Gzipped archives

The first 4 MiB of the same words, in a tar gzipped by gzip -6 (1.6 MB). Thirty copies, each with one bit flipped at a random offset, extracted as the import extracts them: from a pipe, with each of its three tools.

Extracted byRefusedWrong data, no error
GNU tar 1.35, --gzip300
bsdtar 3.7.4030
Python’s tarfile, r|*030

GNU tar runs gzip, which reads to the end and says invalid compressed data--crc error. The other two stop at the blocks of zeros that end the tar, before the CRC that follows them. The import prefers bsdtar when it is installed, so the CRC is checked only on a computer that has GNU tar and not bsdtar.

§4The wrong image

A private disk holds only the clusters its machine changed; it reads the rest from its image. Its qcow2 header names the image by path and format, and nothing else: nothing in the file says which image it was. When the import, or the Images tab, points the disk at another file, the machine still starts. It reads its own clusters on top of another disk’s, and its file system is a mix of the two. Nothing fails until the file system notices, maybe much later, and the machine’s writes make it worse.

How it happens:

  • The image is left out of the archive, as by default, and this computer has another file of that name. Debian publishes its cloud images in latest/ under one name, and each new build replaces the file: debian-12-genericcloud-amd64.qcow2 downloaded in March may not be the one of January.
  • Two projects name different images with the same file name: disk.qcow2, base.img.
  • The user picks a file with Use a file… in the Import window, or in the Images tab.

With the hash of the image the disks were made on, the import can compare it with the file it is about to use, and say so before the import (§8).

§5File bytes or disk contents

The SHA-256 of a file is the hash of its bytes. The same disk can live in files of different bytes, since qemu-img convert lays out the clusters its own way. Measured today:

  • Packing the same qcow2 twice gave two different files: with -W, qemu-img writes the clusters in the order they are ready.
  • A qcow2 made by qemu-img convert came back from packing and unpacking with the same bytes. A disk written in another order, as a running machine writes it (here by qemu-io, from its end), came back with other bytes. qemu-img compare says both are the same disk as before.
  • On this computer, ~/Downloads/debian13.qcow2 (25 February, 6 758 989 824 bytes) and ~/.virtualbricks/vimages/debian13.qcow2 (7 October, 6 610 354 176 bytes) have different SHA-256 hashes. qemu-img compare says they are the same 10 GiB disk.

So an image that went through a packed archive no longer has the hash its disks were made on, and a check by the file’s hash would warn about the right image. The ways out:

§6In contents.toml

The example of virtualbricks-vbp(5), with the new keys:

  • sha256 of a member is the hash of its bytes as the archive holds them, packed for a packed disk. The import checks it right after extracting, before unpacking.
  • [images.name] is there for each image the project uses, in the archive or not: the size and hash of its file on the computer the archive comes from (or the remembered hash, H2). A packed image has two hashes, which differ: its member’s and its file’s.
  • The order. contents.toml is the first member, so that the import knows what the archive holds from its first blocks (page 04, P10). The hashes must then be known before the archive is written: the export hashes each member in its staging folder after packing, while the packed files are still in the page cache, and the images before.
  • Compatibility. A reader of format 1 ignores the keys it doesn’t know, so the new keys stay in format 1. A format 2 would make every Virtualbricks that reads format 1 refuse the archive (written by a newer Virtualbricks). An archive without hashes imports as today. The list of members that the archive protocol sends, [name, size, kind, packed, real_size], would get a field (archive-protocol.html).

§7What it costs

Measured todayResult
SHA-256 with hashlib, in memory (this CPU has the SHA extensions)2.11 GB/s
BLAKE2b with hashlib, in memory1.01 GB/s
CRC-32 with zlib, in memory5.05 GB/s
sha256sum of both Debian 13 copies of §5, 13.4 GB9.9 s
qemu-img compare of the two, right after, from the page cache2.6 s
  • The export reads each member once more after staging. The packed ones are smaller and were just written. An image left out of the archive is read whole, 6.8 GB for the Debian image, at each export, unless its hash is kept by size, time and inode in the workspace.
  • The import reads each member once more after extracting. For an image not in the archive it reads the file it would use, whole, while the Import window says it is looking. The same cache serves it.
  • Other CPUs. A CPU without the SHA extensions hashes slower; not measured.

§8What the import would do

  • Each member with a hash is hashed after extracting and before unpacking. A member that doesn’t match: H4.
  • An image not in the archive: while the import is planned, the file it would use is hashed and compared with [images.name]. Its row in the Import window says when it differs: Not the image its disks were made on. What the import does then: H5.
  • An image in the archive with a file of the same name in the shared images: that file is used only when it holds the same image (H6).
  • An image with no hash, in an older archive, is chosen as today.

§10Later

  • The Images tab checks a new file against the image’s hash, once project.toml keeps it (H7 B).
  • The Images tab shows an image’s SHA-256, to compare with the one a distribution publishes.
  • An archive changed on purpose would need contents.toml signed. That is another design.
  • The imports and exports of the console and of a connection, in the TODO list (14 §11, 19 §13), would make the same checks.
