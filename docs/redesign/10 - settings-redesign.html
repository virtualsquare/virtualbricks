Virtualbricks Settings Redesign

Configuration files that explain every key and say which values are defaults; names in words instead of abbreviations of QEMU options; command lines that each brick builds in plain code; and an icon in the configuration of every brick and event. The groundwork for the new configuration panels.

What this covers: your request of today: comments in the configuration files, with a mark for default values; clearer names in the schemas; a new way to build the command lines and to start the bricks; and an icon for every brick and event, stored and not used yet. The panels come next, in a proposal of their own. The names replace decision D7 of the configuration redesign (“keep the field names”), as D5 was replaced before it.

§1At a glance

Comments
Every key Virtualbricks writes has a comment on the line above: what the key is for, its range or its choices, and its default. A value at its default also says # default on its own line; a value without it was set. The texts come from the schemas, so every writer adds them: projects, settings, state, imports and migrations.
Names
68 keys get names in words: deviceen and cdromen become cdrom = "device", usbdevlist becomes usb_devices, pon_vbevent becomes on_start. The settings too: cowfmt becomes cow_format. One name everywhere: the key in the file, the attribute in the code, the name in the console. qemu_program can’t be empty. The full table is in §4.
Icon
icon moves from the virtual machines into a configuration that every brick and event shares. It’s saved and read; only the virtual machines show it, as today.
Command lines
Each brick type builds its command in a command() method that reads top to bottom as the command line does, with a small Command helper. It reads the configuration and the paths it’s given, and does nothing else. The keys that don’t reach the command line are simply the ones it doesn’t mention. command_builder and its rules of "#", "*" and field names go.
Versions
Before a brick starts, Virtualbricks asks the installed program what it has, and the command line uses what that version accepts. A project made on Ubuntu 22.04 with QEMU 6.2 runs on Debian testing with QEMU 11.1, and the other way round when the older program has what the project asks for. A setting the program can’t honour is left out, and a warning names it and says how to get it. The same for the VDE programs.
Starting
A start runs in stages: the checks and the bricks it plugs into, as today; prepare(), the work the command needs (the private copies of the disks, the key of a tunnel); command(); spawn(). A saved state to resume becomes an option of the start instead of a key of the configuration.
Format
The files stay at format 1. The TOML files haven’t been released, so the new names replace the old ones without an upgrade. The migration of 2.1 projects and settings writes the new names, and rewrites the console commands of the events.
Fixed
Two taps, or two tunnel servers, start with the socket and the name of the last one created. A wire never starts. The kernel command line reaches the kernel in quotes. A tunnel’s key goes through a shell with the password in it. Details in §2.

§2What gets in the way today

From the code at 0bfd5f7. Items marked checked were reproduced on this machine.

Names

  • The virtual machine’s 53 fields are named after QEMU options or abbreviations: deviceen, cdromen, kvmsm, kvmsmem, vncN, tdf, kopt, noacpi, argv0. The same names are the keys of project.toml, the names of the console’s config command and the names the panels pass to brick.set().
  • A switch with a value beside it comes in four spellings: kernelenbl + kernel, cdromen + cdrom, kvmsm + kvmsmem, vnc + vncN, usbmode + usbdevlist.
  • deviceen and cdromen are two booleans for one choice of three: no CD-ROM, a drive of the host, or an image. When both are true the image wins.
  • noacpi is a string where "*" means true. stdout is written in every project and never read. loadvm is a key of the configuration that poweron() sets and clears around a start, and every project saves it.
  • The settings have the same kind of names: cowfmt, erroronloop, femaleplugs, qemupath, vdepath, term, systray, show_missing.

Comments

  • The files have no comments, and the comments of a hand edit are lost at the next save, as virtualbricks-config(5) says under Writing.
  • The schema already has room for words: FieldInfo has label and help. No field sets them.

Command lines

  • command_builder maps options to field names or to callables, with rules of its own: "#" before an option skips it, "*" as a value gives the bare option, "*" before an option drops the option and keeps the value, True gives the bare option, None and False skip it. A field that doesn’t exist is skipped without a word: six of the switch’s entries (--macaddr, -m, -g, --priority, --mgmtmode, --mgmtgroup) and the router’s -c configfile name no field.
  • checked Tap, TunnelListen and TunnelConnect put bound methods of the instance into a dictionary of the class, so every instance uses those of the last one created. With tap1 on sw1 and tap2 on sw2, both command lines are -s /run/vb/sw2.ctl tap2; two tunnel servers both get sw2 as well. The tap’s dictionary is Brick.command_builder itself.
  • checked A wire never starts: Wire.prog() returns a tuple, and spawnProcess fails with “posix_spawnp: path should be string, bytes or os.PathLike, not tuple”.
  • Netemu runs vde-netemu from $PATH, not from the vdepath folder.
  • The virtual machine wraps the kernel command line in single quotes, -append 'console=ttyS0'. No shell takes them away, so the kernel receives them.
  • Building a tunnel’s command line writes a file: TunnelListen.args() runs os.system("echo PASSWORD | sha1sum >/tmp/tunnel_NAME.key"), through a shell that runs whatever the password contains, into /tmp.
  • The virtual machine’s args() returns a Deferred, because it creates the private copies of the disks on the way; the other bricks return lists.
  • checked QEMU 10.0, installed here, refuses five of the options Virtualbricks writes: -soundhw, -no-acpi and -portrait are “invalid option”, -usbdevice host:… is “not supported anymore”, and -sdl is gone from -help. A machine with a sound card, USB devices, the SDL window, the portrait display or ACPI off doesn’t start. Ubuntu 22.04’s QEMU 6.2 still has all five; §7 says which target has which.

Programs and their versions

  • checked The QEMU panel asks the version of qemu-system-x86_64 and picks stored lists of machine types and CPU models, of QEMU 2.0, 1.1.2 or 1.0, comparing the versions as strings. QEMU 6.2 to 9.2 get the lists of 2.0, from 2014; 10.0 and 11.1 get those of 1.1.2, from 2012.
  • checked Ubuntu builds QEMU without the vde network backend, on 22.04, 24.04 and 26.04. A virtual machine with a card plugged into a switch doesn’t start there. Debian’s QEMU has it, and so do the QEMU packages for Ubuntu that you distribute.
  • checked The SDL and GTK windows of QEMU are in the qemu-system-gui package, which qemu-system-x86 only recommends. vde_cryptcab is in vde2-cryptcab, apart from vde2.
  • checked The monitor’s server,nowait gives “short-form boolean option ‘server’ deprecated” on 6.2 and on 10.0.
  • vde-netemu, the program of Netemu, is in no distribution. It comes from cnrl.deis.unibo.it, and its package puts its own wirefilter in place of VDE’s.

Keys that never reach the command line

Found by changing each key of each type, with its switches on, and comparing today’s command lines:

  • Every brick: the events, pon_vbevent and poff_vbevent, which Virtualbricks runs itself.
  • Virtual machine: icon and stdout. The disks reach it through the paths that the start prepares.
  • Tap: mode, ip, nm and gw. Nothing else reads them either: the panel edits them and the brick’s summary shows them, but the address of the interface is never set.
  • Tunnels: password, which goes into the key file. Netemu: the name of a state, which goes to the running emulator over its console. Switch wrapper: path, since it runs nothing.

Other

  • erroronloop only decides whether a loop is logged: the start is refused either way, and the message says to turn the setting off “if you want to start a looped network”.
  • Only virtual machines have icon; graphics.brick_icon reads it with getattr and a default for the others. EventConfig shares nothing with BrickConfig.

§3Comments in the files

A project as Virtualbricks would write it with this plan. A prototype of the writer made this text with the venv’s tomlkit 0.15, and tomllib reads it back unchanged.

The other five disks, hdc to mtdblock, follow hdb and are left out here.

What a comment says

  • Above every key, what the key is for, in the words of the schema: the help of field(), unused until now.
  • At the end of it, in parentheses, the range or the choices from the kind of the field, and the default: (1-64; default 1), (none, image or device; default "none"). An empty string or list is default empty; a default list with items isn’t repeated.
  • On the key’s own line, # default when the value is the field’s default, and nothing otherwise: a key without it holds a value that was set. That is the only comment on a key’s line.
  • Keys that no schema declares, as format, type, connect, endpoints and the keys of a network card, get a fixed sentence above them and never # default.
  • Each file starts with what it is, that Virtualbricks writes it and its comments, and when it rewrites it, then a blank line. There’s no date in it, so an unchanged project gives an unchanged file.

Where it goes

  • The description is wrapped at 79 columns, the width of the man pages, never splitting a word at a hyphen. The parentheses stay whole: when they don’t fit on the last line, they take a line of their own.
  • A value that changes changes only its own line: the description above it doesn’t depend on the value, and # default comes or goes with it.

Default or set

The mark compares the value with the default of the field when the file is written C1. Nothing more is stored, so a value equal to its default says # default even when you chose it. In exchange, any code that writes a file can add the comments from the data alone: the importer, which rewrites a project’s image paths without building its bricks, and the migration. The two other ways, remembering each value you set, or writing defaults as commented-out keys, are in §12.

Which files, in which language

  • settings.toml, state.toml and project.toml. The archive’s contents.toml and the job files passed between processes stay bare: no one reads them.
  • Comments you add by hand are still dropped at the next save C2. The header of each file says so.
  • In English whatever the language of the desktop C3: projects move between machines in archives, and the key names are English anyway. The new panels can translate the same help texts.

How it’s built

  • schema.py: Kind.describe() gives the range or the choices; notes(cls, data) gives, for each key of a table, its description and whether it’s at its default, by the same paths that dump_record() writes, including disks.hda.image and the states of a Netemu.
  • projectfile.project_notes(data) walks a project: settings, images, events, and each brick by its type. settings.py does the same for its two files.
  • tomlfile.dumps_toml(data, notes=None, header="") writes them. The data stays plain TOML data, so the tests that compare dump_record() with dictionaries don’t change.

§4Names

  • Words in snake_case, and one name everywhere: the key in the file, the attribute in the code, the name for the console’s config command.
  • A switch that turns on the value beside it is use_<thing>, next to <thing>: use_kernel and kernel, use_vnc and vnc_display.
  • Units go in the comment, not in the name: memory = 1024 # Memory in MiB.
  • QEMU’s own words stay where they are the words people search for: machine_type, cpu_model, boot_order, initrd, the disk devices hda to mtdblock.
  • A brick’s events are on_start and on_stop, as its menu’s When It Starts and When It Stops.
  • Keys that already say what they are stay: password, delay, actions, transitions, states, a state’s name, an image’s path and description, the keys of a network card, workspace, current_project.

The only changes of structure

The CD-ROM choice, acpi as a boolean, qemu_program never empty (a new Str(required=True)), the tunnel client’s own schema, and stdout, loadvm and portrait gone. Every other row is a rename: same type, same default, same place in the file. The keys stay flat in each brick’s table, as today C5; the disks and the network cards stay tables of their own.

§5The icon

  • A new BaseConfig in base.py, next to Base, with one field: icon = field(Path(), default="", help=…). BrickConfig builds on it and adds on_start and on_stop; EventConfig builds on it too.
  • The virtual machine’s icon moves there. Same key, same kind, same place in the file: format 1 projects need nothing for it.
  • Nothing new reads it. graphics.brick_icon keeps showing a machine’s own icon and the QEMU panel keeps its icon chooser; every other brick and every event keeps the icon of its type. How an icon is chosen, and where it shows, is for the panels.
  • A Netemu keeps its icon on the brick, with its events, not in each state: BRICK_KEYS is the fields of BrickConfig, so the icon follows without a change.

§6Command lines

Each brick type writes its command line in a method, in the order of the command line, with a helper that leaves out what is off or empty C4. A key that doesn’t reach the command line is one the method doesn’t mention. Where versions of a program differ, the method asks what the installed one has, §7.

  • command(prepared) reads the configuration, the brick’s own paths (its socket, its console, the sockets of its plugs) and what prepare() returned, which includes what the installed program has. It reads no file, starts nothing, and returns a list of strings.
  • command_builder, build_cmd_line(), args() and prog() go, and so does the virtual machine’s default_arg0, the program that an empty argv0 meant.
  • Each type is tested with whole command lines, a default brick and one with every switch on, against the recorded programs of every target of §7. Where today’s options work, the expected lists are those today’s code gives, recorded before the change.

§7Program versions

Virtualbricks supports the QEMU and VDE of six targets, and every major version of QEMU from 6.2 on. A project made on one of them runs on a newer one. One made on a newer target runs on an older one when the older programs can do what it asks: that direction isn’t promised, and nothing refuses it for its own sake. The same holds for every brick, not only for virtual machines.

No target ships QEMU 9; the rules below don’t depend on the number, and the tests cover it with a recording from another distribution, as Fedora 41’s 9.1.

Principles

  • The configuration says what, never how: no option of a program is stored. Values that are the program’s own names, as machine types, CPU models, card models and the sound card, are stored as the program names them and checked against the installed one.
  • What the program has, not its version number, decides V1. Before a start Virtualbricks asks the program, and command() takes the spelling it accepts. The version number serves the messages and the supported range.
  • Newer programs are the supported direction. The tests run every command line against the recorded programs of each target, and recording a new one is how a new QEMU is checked.
  • An older program isn’t refused for its version. A setting it lacks is left out, the brick starts, and a warning in the messages window and the log says what, where and how to get it V2: “vm1: QEMU 8.2.2 has no machine type pc-q35-11.1 (machine_type); it starts with the default machine”, “vm1: no SDL window (sdl_window): install the qemu-system-gui package”.

What Virtualbricks asks the programs

  • QEMU, once per program file for the session, keyed by its path, size and time, with the questions run side by side: --version, -help, -machine help, -cpu help, -device help, -display help, -audiodev help, -netdev help, -accel help, and -machine TYPE,help for the properties of the machine in use.
  • VDE: which programs are in the vde_path folder, and the options of each where versions could differ. For a Netemu, vde-netemu, or wirefilter without it V5.
  • A new module, virtualbricks/programs.py, without GTK: qemu_info(path) and vde_info(folder) return Deferreds of what they found, and a parser per question turns an output into data, tested on the recordings. It takes the place of qemu.py, _qemu.py and the three stored lists; the QEMU panel takes its programs, machine types and CPU models from it.
  • The audio driver is the audio_driver setting of settings.toml V4, since it belongs to the host, not to the project. Its default is alsa, which the QEMU of every target that lists its drivers has built in. The settings window gets a field for it.
  • The warning at start about missing programs names the package to install: vde2-cryptcab, qemu-system-gui, vde-netemu.

Cards without QEMU’s vde backend

  • Ubuntu’s own QEMU lacks it; the QEMU packages for Ubuntu that you distribute have it V3. No helper runs between a switch and QEMU.
  • With a QEMU without it, a machine starts with each card that plugs into a switch unplugged: the card without a backend, which QEMU accepts, as a cable pulled out. The warning says that this QEMU can’t join a VDE switch. Host-only cards and socket cards of other bricks follow the same rule where they need vde.

Tests that keep it true

  • Recordings: the answers of each target’s programs to the questions above, in virtualbricks/tests/data/programs/<target>/, made by a script in the same folder that runs podman. A new distribution or a new QEMU is one more run of it.
  • Every brick type’s command lines are tested against every recording: a project for any target gives a working command line on every other, with the warnings it should.
  • An integration test, skipped without QEMU, starts the command lines on the installed QEMU, paused, and stops them.
  • A second script starts a sample project in each target’s container: the check to run before a release, and after a distribution updates its QEMU.

§8Starting a brick

poweron() runs these stages, each a method a test can call alone:

  1. Refuse a brick that isn’t configured or connected. As today.
  2. Start the bricks it plugs into, refusing a loop. As today.
  3. prepare(resume=None) returns a Deferred of what the command needs that takes work. Every brick asks its programs what they have (§7, once per program file) and checks its configuration against it; what the program lacks is left out, with a warning. A virtual machine also makes sure of the private copies of its disks and takes the audio driver from the settings; a tunnel writes its key.
  4. command(prepared) returns the command line, §6.
  5. spawn(argv) logs the command, puts sudo in front for a tap or a capture when Virtualbricks isn’t root, and spawns the process.
  6. Once the process runs, the event of on_start. As today.
  • Resuming a machine passes the state as an option, vm.poweron(resume="virtualbricks"), from the brick menu’s Resume. Today it sets config.loadvm and clears it once the machine started, and the key is saved in every project.
  • The tunnel’s key is written by prepare() with hashlib, into the runtime folder as <name>.key, readable by you only. It has the same bytes as echo password | sha1sum gives, the SHA-1 in hex, two spaces, a dash and a newline, so a tunnel still works with an older Virtualbricks at the other end. The shell and /tmp go.
  • What happens after a start, besides the events, stays as it is. Setting the tap’s address, which nothing does today, would be a stage after the process runs, §13.

§9Old files and the migration

  • The files stay at format 1. No release has written them yet, so the new names simply replace the old ones, and projectfile.UPGRADES stays empty.
  • A file this branch wrote before the change reads as any file with unknown keys: each old key is reported and dropped, and the new key takes its default. The 2.1 files these projects came from are still where they were, so a project can be converted again.
  • The migration of 2.1 projects writes the new names. RENAMED_KEYS in migrate/convert.py, which already maps basehda, gets the whole table of §4, and the conversion turns cdromen and deviceen into cdrom, noacpi=* into acpi = false, an empty argv0 into qemu-system-x86_64, and drops stdout, loadvm and portrait, saying so in its report.
  • It also rewrites the console commands of the events: vm1 config ram=512 becomes vm1 config memory=512, by the type of the brick named. A command it can’t read, or that names no brick of the project, is kept and reported C6. Shell commands are left alone.
  • The same goes for the settings: the migration of ~/.virtualbricks.conf writes terminal, tray_icon and the others, and a settings.toml of this branch loses its four renamed keys to their defaults, with a line in the log.

§12Decisions

QuestionOptionsDecided
C1 What the mark of a value says

A Equal to the field’s default or not, worked out when writing. Nothing to store, and any writer can add it from the data; a value you chose that equals the default reads as default.

B Remembered per field: the panels and the console mark what you set, the mark is written in the comment and read back with tomlkit. Exact, but the comments become data: a hand edit of a value must also edit its comment, and the importer and the migration have to carry the marks.

C Defaults written as commented-out keys (# memory = 64), set values as keys, as sshd_config does. Exact and read by tomllib, but a project then follows new defaults when Virtualbricks changes them, which undoes D4, every value written.

 Decided: A
C2 Comments you write by hand

A Dropped at the next save, as today; the header of each file says so.

B Kept: each file read with tomlkit too, and a comment put back beside the same key. It breaks when a key is renamed, and two writers share one comment.

 Decided: A
C3 Language of the comments

A English. B The language of the desktop that saved the file.

 Decided: A
C4 How command lines are built

A A command() method per type with the Command helper.

B Options declared on the fields, field(Bool(), option=Flag("-snapshot")), plus code for the rest. The -machine props, the CD-ROM, the clock, the kernel, Netemu’s pairs and the network cards each come from several fields, so the virtual machine would be split between the two places.

 Decided: A
C5 Layout of a brick’s keys

A Flat, as today; the disks and network cards stay tables.

B The virtual machine’s keys in tables by topic, [bricks.vm1.display], .kernel, .clock, .cdrom: shorter names, but a table per topic in every machine, grouped after panels still to be designed.

 Decided: A

B The old names accepted as well, for a while.
