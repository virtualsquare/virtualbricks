An Events Tab That Says What Happens

The Events tab takes the shape of the Bricks tab: a row per event that says in words what it does, after how long and because of which brick, a countdown while it waits, its menu, and its settings in the tab, where its actions are chosen instead of typed.

  • implemented

What changed: revision 2 applies your answers: the recommended one for seven questions, and the All or Waiting switch of the Bricks tab above the list (E3 B), now in every board; board X3 becomes A7, the waiting events. An action that changes a brick’s settings, today’s Brick config, goes to §10. The boards of the options not chosen stay for reference, X1, X2 and X4.

Implemented in eight commits from e48fc4b, one per step of §7, with these differences. The two menus make their items with the same helpers, and Run Now leaves a wait alone: the actions run now, and again when the delay is over. The rows of the events follow the bricks too, so a brick renamed, duplicated or deleted changes “when sw1 starts” at once. With the settings of a brick and of an event open in the two tabs, OK and Cancel close those of the tab they are in. In the editor, an action without its brick, event or command is left out. New Event keeps today’s 10 seconds, refuses a brick’s name too, which the console would read as the brick, and lives by the Events tab. On the way: a brick that stopped started its event for when it starts and never the one for when it stops; an event without actions failed the start of its brick; Start All stopped at the first event without actions; Delete on the last line of today’s panel failed. All four are mended, the last with the panel.

Since then: the modules of §7 are a package of their own, gui/mainwindow/events/, with the tab in tab.py and New Event in newevent.py (3cbac0e); rowtab.py stays in gui/mainwindow/, shared with the Bricks and Images tabs. The keys of the bricks have new names, and the migration of a 2.1 project rewrites the console commands of its events to them: vm1 config ram=512 becomes vm1 config memory=512 (step 10). The editor of A3 is a panel on a draft, as a brick’s settings are (ae2a782, step 11), and looks the same: an event saved without changes stays as it was written, and while it waits, a bar says that it runs its actions as they are when the wait is over, and that a new delay counts from its next start. The page of a project without events no longer has a New Event of its own: the one in the row above the list is always there (292f41f, step 12). The console redesign (step 14) changed the project file after all: starting and stopping a brick or an event are actions of their own, {kind = "start", target = "sw1"}, so the editor no longer reads them from the text, and a console command speaks the new grammar, brick set vm1 memory=512; a project of format 1 is rewritten once, when it opens (6975fc2). The editor’s console field shows a warning, with the reason in its tooltip, when the console can’t read it. eventinfo.py moved to bricks/, where the console reads it too (cc1b47e). The actions still run all at once. A brick or an event deleted no longer stays in the actions as missing: the delete drops the actions that start or stop it, and empties When It Starts and When It Stops of the bricks that ran the event; the dialog of Delete says so first, and a waiting event stops (7606cef, 32a9ef3, step 24).

§1At a glance

As bricks
The row above the list, with the All or Waiting switch (E3), a row per event with Start or Stop and its menu, the search, the keys, the page of a project without events, and the settings in the tab under Cancel and OK. The whole-window settings go for good.
Rows
What the event does in words, after how long, and which brick starts it; a countdown while it waits (E1, E2, E8).
Actions
Chosen, not typed: start or stop a brick or an event, or a command of the console or of the shell. A new event asks a name and a delay, then opens its settings (E4, E5).
Menus
An event’s menu gets Run Now. A brick’s menu gets When It Starts and When It Stops, in place of the Attach Event window (E6, E7).

§2The tab today

  • The Parameters column is the event’s text for the console: “Delay: 5; Actions: "sw1 on", "sw2 on"”, a shell command marked with an asterisk.
  • A “running” event waits for its delay, and nothing says how long is left. Once its actions have run, it is “off” again.
  • Start All Events stops at the first event that isn’t configured: poweron() raises, and the loop ends there. Start from the menu or a double click on such an event raises too, and nothing tells the user.
  • An event with a delay of 0 is “unconfigured”: it can’t run its actions at once.
  • Configure takes the whole window, titled “Configuring Brick” (T1).
  • In the panel, an action is a line of text in the console’s words; a checkbox makes it a shell command; the empty last line adds one. Delete on the last line fails: the panel calls self.model, which it doesn’t have.
  • New Event has no title. Brick config is always insensitive. Events collation opens the brick picker of Brick start, so it makes an event that starts bricks. A shell command event starts with the example action “new switch myswitch”, which creates a switch if left there (T2).
  • The brick picker says “Availables”, uses arrows made of dashes, the code’s kinds (“Qemu”) and the hatched grey icons.
  • Attach Event, in the brick’s menu, lists only the configured events and says “Assing nothing”. Nothing in the Events tab says which brick starts an event (T3).
  • The menu of an event is the old one of bricks: the name as its first item, untranslated labels.
  • Renaming an event moves it to the end of the list: the factory keeps them in a dictionary by name.
  • Renaming a brick leaves its old name in the actions of the events: they fail when the event runs.

§4Rows and states

What a row says (E1, E8)

The second line is the delay and the actions in words, then the bricks that start the event. Actions of the same kind are joined: “starts sw1 and sw2”. What the words don’t cover shows as the command itself.

The countdown moves every second while an event waits, and only then. A delay of 0 runs the actions at once when the event starts: “Not configured” is only for an event without actions. Start All starts the ready events, Stop All stops the waiting ones; nothing raises.

Keys and mouse

As in the Bricks tab: a double click or Enter configures; Delete asks to delete; F2 renames; the right button, Menu and Shift+F10 open the menu; Ctrl+F or typing searches, by name; Escape clears the search, or leaves the settings.

§6Editing an event

With E4 B, the settings of an event are the delay, a number of seconds, and a list of actions (A3). Each action has a kind and a subject:

KindSubjectSaved as, as today
Start a brick, Stop a bricka brick of the projectvb “sw1 on”, vb “sw1 off”
Start an event, Stop an eventanother eventvb “start-vms on”, vb “start-vms off”
Console commanda line for the consolevb “…”
Shell commanda line for sh -cshell “…”
  • The project file doesn’t change: the editor reads a console command “name on” or “name off” as starting or stopping a brick or an event when name is one, and anything else as a console command. What it saves reads the same way.
  • An action whose brick is gone, renamed or deleted, shows its old name marked missing, until it’s changed: today it fails when the event runs.
  • An event can’t start itself: its own name isn’t in the list of events.
  • With E5 B, New Event asks a name and a delay (A4), creates the event and shows its settings; Cancel there keeps the event, without actions. The brick picker and the shell command window go.
  • The settings close as a brick’s do: Cancel, OK, Escape, deleting the event, opening another project. The window’s whole-window settings go, with its frame.

§7Implementation plan

With the recommended answers. Each step is a commit with its tests, stopping for review after each. The Bricks tab keeps its behaviour and its tests throughout.

  1. What the two tabs share. The row above the list with its All switch, the list of rows that follows the factory, the page without items, the settings page, the keys and the count move from bricks.py and bricklist.py to a module both tabs build on. The Bricks tab stays as it is, and its tests pass unchanged.
  2. What a row says about an event. eventinfo.py, without widgets: the state, the seconds left, the actions read as kinds and subjects and back, the summary in words, and the bricks that start the event. An event with actions and a delay of 0 becomes ready: Event.configured() no longer asks for a delay.
  3. The menu of an event. eventmenu.py, as brickmenu.py, with Run Now. BaseMenu and EventPopupMenu leave gui.py.
  4. The tab. EventsTab on the shared parts: rows with the countdown, a call each second while an event waits; the row above the list, with All or Waiting; the empty page; the keys; the settings in the tab with today’s panel for now. The window’s whole-window settings go. Start All and Stop All no longer raise.
  5. The editor of actions. The delay and the rows of actions (A3), in place of today’s panel and the part of it that the shell command window shares.
  6. A new event. The small window of A4; the New Event window, the brick picker and the shell command window go.
  7. The events of a brick. When It Starts and When It Stops in brickmenu.py; the Attach Event window goes.
  8. The rest. What nothing uses any more in widgets.py and graphics.py, the hatched icons among them. A check of the whole application on Broadway, and this page marked implemented.

§8Tests

  • The shared parts: the Bricks tab’s tests, unchanged, and tests of what the module adds.
  • What a row says: each kind of action read and written back, the summary of mixed actions, the states, the seconds left with a fake clock, the bricks that start an event.
  • The menu: its items and their sensitivity, Run Now running the actions without touching a wait.
  • The tab: rows following the factory, the countdown starting and stopping with the waits, Start All and Stop All, the keys, the settings in the tab.
  • The editor: an event read into rows and saved back unchanged, each kind and its subject, adding and removing actions, a missing brick.
  • New Event, and the two submenus of a brick.

As before, each new test is checked against the code it guards, broken on a copy.

Why these: an event is its actions, so the row says them in words and the editor chooses them; the console’s words stay for the console (E1, E4). A wait with no end in sight is the question the tab answers worst today (E2). The Waiting switch keeps the two tabs alike (E3). One window for a new event, then the editor, lets an event mix kinds, which today’s kind-first windows can’t (E5). Two submenus replace a whole window, and the rows of events close the loop by saying which brick starts them (E6, E8). Run Now lets an event be tried without its delay (E7).

§10Later

  • Events that repeat, every so many seconds.
  • Actions in order, each after the previous one, where today they all start together.
  • The events in the Topology picture, next to the bricks they start.
  • The output of a shell command in the messages.
  • Renaming a brick or an event renames it in the actions that name it.
  • An action that changes a brick’s settings, as the console’s “sw1 config numports=16”: today’s Brick config of New Event, never enabled (E5).
