§1At a glance

Format
Mallard pages in help/C/, one topic each: how to make a lab, what each window does, what to do when something goes wrong. They link the man pages for the details (H1).
Pages
Sixteen pages in four groups: getting started, your lab, projects, and settings and beyond (§3, H6).
Opening
Yelp, through help:virtualbricks, when a program handles help: and the pages are where Yelp looks. Otherwise the browser, on the HTML built from the same pages and installed with Virtualbricks, or on the website copy if that isn’t there either (§4, H2).
F1
Help → Contents, with F1, opens the guide. F1 in a window opens that window’s page: the Settings window opens Settings, the Images tab Disk images. Settings, and the settings of a brick or an event, get a Help button too (§5, H4).
HTML
yelp-build makes it, a pre-commit hook keeps it in step, as the man pages are kept, and it is committed in help/html/. So a packager needs no Yelp tools (§6, H3).
Languages
English first. The pages are ready for itstool, which turns them into a .pot and back, as the program’s strings are (§6, H5).
Website
A task of the website branch copies the HTML of a commit of develop into the site, and the Documentation pages with it. make publish stops while the copy differs from that commit (§7, H7, H8).
Plan
Four steps on develop, a commit each, then one on website (§10).

§2Today

  • The Help menu has one item, About, the stock gtk-about item (gui/mainwindow/window.py, line 247). F1 does nothing. The accelerators of the window are Ctrl+N, Ctrl+O, Ctrl+S, Ctrl+P and Ctrl+Q.
  • The reference pages are for whoever already knows what to look for: virtualbricks(1), the command and the console; virtualbricks-config(5), the files; virtualbricks-vbp(5) and virtualbricks-archive(7), the archives; virtualbricks-control(7), the control protocols. Each has an HTML twin in docs/, and two are on the website. None of them says how to use the windows.
  • The README and the four posts of the website describe what is new in 3.0, not how to do a task.
  • The console has help, for its own commands.
  • Opening a link already has a pattern. markdownview.open_link(), projects.py and imagedialogs.py call Gtk.show_uri_on_window() and log a GLib.Error.
  • Finding installed files has a pattern too. i18n.find_localedir() looks in the checkout, then under sys.prefix, the user base and sys.base_prefix, so that the catalogs are found in a virtualenv and after pip install --user.
  • The desktop file is share/virtualbricks.desktop, so the usual id of the guide is virtualbricks. Page 18 plans org.virtualsquare.Virtualbricks as the id of the application. The guide can keep the short id, as help:gnome-terminal does.

§3The guide

Mallard is the format of the GNOME help: an XML page for each topic, linked into guides. A topic says which guide it belongs to, so the index lists the topics without being edited for each new one. Pages are short and task-shaped: “Make your first lab”, not “The New Brick popover”. yelp-check validates them against the schema and finds links to pages that aren’t there.

The guide is for someone at the windows. For the console, the files and the protocols it says what they are for, and links the man page that has the details. A Mallard conditional gives each link two forms: man:virtualbricks(1) for Yelp, which shows man pages, and the website copy in the HTML.

§4Opening it

A Mallard page needs a program to show it, and only Yelp does. Yelp registers the help: scheme. Without it, nothing handles help:virtualbricks, and Gtk.show_uri_on_window() raises. That is the usual case on Xfce, on KDE and under a bare window manager. Virtualbricks therefore picks the first of three ways that works:

  1. 1A program handles help:, and the pages are in a folder where Yelp looks: ~/.local/share/help or the help folder of a system data folder. This covers a Debian package and pip install --user.Yelp: help:virtualbricks/settings
  2. 2Otherwise, the HTML installed with Virtualbricks is found, as find_localedir() finds the catalogs: in the checkout, under sys.prefix, the user base or sys.base_prefix. This covers a virtualenv and a desktop without Yelp.the browser: file:///…/share/virtualbricks/help/C/settings.html
  3. 3Otherwise, the website copy, for an install that lost its files.the browser: https://www.virtualbricks.it/help/C/settings.html

The check for 1 looks at the folders before it opens anything, so Yelp never says “page not found” for pages installed in a virtualenv, where it doesn’t look. A failure to open is logged, as a link of the README is.

Checked on Debian 13, this machine. Yelp 42.2 handles help: through yelp.desktop. With XDG_DATA_DIRS and XDG_DATA_HOME on empty folders, Gio.AppInfo.get_default_for_uri_scheme("help") is None, and Gio.AppInfo.launch_default_for_uri("help:virtualbricks") fails with G_IO_ERROR 15, “The specified location is not supported”. Not tried: Yelp showing pages from ~/.local/share/help; KDE’s help center on a Mallard page.

§5F1 in each window

Each window names its page, and F1 opens it. The table of §3 lists them. The windows subclass dialogs/base.py’s Window since 12 October, so the key is handled once there: a help_page attribute, None for the guide’s index, and a key handler on the root widget that calls show_help(). In the main window, F1 opens the page of the tab in view, and of the settings in view: each tab gets help_page too, and a panel names its page, machines for a machine’s.

The places with a row of buttons get a Help button as well, on the left: the Settings window, where GTK puts Gtk.ResponseType.HELP, and the settings of a brick or an event in their tab, beside Cancel and OK. The windows with a header bar keep F1 only, since a header bar has no room for Help without a menu.

The windows of --connect are the same windows, so they open the same pages, from this computer. The remote page tells the lab machine apart from this one.

§6Build, install, translate

In the sources

  • help/C/*.page, the pages, and later help/C/figures/.
  • help/html/C/, the HTML that yelp-build html makes: one .html for each page, plus C.css, yelp.js and highlight.pack.js. It is committed, as the man pages are (H3).
  • A pre-commit hook, help, beside man: on a change to help/C/ it runs yelp-check validate, yelp-check links and yelp-build html. Like man, which needs pandoc, it needs yelp-tools on the machine that commits, and nowhere else.

Installed

  • share/help/C/virtualbricks/, the pages, where Yelp looks.
  • share/virtualbricks/help/C/, the HTML. Not share/doc/: the Ubuntu container images leave /usr/share/doc/* out.
  • Both in [tool.setuptools.data-files], a key for each folder, as the man pages are listed. MANIFEST.in takes help/ into the sdist.

Languages

English first (H5). Later, itstool writes a .pot of the pages, the translators fill a .po for each language as for the program, and itstool -m writes help/<lang>/. Yelp then picks the language of the desktop by itself. For the HTML, show_help() picks the folder of the language, else C. The l10n hook could run it.

Checked with yelp-tools 42.1, itstool 2.0.6 and mallard-rng from the Debian 13 packages, unpacked in a scratch folder, on four sample pages. yelp-check validate refuses a page with an unknown element. yelp-check links names an xref to a page that isn’t there, and exits with 1. yelp-build html makes 196 KB with no remote resources, and keeps the if:test="target:html" paragraph of a pair while dropping its !target:html twin. In the ubuntu:22.04 image, dpkg leaves out /usr/share/doc/* and /usr/share/man/*; the debian:bookworm image leaves out neither. The versions of yelp-tools on the other targets aren’t checked: only the machine that commits needs them.

§7The website

The website is the website branch of the same repository: Pelican, published by hand with make github, which builds with publishconf.py and pushes gh-pages to virtualsquare. There is no CI. The help has one source, the HTML in help/html/C/ of develop, and the website takes a copy of it from a commit, as it should take its Documentation pages.

The copy

  • A task, invoke sync-docs REF, in tasks.py. It empties content/help/C/, so that a page removed from the guide leaves the site too, and fills it from git archive REF help/html/C. It says which commit REF was in the local repository; a fetch first makes it the published one.
  • The Documentation pages with it. config-files and control-protocols are made by hand today from docs/*.html: the page’s head up to <body> kept, the body after </style> taken as it is, the <style> moved into NAME.css. The task does the same for each page that content/documentation/ has, from the same commit, so the guide and the pages it links never come from two commits.
  • A commit on website, as now, with the commit of develop in its message: Help and Documentation of develop 2c4eb22.
  • A check, invoke sync-docs --check REF, which changes nothing and exits with 1 when the site differs from REF, naming the files. The publish target of the Makefile runs it first, so make github stops on a stale copy instead of publishing it.

In Pelican

The help is copied as it is, not read as content. pelicanconf.py gets help in STATIC_PATHS, and in ARTICLE_EXCLUDES and PAGE_EXCLUDES. A Help item in the menu of the site, beside Documentation, links /help/C/, and so does the first post.

The pages keep the look of the GNOME help, not that of the site. yelp-build html -x imports a stylesheet of our own, which could add the site’s name and a link back to it; that is for later.

Which commit

While 3.0 is in development the site describes develop, as its posts and its Documentation pages do. Once 3.0 is out it should describe the release, since the last way of §4 sends every installed Virtualbricks to /help/C/. One copy, of develop now and of the latest release then, is enough while one version is in use (H7). A copy for each version, under /help/3.0/C/, with the version in the address that show_help() opens, is the step after, if older versions stay in use.

Checked with Pelican 4.11 on the website branch at b35197b, in a scratch worktree, with the sample pages of §6 in content/help/C/. Without the three settings, Pelican reads each page as an article and skips it with an error. With them, output/help/C/ has the files byte for byte, C.css and yelp.js too. yelp-build html lists -x CUSTOM, “Import the custom XSLT file”.

§8Other directions

  • Markdown in a window of Virtualbricks. The Readme tab already draws Markdown, with pictures (page 05). A Help window with a list of pages on the left would need nothing outside Virtualbricks. But it would be a viewer of our own to keep: links between pages, search, the language of the pages, and no copy for the browser or the website without a second renderer.
  • HTML by hand, in the style of the reference pages, opened in the browser. It has one form and no tools, but no schema, no link check, and no way to translate a page but copying it.
  • Yelp only. The pages and help:virtualbricks, with Yelp in the package’s Recommends. It is the least code, but on a desktop without Yelp, Help shows an error.
  • DocBook, which the GNOME help used before Mallard. Yelp still reads it, but it is a book in chapters, heavier to write, and the GNOME guides moved away from it.

Tests

  • The pages against the code: each help_page of a window or a tab names a page of help/C/; each page has its HTML in help/html/C/; pyproject.toml lists every page. These need no tools.
  • yelp-check validate and links on help/C/, skipped where yelp-check isn’t installed.
