Virtualbricks Disk Images Redesign

One place for the disk images of a project, which says what each image is, who uses it and what a change would touch; a disk picker in every machine; and the operations that can lose work made safe or made explicit.

§1At a glance

Recommended
An Images tab in the main window (board B), beside Bricks and Events, with the list, the details of the selected image and This project / All projects. In each machine, the disks it has, each with an image picker and a mode (board D1).
Library
Each image says its format, the size of the disk, the space it takes, whether its file is there, and which disks use it and how: a private copy, the image itself, running or not. All projects adds the other projects that use the same file, and the files of the image folder that no project uses.
Adding
One Add, from the library and from the picker: an existing file, read with qemu-img info and copied to the image folder by default, or a new empty disk, qcow2 or raw, created in the image folder and added at once.
Safer
Remove says which disks lose their image. Finding a missing file points the private copies at it, where today changing the path of an image makes the next start set every private copy aside and begin from an empty one. Merging a private copy into its image lists everything else the image changes for, and offers to save a new image instead.
Code
What the library knows goes in virtualbricks/config/images.py, without GTK. The long operations, saving a disk as a new image and merging, run in the process that imports and exports archives, with their progress. Five dialog modules go.
Unchanged
The images of a project stay in its project.toml, and a disk still names its image. The image folder is still <workspace>/vimages, and a private copy is still <vm>_<device>.cow in the project.

§2What gets in the way today

From the code on this branch; the canvas redraws these windows in its first row.

The library

  1. Four places manage images: the Images library window, the three other items of the Disk images menu (Create new image, New image from file, Commit cow image), and three buttons in the Drives tab of every machine.
  2. The library can't add an image, only edit one (disklibrary.py). Its edit screen replaces the list in the same window.
  3. Remove removes at once, without asking, even an image that disks use; they keep its name, and the next opening of the project reports them.
  4. “Used by” and “COWs” count the same thing, the private copies (set_cell_used_by and set_cell_cows); a machine that uses the image itself isn't counted anywhere. “Master brick” shows the repr() of a disk.
  5. Size is the length of the file, in KiB, MiB or GiB (Image.get_size): neither the size of the disk the machine sees nor the space the file takes. A missing file shows 0B and nothing else.
  6. Nothing crosses projects: the library shows the images of the open project, and nothing says which other projects use the same file, or which files of vimages no project uses any more, as the copies an import leaves.

Adding and creating

  1. Create new image makes the file and stops: create_image returns its name and path, and nothing adds it to the library, so you add it again with New image from file.
  2. Its formats are those of old Qemus: raw, qcow, qcow2, cow, vmdk and cloop, “Auto” meaning raw. The folder chooser doesn't start in the image folder.
  3. New image from file reads a <file>.vbdescr for the description, and says nothing about the file: format, size, backing file.

Using images

  1. Changing the path of an image loses the private copies: the next start finds each private copy on the old path (Disk._ensure_private_image_cow), renames it <vm>_<device>.cow.bak-<date> and makes an empty one, so the machine starts without its changes, with a warning in the log.
  2. Commit merges into an image that others may use without a word: the changes reach every private copy made on it, here and in other projects, which may stop working. Commit asks for a file; “Commit virtual machine changes” logs “not implemented”.
  3. The Drives tab has seven rows, hda to mtdblock, each a combo of names and a Private COW check. Nothing says what an image is or whether its file is there; Snapshot mode is a check with no word on what it does.

Implementation

  1. commitdialog.py is dead code: no window uses it.
  2. The image lock (Image.master) is right, a disk that writes the image itself takes it while the machine runs, but only its repr() ever shows.

The list and the details (boards A and B)

  • A row shows the name, one line of facts, “qcow2 · 4.0 GB disk · 612 MB on disk”, and one line of use, “r1, r2 and r3, private copies”. An image whose file is missing shows so, in the warning colour; one that a running machine writes shows In use.
  • The details add the path, the description, the backing file, the snapshots (suspend and resume use one), when the file changed, each disk that uses the image with its mode and the size of its private copy, and, in This project, the other projects that use the same file.
  • The actions: Rename…, Edit Description…, Show in Files and Remove…; for a missing file, Find the File…. Add… in the header bar or the toolbar.
  • The facts come from qemu-img info, read in the background for each file and kept while its size and time don't change, so the list fills in as it's read.

§5Choosing an image for a disk

The canvas's third row.

  • D1, the disks of the machine (board D1): only the disks the machine has, each with its device, an image picker, a mode and a menu; Add Disk offers the free devices, hda to mtdblock. Under each disk a line says what the mode does: “r1’s changes are kept in r1_hda.cow, 18 MB, in the project; frr-debian stays as it is.”
  • D2, today's grid (board D2): the seven rows stay, with the same picker and mode, and the three buttons become Add an Existing Image…, New Empty Disk… and Manage Images…. The smaller change.

Recommended: D1 (L3). A machine has one or two disks; seven rows hide them among empty ones.

In both

  • The picker lists the library with the facts of each image, the machines that use it and a warning for a missing file, then Add an Existing Image…, New Empty Disk… and Manage Images…. What it adds is chosen for the disk.
  • The mode replaces the Private COW check: Private copy, the default, or The image itself, which the machine writes and locks while it runs, the lock that exists today.
  • Snapshot mode stays a setting of the machine, said as what it does: “Forget every change when r1 stops”.
  • The disk menu: Save as a New Image…, Merge into <image>…, Start Over from <image>… (the private copy goes to the trash and an empty one is made at the next start), Show in Files and Remove Disk.
  • The CD-ROM stays a file or a drive of the computer, not an image of the library: an ISO file is used as it is, never copied or written (L10).

§6The dialogs

The canvas's last row; they go with either place and either Drives tab.

Add an Existing Image

  • The file is read with qemu-img info as soon as it's chosen: format, size of the disk, space taken, backing file. A file that isn't a disk image says so, and Add waits.
  • The name starts from the file name, checked as you type against the names of the library.
  • A file outside the workspace is copied to the image folder by default, with its size said; Use it where it is keeps the path (L4). A copy keeps the holes, and a file with a backing file is used where it is.
  • The description starts from a .vbdescr beside the file, if there's one (L12).

New Empty Disk

  • Name, size in MB or GB, and format: qcow2, the default, or raw (L8). The file goes in the image folder, under the name, and Change… picks another place.
  • The image is added to the library when qemu-img create ends, and from the picker it's chosen for the disk.

Remove

  • It lists the disks that use the image: they keep no image and can't start until another is chosen; their private copies stay.
  • The file stays, except that, when it's in the image folder and no other project uses it, the dialog offers to move it to the trash with its size (L5). Without a trash, as the projects, it deletes for good and says so.

Find the File

  • For an image whose file is missing. When the image folder has a file of the same name and size it's offered first; else Choose a File….
  • The private copies are pointed at the new file with qemu-img rebase -u, the step the import already does, before the path changes, so no machine loses its changes. The same holds whenever the path of an image changes.

Save as a New Image, and Merge

  • Save as a New Image writes the image with the disk's changes, standalone, with qemu-img convert, to the image folder, and adds it; Use it for r1’s hda, on by default, gives the disk the new image and an empty private copy. The machine is stopped first.
  • Merge writes the disk's changes into the image with qemu-img commit. The dialog lists everything else that uses the image, here and in other projects, says their private copies may stop working, and offers Save as a New Image Instead. Every machine that uses the image is stopped first. Kept behind that warning (L6).
  • Both run in the archive process, with their progress, and can be stopped; a stopped Save leaves no file (L7).

Rename and Edit Description

Rename changes the name in the project, as today through the factory, so the disks follow; the file keeps its name (L11). The description is edited in place.

§8The code

What the library knows, without GTK, as the rule of config wants, beside the workspace:

  • The factory keeps the library: new_disk_image, rename and remove_disk_image, which returns the disks it leaves without an image. A new relink(image, path) rebases the private copies before it changes the path. Image.get_size and the "m" and "s" formats go.
  • A disk gets a mode for the picker, over the private<dev> field that the project file keeps; the file format doesn't change.
  • The workspace's summaries count, for each image, the disks that use it, so All projects reads what the Projects window has already read.
  • The archive process gains two jobs, save-image (qemu-img convert) and merge-image (qemu-img commit), on the QemuImg it already has, with the progress of -p, cancelling and the removal of what a stopped job wrote. qemu-img info and create are quick and run from the application.

§9Implementation plan

Each step leaves the application working and can be committed on its own; the tests go with each step, as for the projects.

  1. The model, and the fixes that need no new window. config/images.py; relink with the rebase, used by the edit screen of today's library; Create new image adds what it creates; Remove asks; the columns count the disks right, and the sizes come from qemu-img info.
  2. The library, in the tab or the window as L1 decides, with Add, Rename, Edit Description, Remove and Find the File. disklibrary.py, loadimagedialog.py and createimagedialog.py go, and the Disk images menu with them.
  3. The Drives tab, with the picker, the mode and Add Disk.
  4. The disk menu: Save as a New Image and Merge in the archive process, and Start Over. commitimagedialog.py and commitdialog.py go.
  5. All projects, with the counts in the workspace's summaries, and the files of the image folder that no project uses.

§11Later

  • One library for the workspace (S2), if the images should be defined once and shared by name.
  • Compacting an image, with qemu-img convert, to give back the space of deleted data.
  • The snapshots of an image, listed and deleted from the details, beyond the one that suspend and resume use.
  • Matching images by checksum rather than name and size, for Find the File and the import.
  • Dropping a file on the library or on a disk to add it.
