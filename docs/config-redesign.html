How settings and projects are stored, described and upgraded: one readable format, one schema per brick type, and a migration that runs once, so the rest of the code only knows the new files.

§1At a glance

Format
TOML for every file. It's read with tomllib on Python 3.11+, or with tomli on Ubuntu 22.04's Python 3.10, and written with tomlkit. Both distributions package all three.
Files
Three kinds of file, split by who owns them:
  • settings.toml for your preferences;
  • state.toml for what the app remembers;
  • project.toml in each project.
Sockets move to your private runtime directory ($XDG_RUNTIME_DIR). The lock stays global at /tmp/vb.lock for now.
Projects
A project is a directory in the workspace with a versioned manifest. The manifest holds the full configuration, defaults included, plus the project's own settings, which start as a copy of the app settings. One project is open at a time, as today.
Schemas
Each brick type declares one schema as an attrs class: typed fields with defaults, limits and references. The loader, the writer, validation, the console's config command and rename all read it.
Migration
One engine that understands every old format, with three ways to run it:
  • automatically at startup, in a window;
  • as python -m virtualbricks.migrate INPUT OUTPUT on copies;
  • from the virtualbricks-migrate window, also opened by --gui.
Old files are never touched, and old .vbp archives stay importable.

Configuration lives in two places with two different formats, and running bricks put their sockets inside the project.

Every brick also has pon_vbevent and poff_vbevent, the events that run when it starts and when it stops.

A schema already exists, in embryo

Each type declares a parameters dict of Parameter objects: String, Integer, SpinInt, SpinFloat, Boolean, ListOf, plus the special Device, Command and UsbDeviceParameter. A parameter converts one value to and from its text form in the file, and the spin kinds carry a range.

That's the seed of what you're asking for, but it has three limits. It's tied to the text format, it checks nothing beyond ranges, and it can't describe nested data such as a VM's network cards or Netemu's states.

§3Problems worth fixing

Security · fix independently of this redesign

Opening a project can run code. ListOf.from_string calls eval() on text from the file (base.py:177). Passing empty globals doesn't help, because eval still reaches the builtins. A crafted value such as [__import__('os').system(…)] runs when the project opens; I confirmed this with os.getcwd().

Event actions and VM USB lists use ListOf, and projects arrive from other people as .vbp archives.

Bugs found while reading

  • A saved USB device list can't be loaded. The writer stores bare ids, but UsbDeviceParameter.from_string calls UsbDevice(id), and UsbDevice needs an id and a description (virtualmachines.py:746). Opening such a project fails with a TypeError.
  • A wire whose left end is unconnected comes back with its right end on the left. The unconnected plug is saved as link|wf||…, which the parser ignores, and the loader then gives the next link to the first free plug.
  • Renaming an event breaks the bricks that use it. Their pon_vbevent and poff_vbevent keep the old name, because references are plain strings and rename only updates the factory's own index.
  • The MAC address pattern accepts g and h as hex digits (_configparser.py:69).
  • Only one user per machine can run Virtualbricks. While one user runs it, or after their instance crashed, another user can't start it. /tmp/vb.lock is shared, and the lock check raises a permission error on the other user's lock. This stays as it is for now (D3, §14).

The format

  • Three dialects. Settings are configparser INI, and projects use a hand-written line format with its own parser. Netemu adds a second syntax inside its own section and reads it by seeking in the file object (wires.py:376–564).
    • Two different writers produce project files: Base.save_to writes key=value and ProjectEntry.dump writes key = value.
  • Values are text whose meaning depends on the parameter.
    • Booleans are * or empty, and the command-line builder tests for "*" directly (bricks.py:388).
    • Lists are Python literals.
    • Image descriptions join their lines with <nl>.
  • Meaning hidden in line order. The order of the link lines decides a VM's card order and a wire's left and right ends, which Netemu's LR and RL values refer to.
  • No version number. The compatibility code for older files runs on every load, forever, and decides by guessing. It covers the Wirefilter, DiskImage and Project sections, Qemu base… keys and SwitchWrapper numports (configfile.py:274–329), and single-file projects (project.py:460).

Defaults

  • Projects store only values that differ from the default (base.py:247). Changing a default in the code silently changes every existing project.
  • Settings do the opposite. The file always contains every key, defaults included, so a changed default never reaches existing users. The default sudo is still /usr/bin/gksu, which current distributions no longer ship.

State and layout

  • Opening a project changes a global path. It reassigns settings.VIRTUALBRICKS_HOME to the project directory (project.py:249, 335), and socket paths are derived from it every time they're used (bricks.py:437, switches.py:52).
  • Opening a project rewrites your settings file, because current_project is stored there.
  • Sockets are created inside the project directory. They end up in copies and exports, and a deep workspace path can exceed the 107 bytes allowed for a Unix socket path.
  • Project.exists() creates the directory and deletes it again to find out (project.py:289).

§4Goals and non-goals

Goals

  • One format for every file: readable, editable by hand, with real booleans, numbers and lists.
  • One schema per brick type, read by everything that loads, saves, validates or edits a brick.
  • Self-describing projects: versioned, complete (every value and the settings they depend on), and with no global state tied to the open one.
  • Old formats handled in one place, once. The runtime reads and writes only the current format.
  • A migration you can try on copies and watch as it runs.
  • Only packages available in Ubuntu 22.04 and Debian 13.

Non-goals

  • Changing how QEMU and VDE are started: the command lines stay the same.
  • Redesigning the configuration dialogs: they keep their layout and get validation from the schema.
  • Moving disk images or private COW files.
  • Project templates, projects outside the workspace and several open projects D6.
  • Merging hand edits into an open project. While a project is open the app owns project.toml and overwrites it at the next autosave.

§5File format

The format has to be written by the app, since autosave runs every three minutes. It also has to be read back without surprises and still be pleasant to open in an editor.

Decided: TOML D1, written with tomlkit D2. YAML's type guessing does bite in these files, because MAC addresses are everywhere. PyYAML reads QEMU's default 52:54:00:12:34:56 as the integer 41135085296 unless it's quoted, and no as false. I tested this with PyYAML 6.0.3.

TOML caveats

  • There's no null. An unset reference is an empty string (pon_vbevent = ""). Since every field is written, a missing key only shows up in a hand-edited file.
  • Dots in brick names need quoting. Brick names may contain a dot, which TOML reads as a key separator. The writer quotes such names ([bricks."vm.1"]), and hand edits must too.
  • Why tomlkit rather than tomli-w.
    • tomli-w 1.0.0, the version in both distributions, puts each record on one long line and every number of a matrix on its own line. It also escapes line breaks.
    • tomlkit 0.9.2, Ubuntu 22.04's version, writes records as [[…]] blocks and keeps short arrays on one line. It also keeps comments when it rewrites a file, which matters for a hand-edited settings.toml.
  • Multi-line text stays out. The project description remains in README.

§6Where files live

Files are split by owner and lifetime: what you set, what the app remembers, what exists only while bricks run, and the projects themselves.

  • settings.toml changes only when you change a setting. Switching projects writes state.toml instead.
  • The runtime directory is private and short. It belongs to your user, is cleared at logout, and keeps socket paths well under the 107-byte limit. If $XDG_RUNTIME_DIR isn't set, the app falls back to a 0700 directory under /tmp named after your user id.
  • The lock stays /tmp/vb.lock D3. A per-user lock is noted for later in §14.
  • The workspace stays where it is. It holds gigabytes of images, and paths inside projects point into it.
  • Moving sockets changes their paths. Anyone who attaches an outside tool to ~/.virtualbricks/<project>/sw1.ctl needs the new path, so the switch's panel should show it.

§7The project file

This example lab has a VM, two switches, a tap, a Netemu link with two Markov states and a start event. Every field is written; where this document shortens a brick, a # … comment says what's left out. The other comments are for this document too, and the app doesn't write any.

Rules

  • format is the file's version. The app reads only the current version. Older files go through the migration first, and newer ones are refused with a message that a newer Virtualbricks wrote them.
  • [settings] is the project's own copy of the per-project settings D5. It's always complete and overrides the app settings while the project is open (§8).
  • images, events and bricks are tables keyed by name. TOML itself rejects duplicate keys. The loader also checks, as the app does today, that no name is used in more than one of the three.
  • type is the lowercase registry name D7: qemu, switch, switchwrapper, tap, capture, wire, netemu, tunnellisten, tunnelconnect or router. The old Wirefilter becomes netemu.
  • Every field is written, defaults included D4. When a default changes in the code, existing projects keep their stored value, and only new bricks get the new default. Adding a field is a format change whose step writes the field, with its default, into older files.
  • Hand-edited files are read leniently. A missing field takes its default, and an unknown field is dropped at the next save. Both are reported in the messages window.
  • Connections belong to the brick that owns the plug, in an explicit order. The separate link lines disappear.
    • connect for bricks with one plug (tap, capture, tunnels).
    • endpoints = [left, right] for wires and Netemu. An unconnected end is "", so an end can no longer change sides (§3).
    • A nics list for VMs, in the order the guest sees the cards.
  • A connection names its target. "sw1" is a brick's only socket, and "vm2:sock_eth1" is a VM's socket card. kind = "hostonly" replaces the _hostonly pseudo-socket.
  • Each disk becomes disks.<device> = { image, private }, replacing the hdX and privatehdX pairs. All seven devices are written, unused ones with an empty image.
  • A name field that only repeats the brick name is dropped, for VMs and routers. Netemu states keep theirs, because there it names the state.

§8Projects

Per-project settings

  • A new project starts from the app settings. Creating a project copies the current values of the per-project settings into its [settings].
  • From then on the project's copy wins. While the project is open, every per-project setting comes from its [settings], and app-only settings come from settings.toml.
  • Migrated projects get a copy of your migrated app settings, so they behave exactly as they do today.
  • The settings window gets three groups: Application (the app-only settings), This project (the open project's copy) and New projects start with (the starting values in settings.toml).
  • The per-project settings are cowfmt, erroronloop, femaleplugs, qemupath and vdepath. The rest stay app-only, because they're about you or your machine rather than the lab S2.
  • Imports carry the other machine's paths. An imported project's qemupath and vdepath may not exist on your machine. The import dialog shows them next to this machine's values, and preselects this machine's when the project's paths don't exist here S3.

Lifecycle

  • Create writes a manifest with format = 1 and a complete [settings]. Today it creates an empty .project.
  • Open loads the manifest, validates it, builds the bricks and records the project in state.toml. Nothing global changes: the open project is an object, and runtime paths come from the runtime directory plus the project name.
  • Save writes a temporary file, syncs it and renames it over project.toml. The rename is atomic, so the .project~ and .project.back recovery at startup goes away.
  • Rename and copy stay directory operations. Private disks are named after the VMs, not the project.
  • Export archives the directory as today, and there are no sockets left in it to skip.
  • Import extracts the archive and, if it holds a legacy .project, migrates it first D9. The existing image remapping and COW rebasing then edit the manifest through the schema instead of ProjectEntry.
  • A project exists when its project.toml exists.

§9Settings and state

  • Every setting is written, like in project files S1. Opening the file shows all of them, and a default that changes in the code reaches existing users only through a format step.
  • App-only settings: workspace, term, sudo, ksm, systray and show_missing.
  • Per-project settings: cowfmt, erroronloop, femaleplugs, qemupath and vdepath. Here they're the starting values for new projects S2.
  • Dropped because nothing reads them D10:
    • alt-term and cdroms;
    • kvm, since each VM has its own kvm field;
    • python, which the settings window writes but nothing reads.
  • Settings get a schema too, with each key marked app-only or per-project.
  • Settings become a normal object loaded at startup. The settings module stops replacing itself in sys.modules when it's imported.

What reads the schema

  • The loader turns a table into a typed config, and an error names the exact place: bricks.sw1.numports: 500 is outside 1–128.
  • The writer turns it back, in schema order, writing every field.
  • The console's sw1 config numports=64 parses the text by field type, which today's Parameter.from_string does.
  • The configuration dialogs validate before OK and offer references as pickers.
  • Reference checks and rename. The loader checks references when it reads a project, and rename updates every reference to the renamed item.
    • Event actions stay free text (sender on), so renaming a brick can't rewrite them. The rename dialog can warn about them instead.
  • The migration validates a converted project before it writes it.
  • Optionally, a generated JSON Schema lets editors complete and check project.toml, for example the Even Better TOML extension through taplo.

The config holds data only

Today a VM's disk fields hold live Disk objects bound to Image objects, and Netemu swaps self.config for the current Markov state. In the new model the config is plain data. Bricks build their runtime objects (disks, image locks, sockets) from it, and the command-line builders read typed values instead of testing for "*".

§11Migration

One module, virtualbricks.migrate, is the only code that knows the old formats. Today's parser and compatibility builders move into it, and everything else reads and writes the new files. It stays for good, so old .vbp archives remain importable D9.

What it does

  1. Lock. When the command or the window migrates your real files, it holds the app's lock, /tmp/vb.lock (LOCK_FILE in app.py), so the app can't run at the same time. If Virtualbricks is already running, the command exits with status 3 and the window asks you to close it. At startup the app holds the lock already. Migrating copies into a test folder, and a dry run, need no lock.
  2. Settings. It converts .virtualbricks.conf.
    • It drops the keys nothing reads and keeps every other value as it is.
    • It warns about programs and directories that don't exist, such as sudo = /usr/bin/gksu.
    • It moves current_project to state.toml and writes settings.toml in full.
  3. Single-file projects left in the workspace, which ProjectManager2.upgrade handles today, become project directories first.
  4. Projects. For each project directory without a project.toml:
    1. Finish an interrupted save the way today's loader does, putting .project~ back over .project.
    2. Parse .project with the old reader, which tracks line numbers for the messages.
    3. Convert it section by section, filling every field the file left out with today's default.
    4. Add [settings] from the migrated app settings.
    5. Validate the result against the current schemas.
    6. Write project.toml atomically.
  5. Report, for each project, what was converted, what was dropped and why, and any errors.

Three ways to run it

The engine is one function, and each of these calls it:

  • At startup, when the app finds old files and no new ones. It migrates your real files in place, showing the migration window described below with its destination fixed to "in place". The app continues when you close the window. Without a display, the report goes to the log instead.
  • From a terminal, with an input folder and an output folder, so you can test on copies without touching ~/.virtualbricks:
    • --in-place instead of the two folders migrates your real files, like startup does.
  • In a window, which shows the projects, the progress and the errors. Three commands open it, and they take the same options:
    • virtualbricks-migrate, installed with the app;
    • python -m virtualbricks.migrate --gui;
    • python -m virtualbricks.migrate.gui.
    The folders, --settings and --in-place fill in the form, and the window checks them when you press Check or Migrate. --copy-files, --dry-run and -v are for the terminal only; in the window, Check is the dry run.
  • INPUT is an old workspace: a folder of project directories, for example a copy of ~/.virtualbricks. It's only read.
  • OUTPUT must be new or empty. It receives the layout below.
  • --settings FILE also migrates an old settings file. Without it, projects get today's default settings.
  • --copy-files also copies each project's disks and other files. It's off by default, because private disks can be large.
  • --dry-run converts and validates everything but writes nothing, and -v also prints informational messages such as "Wirefilter became netemu".
  • --gui opens the window instead, filled with the other options: python -m virtualbricks.migrate --gui ~/vb-copy /tmp/vb-test.
  • Exit status: 0 when every project migrated (warnings are fine), 1 when at least one failed, 2 for bad arguments, and 3 when Virtualbricks is running and --in-place was given.
  • The output is laid out like the XDG directories, so you can open the result in the app without touching your real files: XDG_CONFIG_HOME=/tmp/vb-test/config XDG_STATE_HOME=/tmp/vb-test/state virtualbricks.
  • Close your normal instance first, because the lock is still global.
  • Without --copy-files, a VM with a private disk starts from a new copy-on-write image.

Safety

  • Old files are never modified, moved or deleted. Going back to 2.1 still works, but 2.1 won't see changes made after the migration.
  • Running it twice is harmless: a project that already has a project.toml is skipped.
  • A project fails only when it can't be represented, for example two sections with the same name, or when its files can't be read or written. It stays untouched and is listed in the report.
  • An invalid value falls back to the default with a warning, instead of failing the whole project. An example is a MAC address containing g.
  • Images whose file is missing are kept. Today's loader drops them silently (configfile.py:202).

Future format changes

Each file carries format. A format change is a numbered step that rewrites the plain table from version N to N+1. Adding a field is one: its step writes the new field with its default. The loader applies the missing steps before the schema sees the data, and the next save writes the new number.

Each step comes with fixture files of before and after. This keeps the runtime single-format for every later change too.

§12Implementation plan

Done on the branch, not committed yet. All five steps below are implemented, with 381 tests. The tests cover every line and branch of virtualbricks.config, project.py and virtualbricks.migrate. They pass on the repository's Python 3.10, on an Ubuntu 22.04 set (Twisted 22.1, attrs 21.2, tomli 1.2.2, tomlkit 0.9.2) and on Debian 13's Python 3.13.

  1. Schemas.
    • Add the registry and one attrs schema per type, plus one for settings.
    • Configs hold typed data, and the command-line builders and the console read typed values.
    • Rewrite the config["…"] sites to attributes.
    • Files don't change yet: the old reader and writer go through the schema, so this can land in small steps with tests.
  2. New files.
    • TOML reader and writer for projects, settings and state.
    • Per-project settings, and the three groups in the settings window.
    • A project lifecycle without VIRTUALBRICKS_HOME.
    • The runtime directory for sockets, and atomic save.
  3. Migration engine. Move the old reader into virtualbricks.migrate, give it line numbers, and add the report and the import path.
  4. Migration front ends.
    • The python -m virtualbricks.migrate command, with input and output folders and --in-place.
    • The virtualbricks-migrate window, registered under [project.gui-scripts] in pyproject.toml.
    • The startup hook that opens the window.
  5. Cleanup. Delete ProjectEntry, the CompatibleBuilder classes, ProjectManager2 and the Parameter classes.

Where the code lives

project.py stays at the top level: it manages the workspace and its archives, and most of the app uses it.

Tests

The test suite, removed in 8584bba, is back. Its layout mirrors the package: the tests of virtualbricks/migrate/gui.py are in virtualbricks/tests/migrate/test_gui.py. Test modules keep the test_ prefix, because trial only collects those when it walks a package.

Run them with PYTHONPATH=. python -m twisted.trial virtualbricks.tests. Every test gets its own home, XDG directories and lock file, so it never touches your files or a running Virtualbricks.

  • Migration fixtures. The engine, the command and the window run on fixture workspaces in temporary folders, and the tests check the files they write and every message of the report.
  • Their sources. The old fixtures (the sample above and the PROJECT and HOSTONLY_CONFIG projects) come first, then new ones for Netemu with several states, events, USB lists, VM socket cards and unconnected wire ends.
  • Per brick type: a round-trip test, and tests for its error messages.

Dependencies. The new ones are tomli (only below Python 3.11) and tomlkit. For Debian packaging that means python3-tomli on Ubuntu 22.04, and python3-tomlkit on both.

§14Later

  • A per-user lock, from D3. The lock would move into $XDG_RUNTIME_DIR, next to the sockets, so users on the same machine stop blocking each other (§3). It would also let a test instance run next to your normal one. LOCK_FILE in app.py is the one place to change, and the migration takes the lock through the same constant.
